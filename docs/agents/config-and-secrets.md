# 配置与密钥规范

适用于全部服务。配置基类在 `lib/config/`，运行时可变参数机制在 `lib/runtime/params.py`（见 [`project-structure-python.md`](project-structure-python.md) §4）。

配置错误的特征是**它在测试环境永远是对的**——测试环境什么都配好了。配置的缺陷只在部署时暴露，而那通常是最不想调试的时刻。因此这份规范的重点是：**让配置错误在启动的第一秒响亮失败，而不是在运行第三天静默地做错事。**

---

## 1. 来源与优先级

```
命令行参数  >  环境变量  >  .env 文件  >  代码内默认值
```

- **生产环境只用环境变量**（或挂载的密钥文件）。`.env` 是本地开发的便利，不进生产镜像。
- 配置对象在**启动时一次性构造并冻结**，之后只读。不允许运行中途改环境变量再重读——那会让同一进程的不同代码路径看到不同配置。
- 唯一的例外是**运行时可变参数**（§7），它有自己的机制与边界。

---

## 2. 命名

```
<SERVICE>_<GROUP>_<KEY>
```

| 例 | 含义 |
|---|---|
| `PLATFORM_POSTGRES_HOST` | platform-server 的数据库主机 |
| `PLATFORM_APP_ROLE` | platform-server 的运行角色 |
| `COLLECTOR_OPCUA_SESSION_TIMEOUT_S` | collector 的 PLC 会话超时 |
| `AUTH_JWT_SECRET` | auth-server 的令牌密钥 |

规则：

- **服务前缀必须有**，且与服务名对应。多个服务跑在同一台机器上时，无前缀的 `DATABASE_URL` 会互相污染。
- **单位进名字**：`_S`（秒）、`_MS`（毫秒）、`_MB`、`_COUNT`。`TIMEOUT=30` 是秒还是毫秒？名字不该留这个问题。
- **布尔用 `ENABLED` / `DISABLED` 后缀**，取值 `true`/`false`，不用 `1`/`0`/`yes`。
- 全大写下划线，不用点号或连字符。

---

## 3. 启动即校验，缺失即拒绝

配置在启动时**全量校验**（Pydantic Settings），任何一项不合法就**打印清晰错误并退出非零**。

绝不允许的三种做法：

| ❌ | 后果 |
|---|---|
| 缺失时用空字符串继续 | 服务起来了，但连不上/认证永远失败，表现为难以归因的运行时错误 |
| 缺失时打一条 WARN 继续 | 没人看 WARN。它会一直跑到出事 |
| 第一次用到时才发现没配 | 服务已经接了流量，此时失败影响真实用户 |

错误信息要**指出是哪个变量、期望什么、当前是什么**（密钥类只说"未设置"，不回显值）：

```
配置错误: PLATFORM_POSTGRES_HOST 未设置
         期望: 数据库主机名或 IP
```

### 3.1 启动自检

除了配置格式，启动时还要做一次**连通性自检**并把结果写进日志：数据库可连、Redis 可连、（collector）工控网段可达。

⚠ collector 的网段可达性自检是硬要求：**连不通就响亮失败**，不要静默退化成一个连不上 PLC 的采集器——那个状态下它看起来是健康的，但一个点位都采不到。

## 4. 默认值策略

这是配置规范里最容易出事的一条。

| 可以有默认值 | 绝不能有默认值 |
|---|---|
| 端口、超时、批大小、重试次数 | **任何密钥、令牌、密码** |
| 日志级别、队列名前缀 | 数据库/Redis 的连接地址与凭据 |
| 分页上限、保留天数 | 允许的跨域来源 |
| 功能开关（默认关） | 对外可访问的地址 |

### 4.1 ⚠ 弱默认的密钥等于没有密钥

给服务级密钥一个"开发用默认值"，等于把这个默认值发布给了全世界——它在代码里、在镜像里、在文档里。凡是拿到镜像的人都能用它调你的内部推送接口。

**密钥类配置的正确形态是：未设置 → fail-closed 拒绝启动或拒绝服务**，而不是回退到某个值。这与 [`runtime-resilience.md`](runtime-resilience.md) §9 的降级方向一致。

### 4.2 ⚠ 危险的默认值是"看起来最方便"的那个

`CORS_ORIGINS=*`、`DEBUG=true`、`AUTO_CREATE_TABLES=true`、`TLS_VERIFY=false`——这些在本地开发时最省事，因此最容易被写成默认值，然后跟着镜像上生产。

**判据：如果一个默认值让本地开发变轻松的方式是"少了一道安全检查"，它就不该是默认值。** 让本地开发轻松的正确位置是 `.env.example`，不是代码里的 `default=`。

### 4.3 跨服务共享值的回退链

多个服务共享同一个值（服务级推送密钥、JWT 密钥）时，编排文件里常写成 `A_KEY: ${A_KEY:-${SHARED_KEY}}` 这类回退。

⚠ **回退链必须每个服务都写全**。少写一处的后果是非对称失效：发送端拿到了值、接收端没有，于是所有调用 403；或者三个服务起得来、第四个起不来。这类故障的现象与原因隔得很远，极难归因。

规则：**共享值要么全部服务都从同一个变量读，要么全部都写同样的回退链。** 不允许"大部分服务写了"。

## 5. 密钥

| 规则 | 说明 |
|---|---|
| **不进版本库** | `.env` 进 `.gitignore`；CI 跑 `gitleaks` 类扫描，命中即失败 |
| **不进镜像** | 镜像层不可删除——某层 `COPY` 进来、后层 `rm` 掉，文件仍在历史层里可被提取（见 [`docker-build.md`](docker-build.md) §6） |
| **不进日志** | 见 [`observability.md`](observability.md) §2.4，只记指纹 |
| **不进错误响应** | 见 [`api-contract.md`](api-contract.md) §4.2 |
| **不进 URL** | query 参数会进访问日志、Referer 头、浏览器历史 |
| 注入方式 | 环境变量或挂载文件。挂载文件更好（不出现在 `/proc/<pid>/environ`，也不被子进程继承） |

### 5.1 轮换

每类密钥都要能在**不停机**的情况下轮换，这要求验证侧**同时接受新旧两个值**：

```
1. 验证侧加入新密钥（新旧都接受）
2. 签发侧/调用侧切到新密钥
3. 观察旧密钥的使用量归零
4. 验证侧移除旧密钥
```

⚠ 设计时就要留出"同时接受两个值"的位置。如果配置项是单值 `SECRET`，轮换就必然要停机——而需要轮换的时刻，往往正是泄漏之后最不能停机的时刻。

### 5.2 JWT 密钥的特殊性

换 JWT 签名密钥会让**所有已签发的令牌立刻失效**（全体用户被登出）。因此它必须支持"主密钥签发 + 密钥集校验"，否则一次轮换就是一次全站强制重新登录。

## 6. 环境差异

**不同环境的差别只能是取值，不能是行为。**

```python
# ❌ 环境分支：dev 跑的根本不是生产的那条路径
if settings.ENV == "prod":
    use_real_storage()
else:
    use_local_dir()

# ✅ 同一条路径，不同取值
storage = ObjectStore(endpoint=settings.OSS_ENDPOINT, bucket=settings.OSS_BUCKET)
```

理由：一旦有 `if env == "prod"`，生产上跑的那条分支**从未在任何地方被测试过**——测试环境永远跑的是另一条。这类缺陷只在生产出现，且无法复现。

功能开关（feature flag）是允许的，但它的判据是**功能是否启用**，不是**当前是什么环境**；且开关的两个取值都要有测试。

## 7. 运行时可变参数

有一类参数需要在**不重启**的情况下调整：采集周期、归档心跳、保留天数、限流阈值。它们走 `lib/runtime/params.py` 的机制，存在数据库里、有 API 可改。

四条约束：

| 约束 | 理由 |
|---|---|
| **有取值边界并强制校验** | 一个手滑把采集周期改成 0 会打垮 PLC |
| **变更进审计日志** | 它是能改变系统行为的操作，见 [`observability.md`](observability.md) §7 |
| **生效方式明确**（下一周期生效 / 立即生效） | 调的人要知道什么时候会看到效果 |
| **参数定义留在服务，机制在 `lib`** | `lib` 零项目名词 |

### 7.1 ⚠ 环境变量是永久默认值，不是一次性播种

一个参数同时有环境变量和数据库值时，语义必须明确：

- **环境变量 = 该参数的默认值**，数据库里没有显式设置时用它，**且改环境变量重启后会生效**；
- 不是"首次启动时把环境变量写进数据库，之后环境变量再也不起作用"。

后者的问题是：运维改了环境变量、重启了服务、行为没有任何变化，而且**没有任何地方告诉他为什么**。他会认为配置系统坏了——某种意义上确实坏了。

## 8. 配置文件与模板

- 仓库里维护 `.env.example`（或 `.env.template`），**列出全部变量**，密钥类留空并注明"必填"。
- 模板里的注释要写清**哪些是必须改的**、哪些可以不动。
- 新增一个必填配置项时，**同一个提交里**要改模板——否则下一个部署的人会撞上一个没有文档的启动失败。
- 配置项的增删是**破坏性变更**，要在发布说明里写明。

---

## 9. 反模式

- **弱默认的密钥**：等于把密钥发布给所有人。
- **`CORS_ORIGINS=*` / `DEBUG=true` 作为默认值**：跟着镜像上生产。
- **回退链只写了一部分服务**：非对称失效，极难归因。
- **`if env == "prod"`**：生产跑的分支从未被测试。
- **运行中重读环境变量**：同一进程不同代码路径看到不同配置。
- **密钥写进 URL query**：进访问日志与浏览器历史。
- **配置校验推迟到第一次使用**：故障暴露在已经接流量之后。
- **环境变量只在首次启动播种**：改了配置重启却没有任何变化，也没有任何提示。
