# 工程协作规范

分支、提交、评审、依赖、发布。议题流程见 [`issue-tracker.md`](issue-tracker.md)，分诊标签见 [`triage-labels.md`](triage-labels.md)。

---

## 1. 分支

**主干开发**：`main` 永远可发布，功能分支短生命周期（**目标 ≤ 2 天**，超过 5 天视为拆分不足）。

| 分支 | 命名 | 说明 |
|---|---|---|
| 主干 | `main` | 受保护，禁止直推，全部闸门必须绿 |
| 功能 | `feat/<简述>` | 关联一个 issue |
| 修复 | `fix/<简述>` | |
| 重构 | `refactor/<简述>` | 无行为变更 |
| 文档 | `docs/<简述>` | |

**长期分支是有毒的**：它与主干的差异每天都在扩大，合并冲突的解决本身就是引入缺陷的高发场景。大改造用**功能开关**在主干上分批合入，不用长期分支。

---

## 2. 提交

一个提交 = 一件事，且**提交后的每个状态都应当是可构建、测试全绿的**。

```
<类型>(<范围>): <一句话说清做了什么>

<为什么这么做——只在不显然时写>
```

类型：`feat` / `fix` / `refactor` / `perf` / `test` / `docs` / `build` / `chore`。范围是服务名或模块名（`platform/dataset`、`collector`、`lib/auth`）。

- 标题写**做了什么**，不写"修改了若干问题"。
- 正文写**为什么**，不写做法——做法在 diff 里。
- **不写变更史叙事**（"原先是 X，改成了 Y"），这与 [`comment-style-python.md`](comment-style-python.md) 是同一条原则：git 已经记着了。
- 修复类提交要引用 issue 编号。

## 3. Pull Request

### 3.1 规模上限

| 指标 | 上限 | 超了怎么办 |
|---|---|---|
| 改动行数（不含生成物与锁文件） | **400 行** | 拆成多个 PR |
| 涉及文件 | 20 个 | 同上 |
| 涉及服务 | **1 个** | 跨服务改动拆成"先加新的、后切换、再删旧的"多个 PR |

理由不是洁癖：评审质量随 PR 规模**断崖式下降**。超过几百行之后，评审就从"逐行看"退化为"看起来没问题"，而那正是缺陷溜进去的方式。

例外：机械化的大范围改动（重命名、格式化、自动生成）可以超限，但**必须单独成 PR**，不与逻辑改动混在一起。

### 3.2 PR 必须包含

1. **关联的 issue**。
2. **动机**：解决什么问题，不是"做了什么改动"。
3. **验证方式**：跑了什么、怎么确认它对。
4. **风险与回滚方式**：如果上线后出问题怎么退。
5. 若含迁移：**迁移是否可逆**，不可逆则写明原因。
6. 若改了对外契约：**是否破坏性**，破坏性则写明弃用计划。

### 3.3 评审

- 至少一人批准；作者不能自己批准。
- **以下情形必须由人逐行看，不接受"看起来没问题"**：
  - 数据库迁移
  - 鉴权与权限判定
  - 并发、锁、租约相关
  - 对外契约变更
  - 任何 `# type: ignore` / `# noqa` / `pragma: no cover` 的新增
- 评审意见分两档：**必须改**（阻塞合并）与**建议**（可另开 issue）。不标档次的意见会让作者猜。

### 3.4 合并

**squash merge**，一个 PR 一个提交进主干。主干历史因此是一串可读的、每个都可发布的提交。

禁止 `--force` 推主干；禁止在别人正在评审的分支上 rebase 后强推（评审意见会全部错位）。

## 4. 什么时候必须写 ADR

不是每个决定都值得写。判据是**这个决定是否难以逆转**——满足任意一条就要写：

| 触发条件 | 例 |
|---|---|
| 影响**多个服务**或跨服务边界 | 通信方式、数据归属、共享层的引入 |
| **难以逆转**：改回来的代价远大于当初选它 | 主键类型、时间存储口径、队列语义 |
| **否决了一个明显的替代方案** | 选 A 不选 B，而 B 是大多数人的第一直觉 |
| 引入**新的依赖类别** | 新的中间件、新的存储、新的协议 |
| 有意**违反**本仓某条既有规范 | 必须写明为什么这里是例外 |

ADR 写在 `docs/adr/`（系统级）或 `server/services/<svc>/docs/adr/`（服务内），格式见既有条目。**与既有 ADR 抵触时要明说，不许默默覆盖**（见 [`domain.md`](domain.md)）。

**不需要 ADR 的**：选一个库的具体版本、命名偏好、能在一次 PR 里改回来的任何事。

## 5. 依赖管理

### 5.1 新增依赖的判据

新增一个第三方依赖前，逐条回答：

1. 它解决的问题，自己写要多少行？**少于 200 行且没有隐藏复杂度，就自己写。**
2. 它维护活跃吗？最近一次发布、未解决 issue 数、是否有单一维护者。
3. 它拖进来多少传递依赖？
4. 许可证是否可接受（§5.3）？
5. 它进的是 `lib`/`domain` 还是单个服务？**进共享层的依赖会绑架所有服务**，标准要更高。

⚠ 依赖的真实成本不是"引入时省的时间"，是**它出问题时你要读它的源码**。评估时按后者算。

### 5.2 锁文件纪律

- `uv.lock` 与 `pnpm-lock.yaml` **必须提交**，CI 用 `--frozen` 安装。
- 锁文件的变更**单独成 PR**，不与逻辑改动混合——混在一起时评审者会直接跳过几千行 diff，那正是供应链攻击的藏身处。
- 升级按**季度批量**做一次，安全补丁随时做。
- 升级 PR 必须说明**升了什么、为什么、破坏性变更有哪些**。

### 5.3 许可证

允许：MIT、BSD、Apache-2.0、ISC、PSF。
**禁止**：GPL / AGPL 系（本项目会私有部署交付，传染性许可证不可接受）。
其它（MPL、LGPL 等）逐个评估并记录结论。

CI 中跑许可证扫描，命中禁止项即失败。

### 5.4 供应链

- CI 跑漏洞扫描（`pip-audit` / `pnpm audit` 或等价物），**高危即阻断**。
- 不使用来源不明或近期新建的低星包（typosquatting 的主要形态）。
- 第三方 GitHub Action **按 commit SHA 固定**，不按 tag——tag 可以被重新指向。

## 6. 发布与回滚

### 6.1 版本

语义化版本 `MAJOR.MINOR.PATCH`，全后端服务**同步版本号**（它们一起发布、一起测试）。镜像 tag 用版本号 + commit SHA，**不用 `latest`**——`latest` 让"线上跑的到底是哪个版本"变成不可回答的问题。

### 6.2 ⚠ 发布顺序：迁移先行，且只做扩展

```
1. 跑迁移（只含扩展步：加列/加表/加索引）
2. 滚动发布新版代码（新旧副本并存）
3. 观察
4. 下一个发布周期跑收缩步（删旧列/旧表）
```

这个顺序是 [`database-standard.md`](database-standard.md) §5.1 扩展—收缩模式的执行面。它成立的前提是**迁移向前兼容**：跑完迁移后，**旧版代码仍然能正常工作**。

⚠ **代码可以回滚，数据库不回滚。** 这是发布设计的基本事实：出问题时回滚的是镜像 tag，而数据库仍停在新结构上。因此每一次迁移都必须让"新结构 + 旧代码"这个组合是可用的——否则回滚这条退路就不存在了。

### 6.3 发布检查单

- [ ] 全部 CI 闸门绿，且**未使用重试**
- [ ] 迁移在预生产跑过，且 `upgrade → downgrade → upgrade` 通过
- [ ] 迁移是纯扩展步，"新结构 + 旧代码"可用
- [ ] 新增/变更的配置项已进 `.env.example`，部署环境已配
- [ ] 破坏性契约变更已按 [`api-contract.md`](api-contract.md) §2.2 走弃用流程
- [ ] `openapi.json` 已同步提交
- [ ] 回滚方式已写明（回滚到哪个 tag，有无数据副作用）

### 6.4 回滚

- **代码回滚**：切回上一个镜像 tag，应当在几分钟内完成，不需要讨论。
- **数据回滚**：默认**不做**。真需要时走独立的数据修复流程，有人工确认。
- 回滚之后必须补一条 issue 记录根因，不允许"回滚了就算了"。

### 6.5 变更分级

| 级别 | 例 | 要求 |
|---|---|---|
| 低 | 文案、样式、日志 | 常规评审 |
| 中 | 新功能、非破坏性接口变更 | 常规评审 + 发布检查单 |
| **高** | 迁移、鉴权、并发/锁、跨服务契约、依赖批量升级 | 逐行评审 + 预生产验证 + 明确的回滚方案 + **避开业务高峰发布** |

## 7. 反模式

- **长期功能分支**：合并冲突的解决过程本身就是缺陷来源。
- **千行 PR**：评审退化成走过场。
- **锁文件与逻辑改动混在一个 PR**：几千行 diff 没人看。
- **迁移与代码同批发布且迁移不向前兼容**：回滚这条路直接消失。
- **`latest` 标签**：线上版本不可知，回滚不可能。
- **Action 按 tag 固定**：tag 可被重新指向，等于任意代码执行。
- **"先合了再说，后面再补测试"**：后面不会有。
- **回滚后不查根因**：同一个问题会在下个发布周期原样再来一次。
