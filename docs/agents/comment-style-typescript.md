# 注释规范：TypeScript / Vue

适用于本仓所有 TypeScript、JavaScript 与 Vue SFC 代码。Python 见 [`comment-style-python.md`](comment-style-python.md)，两份文档的原则一致，只是落到各自语言的写法。

## 这份文档要解决的问题

注释有两种坏法，方向相反：

- **臃肿**：注释在源文件里堆成小作文——架构理由、迁移记录、"改造前 / 改造后"的叙事——读代码得先分辨哪几段说的是现状。
- **过简**：只剩一行 `// 处理数据`，等于没写；真正会绊倒人的隐式契约反倒没人记。

修法不是删掉知识，而是**把每一条知识放到它唯一该在的地方**，代码里只留一个指针。下面的规则都服务于这一条。

## 唯一的判定规则：注释只做四件事

要写的注释若不属于以下四类，就别写——那说明代码本身该讲清楚。

| # | 类别 | 篇幅上限 |
|---|---|---|
| 1 | 文件头 `@fileoverview`——这个文件是什么 | 1–3 行 |
| 2 | 函数/方法 JSDoc——一句话 + `@param` | 一句话 |
| 3 | 常量与行内——一个名字，不是一句解释 | 半行 |
| 4 | 反直觉的坑——用到的那一行上方 | 1 行 |

超过上限的内容，一律进 `docs/*.md` / `<service>/docs/adr/` / `CONTEXT.md`，代码里留一行指针。

## 怎么算"适量"

不要背比例，用信号判断。

**注释不足的信号**（该写而没写）：

- 要跳到别的文件才知道某个参数装的是什么
- 出现了没有名字的魔数
- 存在隐式契约（调用必须有先后、必须由某个特定调用方失效缓存、prop 名写错会静默不渲染），漏掉会**静默失效**而不是报错
- 写法反直觉：看着该用 A 却用了 B，且理由不在函数体里

**注释过量的信号**（该删）：

- 注释与紧邻的下一行同义
- 某个函数头上的注释比函数体还长
- 连续三行以上的散文段落
- 同一件事在设计文档和代码里各写了一遍
- 类型已经说清楚的，又用文字复述一遍

**量化参考**（只作嗅探，不是指标）：单文件注释行占比通常落在 5%–15%。逼近 0 一般是缺了文件头和坑位注释；超过 25% 一般是把设计文档抄进了代码。

## 1. 文件头

用 `@fileoverview`（Google JS style）说清这个文件做什么。真正的设计理由不要内联，指向已有或应有的文档。

```ts
/**
 * @fileoverview 3D 孪生渲染层的主题取色单一真源，所有 WebGL 子系统统一从这里读色。
 * 约束见 docs/THEME_SYSTEM_CONTRACT.md §5.1。
 */
```

**Vue SFC** 用同样的块，放在 `<script setup>` 内的第一行：

```vue
<script setup lang="ts">
/**
 * @fileoverview 点位选择面板：把绑定草稿写回上层弹窗，自身不落库。
 */
</script>
```

手工维护的 `@author` / `@date` / 最后更新时间一律不写——`git log` 与 `git blame` 已经准确回答了，而且不会过期。

## 2. 函数与方法

一句话说清做什么，再用 `@param` 按名字列出参数。只有当名字本身讲不清它装了什么时，才在名字后面补一个短句。

不要写 `@returns`（返回类型已在签名里），不要写用法示例，不要写成段落。

```ts
/**
 * 把任意 CSS 颜色表达式规范化为 THREE.Color；解析失败返回 null。
 * @param host 读 CSS 变量级联的宿主元素
 * @param cssColorExpr 待解析的原始 CSS 颜色表达式
 */
function probeColor(host: HTMLElement | null, cssColorExpr: string): THREE.Color | null
```

**类型已经说过的，不要再用文字说一遍**。这是 TS 侧最常见的臃肿来源，尤其是从 JSDoc 时代带过来的习惯：

```ts
// ❌ 类型全都写在签名里了，这段 JSDoc 一个新信息都没有
/**
 * 加载配置。
 * @param {string} path - 配置文件路径，字符串类型
 * @returns {Config} 返回一个 Config 对象
 */
function load(path: string): Config
```

TS 项目里**不要写 JSDoc 类型标注**（`@param {string}`、`@returns {Config}`）——类型的唯一真源是签名，写两份必然漂移。

**平凡函数不需要注释**：无参数、或只有一个自明参数且函数体只有一行的，直接不写。`isOpen()` 上面不需要挂 `/** 返回是否打开 */`。

**Vue 组件的 props**：类型与默认值由 `defineProps` 的类型和 `withDefaults` 表达，不要逐个 prop 写 JSDoc 复述。只有语义不自明的那一个才标：

```ts
const props = withDefaults(defineProps<{
  modelValue: string
  span: AggregateSpan
  strict?: boolean  // 缺样时抛错而非补零
}>(), { strict: false })
```

**composable** 与普通函数同规格，一句话说清它管什么状态、什么时候释放。

## 3. 常量与行内

需要标注时给一个短名字，不是一句解释。

```ts
const DEBOUNCE_MS = 150      // 输入防抖间隔
const WS_RETRY_MAX = 5       // 重连上限
```

行内表达式同理，只在不自明时标：

```ts
const cutoff = now - retentionDays * 86_400_000  // 保留期左边界
```

## 4. 反直觉的坑

能阻止一个具体且不显然的错误的警告，值得在**用到的那一行上方**占一行，沿用 `⚠` 前缀。完整解释若超过约两行，解释进文档、代码留指针。

```ts
// ⚠ 导航键必须阻止冒泡：外层在 window 上挂了方向键快捷键，上抛会让画布被同步 nudge
event.stopPropagation()
```

```ts
// ⚠ 不能用半透明白：浅色主题下白压白，hover 反馈会消失
background: var(--dt-hover-bg);
```

要写的是**当前约束及其后果**，不是它的来历。跨文件、跨包的隐式契约属于这一类，必须写清楚漏掉会怎样——这类是功能注释，不是过程注释。TS 里尤其值得标的一类：**类型检查和 lint 都拦不住的契约**，比如组件 prop 名、插槽名、图标注册名写错时不会报错，只会静默不渲染。

## 直接删掉，不要搬家

- 复述下一行的注释（`// 计数器加一` 配 `count++`）
- 注释掉的死代码
- **变更史叙事**——"改造前是 X，现在是 Y""原先 / 曾经 / 本轮新增 / 旧实现"。git 已经记着了，而且下一次提交落地时这句话就是错的。
  - ✅ `// 初值也走 WS：运行态零 HTTP，见 docs/adr/xxxx`
  - ❌ `// 之前初值是 HTTP 拉的，三期改造后改走 WS 了`
- 设计文档已经写过的内容，只要 §1/§4 的指针在位就删
- 分隔用的 ASCII 大横幅（`// ======== 工具函数 ========`）——文件长到需要分区，就该拆文件

**测试名同理**：写这条用例断言的是什么契约，不写"回归自某次修复"。

```ts
// ✅
it('缺少 node_id 时按 trackKey 回退匹配', ...)
// ❌
it('修复 #42 的回归用例', ...)
```

## 绝对不动——这些不是散文，是给工具的指令

- 静态检查指令：`// eslint-disable*`、`// @ts-ignore`、`// @ts-expect-error`、`/* istanbul ignore */`、`// prettier-ignore`
- `/// <reference types="..." />` 三斜线指令
- 许可证/版权头
- `TODO` / `FIXME`——它们跟踪的是待办，不是叙事，保留（最好带上 issue 编号）
- `// @vitest-environment happy-dom` 这类框架指令注释

`@ts-expect-error` 后面应当跟一句**为什么这里预期报错**——那是 4 类注释，不是可选的：

```ts
// @ts-expect-error 上游 d.ts 漏标了这个可选字段，见 <issue>
```

## 落笔前的自检

1. 这句话属于四类里的哪一类？都不属于就别写。
2. 它是不是在复述代码或类型签名已经说过的事？
3. 它讲的是**现状**还是**来历**？来历删掉。
4. 它超过篇幅上限了吗？超了就挪进文档、留一行指针。
