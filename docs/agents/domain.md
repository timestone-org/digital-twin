# 领域文档

engineering skills 在探查代码库时，应当如何消费本仓的领域文档。

本仓是**多上下文**仓库：每个顶层服务目录是一个独立上下文，各有各的通用语言。

## 动手探查之前，先读这些

- **根目录 `CONTEXT-MAP.md`**——它指向每个上下文自己的 `CONTEXT.md`。与当前话题相关的都读一遍。
- **`docs/adr/`**——系统级架构决策。读与你即将动手的区域相关的那几条。
- **`<context>/docs/adr/`**——上下文内部的决策，某个上下文自己留了 adr 目录时才有。

如果这些文件不存在，**静默继续**。不要提示它们缺失，也不要建议先把它们建起来。词表和 ADR 由 `/domain-modeling` 惰性创建（经由 `/grill-with-docs` 和 `/improve-codebase-architecture` 触达）——某个术语第一次被真正定案时，它所属的上下文才配得上一份 `CONTEXT.md`，不预先建空壳。

## 文件结构

```
/
├── CONTEXT-MAP.md                     ← 上下文索引
├── docs/adr/                          ← 系统级决策
│   ├── 0001-....md
│   └── 0002-....md
├── server/
│   ├── lib/                           ← 通用基础设施，不是上下文
│   └── services/
│       ├── <service-a>/
│       │   ├── CONTEXT.md
│       │   └── docs/adr/              ← 该上下文内部的决策
│       └── <service-b>/
│           ├── CONTEXT.md
│           └── docs/adr/
└── web/
    ├── CONTEXT.md                     ← 前端整体算一个上下文
    └── docs/adr/
```

上下文是 `server/services/` 下的各个服务目录，加上 `web/` 整体。**上下文按代码单元划，不按部署单元划**——一个服务可以按运行角色跑出多个进程，它们共享同一套通用语言，是同一个上下文。`server/` 本身不是上下文，它只是后端这一侧的容器。

**`lib/` 不是上下文**——它是纯技术基础设施（数据库会话、令牌签发、中间件），按设计**不含任何本项目的领域词汇**，因此不需要 `CONTEXT.md`。恰恰相反：`lib` 里出现领域名词即为设计错误，见 [`project-structure-python.md`](project-structure-python.md) §3。

**`domain/` 也不是上下文**——它虽然带领域名词，但那些概念的通用语言归属于消费它的那个上下文（例如公式求值的术语属于 `platform-server` 的词表）。共享包不自立词表，否则同一个词会有两处定义。

`CONTEXT-MAP.md` 列出全部上下文并链到各自的 `CONTEXT.md`，尚未建词表的标注为"待建"。长篇设计文档放在 `docs/` 下——那是设计记录，不是词表；可以当背景读，但领域模型以上面这些文件为准。

## 用词表里的词

当你的产出里出现某个领域概念（issue 标题、重构提案、假设、测试名），就用对应上下文 `CONTEXT.md` 里定下的那个词。不要漂移到词表明确避开的同义词上。

如果你需要的概念还不在词表里，这本身是个信号——要么你在生造项目并不使用的说法（该重新考虑），要么这里确实有个缺口（记下来交给 `/domain-modeling`）。

术语的作用域限于其所属上下文。同一个词在两个上下文里可能指不同的东西；遇到这种情况，明说你指的是哪个上下文，而不是把它们合并成一个。

## 与 ADR 冲突要挑明

如果你的产出与既有 ADR 相抵触，明确指出来，不要默默覆盖：

> _与 ADR-0007（事件溯源的订单）相抵触——但值得重新讨论，因为……_
