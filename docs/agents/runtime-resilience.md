# 运行时韧性规范

适用于全部服务。服务与通信形态见 [`../ARCHITECTURE_MICROSERVICES.md`](../ARCHITECTURE_MICROSERVICES.md)，对外错误形状见 [`api-contract.md`](api-contract.md) §4。

分布式系统里，**故障不是例外，是常态**：网络会抖、下游会慢、进程会被杀、消息会重复投递。这份规范定义系统在这些事情发生时应当如何表现——**它们必须是设计出来的行为，不是碰运气的结果**。

---

## 1. 异常分层

三层，职责不重叠：

| 层 | 是什么 | 例 | 谁抛 |
|---|---|---|---|
| **领域异常** | 业务规则不允许 | 公式语法错误、点位已被大屏引用不能删、报告期未结束 | `services/` |
| **应用异常** | 请求本身有问题 | 参数校验失败、资源不存在、无权限、版本冲突 | `api/` 与 `services/` |
| **基础设施异常** | 外部依赖出了问题 | 数据库连接失败、Redis 超时、PLC 不可达、对象存储 5xx | 适配层 |

三条规则：

1. **业务代码不构造 HTTP 响应**。`services/` 抛领域异常，由统一的异常处理器（`lib/errors` 注册到 FastAPI）翻译成 §4 的错误码与状态码。业务层里出现 `HTTPException` 即为分层错误。
2. **每个异常类自带错误码**，不在处理器里用 `if isinstance` 长链条分派——那个链条一定会漏掉新加的异常，漏掉的结果是 500。
3. **基础设施异常不许裸露给上层**。适配层要把 `asyncpg.PostgresError`、`redis.RedisError`、`httpx.HTTPError` 包成本项目的基础设施异常，否则业务层就得认识每一个第三方库的异常类型。

### 1.1 兜底处理器

未被识别的异常一律 500 + `code=50000` + 通用 message，**完整堆栈只进日志**（带同一个 `trace_id`）。

⚠ 兜底处理器本身**绝不能抛异常**。它里面的任何格式化、序列化、日志调用都要防御性写，否则一次异常会变成"处理异常时又异常"，客户端收到的是空响应或连接重置，日志里什么都没有。

## 2. 可重试性必须显式标注

每个异常都要能回答"重试有没有意义"，这个信息**由异常自己携带**，不由调用方猜：

| 类别 | 可重试 | 例 |
|---|---|---|
| 瞬时故障 | ✅ | 连接超时、连接被重置、503、Redis 短暂不可达、死锁回滚 |
| 永久故障 | ❌ | 参数错误、权限不足、资源不存在、唯一键冲突、公式语法错误 |
| 不确定 | ❌ **按不可重试处理** | 写操作超时——请求可能已经生效了 |

⚠ 第三类是最危险的：**写操作超时不代表没写成功**。盲目重试一次"向 PLC 写值"或"创建订单"，可能造成两次生效。这类操作要么有幂等键（§5），要么就不重试、交给人处理。

## 3. 超时预算

**每一个跨进程调用都必须有显式超时。** 没有超时的调用会在下游卡住时把本服务的连接池、线程、事件循环一起耗光——一个慢下游拖垮整条链路，是分布式系统最常见的级联故障。

### 3.1 预算表

| 调用 | 超时 | 说明 |
|---|---|---|
| 客户端 → edge-gateway | 30s | 上传/下载/导出另算 |
| edge → `/verify`（鉴权子请求） | **500ms** | 全站前置，每个受保护请求过一次，必须快；超时按拒绝处理 |
| edge → 业务服务 | 25s | 严格小于客户端超时 |
| 服务 → 数据库（热路径） | 2s | `statement_timeout` |
| 服务 → 数据库（报表/聚合） | 30s | 单独的连接配置，不与热路径共用 |
| 服务 → Redis | 1s | 快照与缓存读，慢于此还不如不读 |
| 服务 → 内部 HTTP（如 platform → collector 计划下发） | 5s | |
| platform → collector 浏览 RPC | 10s | 走命令总线，含 PLC 往返 |
| collector → PLC 连接 | 5s | |
| collector → PLC 读/写 | 3s | 工控网内，慢于此说明链路有问题 |
| worker 任务（渲染） | 5min | |
| worker 任务（训练） | 30min | |

### 3.2 ⚠ 下游超时之和必须小于上游

如果 edge 给业务服务 25s，而业务服务里串行调了三个各 10s 超时的下游，那么 edge 会在下游还没跑完时就断开——客户端看到超时，服务端却还在继续跑，产生"用户以为失败了、系统其实做了"的最坏结果。

**每写一个新的下游调用，都要回头检查它所在链路的预算是否还成立。**

### 3.3 超时不等于取消

超时之后**必须真正取消下游操作**（`asyncio` 的任务取消、数据库的 `statement_timeout`），而不是只是不再等待结果。只不等待的话，下游仍在消耗连接与 CPU，压力不降反升。

## 4. 重试

### 4.1 规则

- **只重试标记为可重试的异常**（§2）。
- **指数退避 + 抖动**：`base * 2^n ± random`。没有抖动的退避会让所有失败的客户端在同一时刻一起重试，把刚恢复的下游再打死一次。
- **次数有上限**（默认 3 次），且总耗时不得突破本层的超时预算。
- 重试**要记日志**（WARN 级 + 尝试次数），否则"偶尔慢"的原因永远查不到。

### 4.2 ⚠ 不要在每一层都重试

重试次数是**逐层相乘**的：边缘 3 次 × 服务 3 次 × 数据库客户端 3 次 = 一次用户点击变成 27 次下游请求。这是把小故障放大成雪崩的标准做法。

**规则：一条链路上只有一层负责重试。** 本项目里这一层是**发起方最靠近下游的那个适配器**，其余各层只透传失败。

### 4.3 断路

对下游连续失败达到阈值时**短路直接失败**（不再发请求），一段时间后放少量探测请求试探恢复。

必须有断路器的下游：`auth-server /verify`（全站前置）、对象存储、AI 模型的外部 API。

⚠ 断路器的"打开"状态必须**明确暴露**（日志 + 指标），否则表现为"下游明明好了但我这边还在报错"，而没人知道是断路器还没合上。

## 5. 幂等

### 5.1 哪些必须幂等

| 场景 | 为什么 |
|---|---|
| **所有队列任务** | 队列是 at-least-once，重复投递是常态而非异常（§7） |
| **向 PLC 下发写值** | 客户端重试会导致设备被写两次 |
| 创建资源的 POST | 网络抖动下的重复提交 |
| 归档写入 | leader 切换、消费者重启都会造成重复 |
| 定时任务 | 调度器重启可能重复触发同一周期 |

### 5.2 三种实现，按场景选

| 方式 | 做法 | 适用 |
|---|---|---|
| **自然幂等** | 操作本身重复执行结果相同（`SET x = 5`） | 状态同步、配置下发 |
| **唯一约束兜底** | 用业务键做唯一约束，冲突即视为已完成 | 归档写入、按周期生成的报告（`(schedule_id, period)` 唯一） |
| **幂等键** | 缓存 `(操作, 键)` 的首次结果，重复请求直接返回 | 对外 POST、下发写值 |

**内容寻址的 id 用 `uuid5`**：同一份输入算出同一个 id，重复导入天然不产生重复行。

⚠ **"先查再插"不是幂等**。两个并发请求会同时查到"不存在"然后都插入。唯一约束是唯一可靠的手段，应用层检查只是用来给出友好错误。

## 6. 并发与锁

### 6.1 分布式锁的使用规则

| 规则 | 理由 |
|---|---|
| **锁必须有 TTL** | 持有者进程被杀不会释放锁；没有 TTL 就是永久死锁 |
| **续约与释放必须 CAS**（值等于自己才操作） | 否则会续别人的锁、删别人的锁 |
| **锁内禁止长 IO** | 锁内做 HTTP 调用或大批量写，会让 TTL 到期而操作还在跑——此时**两个进程同时认为自己持有锁** |
| **锁不是事务** | 锁保证互斥，不保证原子。跨了锁边界的多步操作仍需事务或补偿 |
| 拿不到锁的行为要明确 | 是等待、跳过，还是报错？必须显式选，不能默认死等 |

### 6.2 租约与 fence

单活角色（collector 的采集、platform 的 publisher）用**租约选主**：

- 抢锁 `SET NX PX`，续约用 Lua CAS，续约失败立刻**停止工作再让位**（renew-or-die），把脑裂窗口压到一个 TTL 内。
- 租约带**单调递增的 fence 令牌**，对外部资源的破坏性写要带上它，让落后的旧主的写被拒绝。
- **Redis 不可达时的降级方向要显式**：宁可不干活，也不要两个主同时干活——多副本角色一律判定"非 leader"。

⚠ 这套语义（`SET NX` / `PX` 自动过期 / CAS 续约与释放）必须有**契约测试**锁住，且测试假件与真实现双跑。假件对这三条的近似若与真实现不一致，后果是**生产双主、测试全绿**——这是所有测试替身里唯一会静默损坏数据的一处。

### 6.3 乐观锁

对可能并发编辑的资源（大屏配置、台账列定义、模板）用**版本号**：读时带 `version`，写时 `WHERE version = :v`，影响行数为 0 即冲突，返回 409 让客户端重取。

不要用"最后写入者获胜"——它会让先提交的人的修改**静默消失**，而两个人都以为自己保存成功了。

## 7. 队列语义

队列用 Redis Stream + consumer group。

| 语义 | 后果 |
|---|---|
| **at-least-once** | 消费者必须幂等（§5） |
| 消息未 ack 会被重新投递 | 处理超时的任务会被另一个消费者接手——**长任务要么定期续期，要么切成小步** |
| 消费者崩溃后 pending 消息滞留 | 需要 `XAUTOCLAIM` 类的认领机制把它们捞回来，否则永久卡住 |

三条要求：

- **消息信封里必须带 `traceparent`**（见 [`observability.md`](observability.md) §4.2）与幂等键。
- **死信**：重试超过 N 次的消息进死信流，**不要无限重试**——一条毒消息能让消费者永远卡在同一处。死信要有告警。
- **积压有指标与告警**（`observability.md` §3.2）。积压持续增长意味着即将丢数据或耗尽内存。

## 8. 优雅关停

收到 `SIGTERM` 后的顺序是固定的，**顺序错了就会丢请求或丢数据**：

```
1. readiness 立即转为未就绪     ← 让编排器先把流量摘掉
2. 停止接受新工作（HTTP 不再接新连接 / 消费者不再取新消息）
3. drain：等待在途工作完成（有上限，默认 20s）
4. 释放角色资源：让出租约、flush 缓冲、关闭 PLC 会话
5. 关闭连接池，退出
```

各角色的差异：

| 角色 | 关停要点 |
|---|---|
| `api` | 在途请求跑完即可 |
| `worker` | **当前任务跑完再退**，或显式放弃并把消息还给队列（不 ack）。绝不能跑到一半就退且已经 ack |
| `publisher` / `collector` | **先让出租约**再退出，让热备立刻接管，而不是等租约自然过期（那要等一个 TTL） |
| `collector` | 归档缓冲必须 **flush 完再退**——它是链路末端，退出时缓冲里的数据没有第二个来源 |

⚠ 停止顺序**不是启动顺序的逆序**。归档器启动早但必须最后停（它要接住其它组件 teardown 时补交的尾批数据）。这类顺序约束要在代码里显式声明并由测试锁死，不能靠 `reversed()` 猜。

⚠ 编排器的 `terminationGracePeriodSeconds` 必须**大于** drain 上限，否则 drain 还没完就被 `SIGKILL`。

## 9. 降级

依赖不可用时的行为必须**显式选择**，并写在代码注释里。判据只有一条：**这次降级会不会造成不可逆的后果或安全缺口**。

| 依赖 | 不可用时 | 方向 |
|---|---|---|
| 鉴权服务 | **拒绝请求** | fail-closed——放行等于全站无认证 |
| 服务级密钥未配置 | **拒绝** | fail-closed——未配置说明通道没接好 |
| 采集计划拿不到 | **空转 + 告警，不用过期缓存猜** | fail-closed——用错的计划采数据会写出看似正常的错误历史 |
| Redis（快照读） | 返回"暂无数据"，大屏显示空态 | fail-open——展示降级好过整页报错 |
| 对象存储 | 素材加载失败但页面可用 | fail-open |
| AI 助手的模型 API | 返回明确的不可用提示 | fail-open |

⚠ **缓存兜底是有毒的降级**：下游挂了就返回旧缓存，看起来很优雅，但用户会拿着几小时前的数据当实时数据看——在工业监控场景里这可能导致误判。**任何降级返回的陈旧数据都必须在响应里标注它是陈旧的**，并让前端明确显示。

## 10. 背压与限流

- 公开面（分享链接、匿名接口）**必须限流**，它是可枚举 token 的爆破面。
- 队列生产速度持续超过消费速度时，要**拒绝新任务**并明确告知，而不是让队列无限增长。
- 批量接口有条数上限，超限直接拒绝（见 [`api-contract.md`](api-contract.md) §5.2）。
- WebSocket 单连接的订阅数与推送速率有上限，避免一个客户端占满扇出能力。

---

## 11. 反模式

- **无超时的调用**：一个慢下游拖垮全链路。
- **每层都重试**：把小故障放大成雪崩。
- **重试不可重试的写操作**：可能造成两次生效。
- **锁内做长 IO**：TTL 过期而操作还在跑，等于没有锁。
- **消费者不幂等**：at-least-once 下必然出错，且是间歇性的。
- **无限重试毒消息**：消费者永久卡死。
- **关停时先关连接再 drain**：在途请求全部失败。
- **静默返回陈旧缓存**：用户拿旧数据当实时数据。
- **拿不到锁就死等**：把互斥变成串行排队，最后全体超时。
