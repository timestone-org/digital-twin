# 可观测性规范

适用于全部服务。服务与部署形态见 [`../ARCHITECTURE_MICROSERVICES.md`](../ARCHITECTURE_MICROSERVICES.md)。

一个请求会经过 `edge-gateway → platform-api → Redis Stream → platform-worker`，或 `collector → Redis → platform-publisher → realtime-hub → 浏览器`。**跨了 4–5 个进程的因果链，靠 grep 是追不回来的。**

可观测性不是"上线后再加的运维工作"，它是**第一行业务代码就要遵守的写法约定**：日志字段、trace 传播、指标埋点，事后补的成本是当初写的十倍，而且补不全——历史日志已经写成那样了。

---

## 1. 三根支柱与本项目的最低要求

| 支柱 | 回答什么问题 | 最低要求 |
|---|---|---|
| **日志** | 具体发生了什么 | 结构化 JSON，字段统一，带 `trace_id` |
| **指标** | 有多严重、是否在恶化 | 每个 HTTP 端点与队列消费者的 RED，加本项目特有的若干项 |
| **追踪** | 因果链在哪一段断的 | `traceparent` 跨服务、**跨队列**传播 |

三者由 `trace_id` 串起来：指标告警 → 找到出错时段 → 按 `trace_id` 拉出完整链路 → 定位到具体日志。**任何一环缺 `trace_id`，这条路径就断了。**

---

## 2. 结构化日志

### 2.1 输出形态

生产环境**一律 JSON 单行**，一条日志一行，不换行、不多行堆栈拼接（堆栈作为字符串字段）。开发环境可以人类可读，但字段集必须相同——两套字段集意味着本地调试的经验在生产上不成立。

### 2.2 必备字段

| 字段 | 说明 |
|---|---|
| `ts` | RFC3339 UTC 毫秒，与 [`api-contract.md`](api-contract.md) §6 同口径 |
| `level` | `DEBUG` / `INFO` / `WARN` / `ERROR` |
| `service` | 服务名 |
| `role` | 运行角色（`api` / `worker` / `publisher` / `leader`），多角色服务必须有 |
| `instance` | 实例标识，用于区分副本 |
| `trace_id` / `span_id` | 见 §4 |
| `event` | **稳定的事件名**，snake_case，如 `dashboard_published`、`plc_session_lost` |
| `msg` | 给人读的一句话 |
| `duration_ms` | 有耗时语义的事件必须带 |
| `error` | 出错时带：`{type, message, stack}` |

⚠ **`event` 必须是稳定字面量，不许拼接变量**。`f"用户 {uid} 登录失败"` 让同一类事件有无数种写法，无法聚合计数、无法建告警。正确写法是 `event="login_failed"` + `user_id` 字段。

### 2.3 级别判据

按**是否需要人介入**分，不按"重要程度"这种主观感受分：

| 级别 | 判据 | 例 |
|---|---|---|
| `ERROR` | **需要人介入**，且不会自愈 | 迁移失败、配置缺失、写库失败、未捕获异常 |
| `WARN` | 降级了但能自愈，或接近阈值 | 重试成功、连接断开后重连、队列积压超过水位 |
| `INFO` | 值得记录的**状态变化** | 服务启动、租约易主、任务完成、大屏发布 |
| `DEBUG` | 排障细节，生产默认关 | 单条消息载荷、中间计算结果 |

两条硬规则：

- **客户端错误（4xx）不是 ERROR**。用户输错参数记 INFO 或 WARN；把它记成 ERROR 会让错误日志被无意义的内容淹没，真正的故障反而看不见。
- **每一条 ERROR 都应当有人看**。如果某条 ERROR 每天出现几百次且没人处理，它要么该降级，要么该修——留着它等于训练所有人忽略 ERROR。

### 2.4 ⚠ 禁止记录的内容

| 禁止 | 替代 |
|---|---|
| 令牌、密码、API 密钥、服务级密钥 | 记录其**指纹**（前 6 位 + 长度）或干脆不记 |
| 完整数据库连接串 | 记 host 与库名，不记密码 |
| 个人身份信息（手机号、邮箱、身份证） | 记内部 id，需要时按 id 反查 |
| 请求体/响应体全文 | 只记必要字段，且有长度上限（如 2KB 截断） |
| 点位实时值的全量流水 | 采样或聚合后记；全量走归档表，不走日志 |

日志会被复制到多处（文件、采集器、检索系统、备份），**写进日志的密钥等于泄漏的密钥**。这条要有自动检查：CI 扫描日志调用点，命中疑似敏感字段名即失败。

## 3. 指标

### 3.1 通用：RED

每个 HTTP 端点、每个队列消费者、每个跨服务调用都要有：

- **Rate**：请求/消息速率
- **Errors**：错误率（按错误类别分标签）
- **Duration**：耗时分布（**直方图，不是平均值**——平均值会把长尾完全掩盖）

标签只用**低基数**维度：服务、角色、路由模板（`/dashboards/{id}` 而不是具体 id）、状态码、错误类别。

⚠ **绝不用高基数值做标签**（用户 id、大屏 id、点位 id、trace_id）。它会让时序库的序列数爆炸，一次事故能把监控系统本身打挂。需要按具体对象排查时用日志和追踪，不用指标。

### 3.2 本项目必须有的指标

| 指标 | 归属 | 为什么必须有 |
|---|---|---|
| PLC 会话数（按服务器） | collector | **叠加重复会话是本系统最危险的故障**，它必须能被直接看见而不是靠推断 |
| 订阅点位数、采样速率 | collector | 配置错误的第一现场 |
| 快照写入延迟 | collector | 大屏"数据不动了"的第一判据 |
| 归档积压（Stream 未消费长度） | collector | 积压持续增长 = 数据即将丢失 |
| 租约持有者与易主次数 | collector / publisher | 频繁易主意味着网络或 Redis 有问题，而症状是"数据偶尔卡顿" |
| 队列深度、任务时长、失败与重试次数 | platform-worker | 扩缩依据 |
| WebSocket 连接数、订阅数、推送速率、丢帧 | realtime-hub | 扩缩依据 + 前端"收不到"的判据 |
| `/verify` 的 QPS 与 P99 | auth-server | 它是全站最热端点，每个受保护请求都要过一次 |
| 数据库连接池使用率 | 全部 | 连接耗尽的表现是"整个服务变慢"，很难从业务指标看出来 |

## 4. 追踪

### 4.1 传播格式

用 **W3C Trace Context**（`traceparent` / `tracestate` 头）。不自造格式——现成的采集与展示工具全都认它。

链路：

```
edge-gateway   生成 traceparent（若客户端未带）
   ↓ HTTP 头
platform-api   继承，创建子 span
   ↓ 队列消息的字段里带 traceparent   ★ 最容易漏的一处
platform-worker 恢复上下文，创建子 span
   ↓ HTTP 头
realtime-hub   继承
   ↓ WS 消息的 trace_id 字段
浏览器          回显在错误提示里
```

### 4.2 ⚠ 跨队列传播必须显式做

HTTP 的传播由中间件自动完成，**队列不会**：消息经 Redis Stream 落地再被另一个进程取出，进程内的上下文早就没了。

因此**队列消息的信封里必须有 `traceparent` 字段**，消费端第一件事就是用它恢复上下文。漏了这一步的表现是：链路在"任务提交"处齐刷刷断掉，而这恰恰是最需要追的异步部分。

同一条规则适用于：Redis 命令总线（platform → collector 的浏览 RPC）、WebSocket 推送、任何延迟执行的回调。

### 4.3 长循环怎么切 span

collector 的采集循环、publisher 的发布循环是**长期运行**的，不能整个循环一个 trace（那会产生一个永不结束、包含百万 span 的怪物）。

规则：**一批一个 trace**。一次采样批次、一次发布 tick、一次归档刷盘各自是一个独立 trace，用属性（服务器 id、批大小）关联，而不是用父子关系。

### 4.4 采样

全量采样在生产上不现实。策略：**默认按比例采样（如 10%），但错误链路 100% 保留**（tail-based，或在出错时强制标记）。

⚠ 出错的那条链路正是要看的那条。按头部固定比例采样会让 90% 的故障现场直接消失。

## 5. 健康探针

两个探针语义完全不同，混用会造成级联故障：

| 探针 | 回答 | **不许**做的事 |
|---|---|---|
| `/health`（liveness） | 进程还活着吗？ | **不许查数据库、不许查 Redis、不许查下游** |
| `/ready`（readiness） | 现在能接流量吗？ | 不许做重量级查询 |

⚠ **liveness 查依赖是一个经典的自毁设计**：数据库抖动 10 秒 → 所有副本的 liveness 同时失败 → 编排器把它们**全部重启** → 重启风暴让数据库彻底起不来。liveness 只回答"进程没死锁、没卡住"。

readiness 可以查关键依赖（能否拿到数据库连接），但要有缓存与超时，不能每次探针都打一次库。

### 5.1 角色相关的语义

- **collector 的 readiness 不取决于它是不是 leader**：热备副本也是就绪的，它随时准备接管。把"非 leader"报成未就绪会让编排器认为它坏了。
- **worker 的 readiness 不取决于队列是否为空**。
- 优雅关停期间（收到 SIGTERM 后），readiness 必须**立刻转为未就绪**，让流量先摘掉，再开始 drain。

## 6. 告警

只对**症状**告警，不对**原因**告警。「错误率 > 1%」是症状，「CPU > 80%」是原因——后者经常无害，前者一定有人受影响。

必须有的告警（按本项目）：

| 告警 | 严重度 |
|---|---|
| 任一服务 5xx 率超阈值 | P1 |
| `/verify` 不可用或 P99 劣化 | P1（全站前置） |
| PLC 会话数 > 配置的服务器数 | **P1——说明出现了重复会话** |
| 归档积压持续增长超过 N 分钟 | P1（即将丢数据） |
| 采集租约在 N 分钟内易主 > K 次 | P2 |
| 队列深度持续超水位 | P2 |
| 数据库连接池使用率 > 80% | P2 |
| 磁盘/超表空间接近上限 | P2 |

**每条告警必须写明"收到之后第一步做什么"**。做不到这一点的告警不该存在——它只会制造疲劳。

## 7. 审计日志

审计与普通日志是**两回事**：普通日志可以采样、可以过期删除；审计记录的是"谁在什么时候改了什么"，它是**合规与追责的凭据**，必须完整、不可篡改、单独保留期。

必须审计的操作：

- 权限变更（授权、撤权、角色变更、管理员提权）
- **向 PLC 下发写值**——工业系统里这是唯一能造成物理后果的操作
- 大屏发布与回滚、模板变更
- 台账数据的人工修正（override）
- 报告的生成与导出
- 采集配置变更（新增/删除点位、改采样参数）

每条审计记录至少包含：操作者、操作时间、操作类型、目标对象、变更前后值、来源 IP、`trace_id`。

⚠ 审计记录**写在业务事务内**（与被审计的变更同一个事务），否则会出现"改了但没审计"或"审计了但没改"。这与 §普通日志的异步写入是相反的取舍，因为审计的完整性比性能重要。

## 8. 排障路径（这套设计要能支撑的场景）

一个具体的场景，用来检验上面每一条是否够用：

> **现象**：用户报"某个大屏的温度值不刷新了"。

1. 用户截图里有 `trace_id`（[`api-contract.md`](api-contract.md) §3.1 要求每个响应都带）→ 拉出该次加载的完整链路，确认大屏配置读取正常。
2. 看 **realtime-hub 的推送速率指标**：该 topic 有没有在推？没推 → 往上游走。
3. 看 **publisher 的租约指标**：有没有 leader？刚刚易主过吗？
4. 看 **collector 的快照写入延迟与订阅点位数**：这个点位在订阅集合里吗？延迟是多少？
5. 看 **PLC 会话数指标**：会话是不是断了？是不是出现了重复会话？
6. 按 `event="plc_session_lost"` 检索日志，拿到断开时刻与原因。

**这条路径上任何一步缺指标或缺字段，排查就退化成猜。** 上面每一条要求都是为了让这六步能走通。
