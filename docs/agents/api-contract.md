# API 契约规范

适用于所有服务的 HTTP 与 WebSocket 对外面。结构见 [`project-structure-python.md`](project-structure-python.md)，服务划分见 [`../ARCHITECTURE_MICROSERVICES.md`](../ARCHITECTURE_MICROSERVICES.md)。

这份规范解决的是**口径分裂**：五个服务各自发明一套 URL 形状、错误体、分页参数与时间格式，前端就要为每个服务写一套适配。这类不一致铺开之后**永远改不回来**——每一个已上线的端点都是一个既成事实。

因此本文的每一条都是**全服务统一**，没有"这个服务特殊"。

---

## 1. URL 形状

```
/api/v1/<service>/<资源复数>/<id>/<子资源复数>/<id>
```

| 规则 | 说明 |
|---|---|
| 服务段 | `auth` / `platform` / `realtime` / `assistant`，与 [ARCHITECTURE](../ARCHITECTURE_MICROSERVICES.md) §2.1 一致 |
| 资源用**复数名词** | `/dashboards`、`/nodes`、`/tables`。不用动词——动作由 HTTP 方法表达 |
| 多词用 **kebab-case** | `/node-types`、`/report-templates`。不用下划线，不用驼峰 |
| 嵌套**不超过两层** | `/projects/{id}/dashboards` 可以；`/projects/{id}/dashboards/{id}/modules/{id}/bindings` 不行——第三层起用顶层资源加过滤：`/bindings?module_id=` |
| 路径参数只放**标识** | 其它一切走 query 或 body |

### 1.1 动作端点

有些操作不是资源的增删改查（重算、发布、触发渲染、下发写值）。它们用**子资源 + POST**，动词放在最后一段并用 `:` 前缀标记：

```
POST /api/v1/platform/tables/{id}:recompute
POST /api/v1/platform/dashboards/{id}:publish
POST /api/v1/platform/nodes/{id}:write        ← 向 PLC 下发写值
```

`:` 前缀让动作端点在路由表、日志和权限码里一眼可辨，也避免与资源名冲突（`/tables/{id}/recompute` 会让人以为存在一个 recompute 子资源）。

**动作端点一律 POST**，即使它不改变状态——GET 带副作用会被各级缓存和预取毁掉。

## 2. 版本与演进

版本在 URL 里（`/api/v1/`），全服务同步升版。

### 2.1 什么是破坏性变更

| 破坏性（必须升版本） | 非破坏性（可直接发） |
|---|---|
| 删除或重命名字段 | **新增可选字段** |
| 改字段类型或语义 | 新增端点 |
| 收紧校验（原来接受的输入现在拒绝） | 放宽校验 |
| 改默认值 | 新增可选 query 参数 |
| 改错误码含义 | 新增错误码 |
| 改分页默认值或上限 | —— |

⚠ **"加字段是非破坏"只在客户端忽略未知字段时成立。** 因此这是一条**双向**约定：后端可以加字段，前端**必须**容忍未知字段——前端的响应模型不许用"多一个字段就报错"的严格模式。这条要有契约测试锁死。

### 2.2 弃用流程

不允许直接删。顺序是：标记弃用（响应头 `Deprecation: true` + `Sunset: <日期>`）→ 观察调用量归零 → 下一个大版本删除。弃用期最短一个发布周期。

## 3. 响应信封

### 3.1 形状

所有响应体是同一个信封：

```jsonc
// 成功
{ "code": 0, "message": "ok", "data": { /* 或 [] 或 null */ }, "trace_id": "0af7651916cd43dd8448eb211c80319c" }

// 失败
{ "code": 40101, "message": "令牌已过期", "data": null, "trace_id": "…", "details": [ /* 见 §4.3，可选 */ ] }
```

`trace_id` **每个响应都必须带**，成功也带——用户报"刚才那个页面出错了"时，它是唯一能把前端截图和后端日志接起来的东西。

### 3.2 ⚠ HTTP 状态码必须真实，不许恒 200

信封里有 `code`，不代表 HTTP 状态码可以永远是 200。**两者都要正确**：

| 场景 | HTTP | 信封 `code` |
|---|---|---|
| 成功 | 200 / 201 / 204 | 0 |
| 参数校验失败 | 400 | 4xxxx |
| 未认证 | 401 | 4xxxx |
| 已认证但无权限 | 403 | 4xxxx |
| 资源不存在 | 404 | 4xxxx |
| 冲突（唯一键、版本冲突） | 409 | 4xxxx |
| 超出限额 | 429 | 4xxxx |
| 服务端错误 | 500 | 5xxxx |
| 下游不可用 | 502 / 503 / 504 | 5xxxx |

理由是硬的：**恒 200 会让整条基础设施链失明**——nginx 的限流与错误页、监控的错误率、客户端的重试策略、浏览器 `fetch` 的 `response.ok`、任何 HTTP 层的告警，全部依赖状态码。把结果只写在 body 里，等于要求每一层都解析 JSON 才知道成没成，而它们都不会这么做。

信封的价值是**统一的错误展示与 trace 回显**，不是取代 HTTP 语义。

### 3.3 状态码的细节约定

- `201 Created` 必须带 `Location` 头指向新资源。
- `204 No Content` 用于删除成功，**不带 body**（此时无信封，这是唯一例外）。
- 长任务的提交返回 `202 Accepted` + 任务 id，客户端轮询任务状态端点。
- **`404` 用于"资源不存在"和"存在但无权看见"两种情况**——不能用 403 告诉攻击者"这个 id 是存在的"。真正的 403 只用于"知道你能看见这类资源，但这次操作你没权限"。

## 4. 错误

### 4.1 错误码分配

五位数字：`<HTTP 首位><服务位><领域两位>` 不够用，改用**分段十进制**：

```
  4 01 01
  │  │  └── 该领域内的序号 01-99
  │  └───── 领域号（见下表）
  └──────── 4=客户端错误 5=服务端错误
```

| 领域号 | 归属 | 例 |
|---|---|---|
| 00 | 通用（校验、限流、格式） | `40001` 参数校验失败 |
| 01 | 认证与授权 | `40101` 令牌过期 / `40301` 权限不足 |
| 10 | 大屏与绑定 | `40410` 大屏不存在 |
| 11 | 点位与采集 | `50011` PLC 不可达 |
| 12 | 台账与公式 | `40012` 公式语法错误 |
| 13 | 报告 | —— |
| 14 | 建模 | —— |
| 15 | 素材 | —— |
| 16 | 空调与空间 | `41601` 车间不存在 / `41606` 空调序号已被占用 |
| 20 | 实时通道 | —— |

**错误码一经发布不许改变含义**，只能新增。它是对外契约的一部分，前端会按它分支。

### 4.2 message 是给人看的，code 是给程序看的

- 前端**不许**按 `message` 内容做逻辑判断——文案会改、会翻译。
- `message` 面向最终用户，**不许包含内部信息**：表名、SQL、堆栈、内网地址、上游服务名、文件路径。
- 内部细节写日志（带同一个 `trace_id`），不写响应。

⚠ 这条最常见的破法是"为了方便排查"把异常原文塞进 `message`。方便排查的正确做法是响应里的 `trace_id` + 日志里的完整上下文。

### 4.3 字段级校验错误

```jsonc
{
  "code": 40001, "message": "参数校验失败", "data": null, "trace_id": "…",
  "details": [
    { "field": "period.start", "code": "invalid_format", "message": "应为 RFC3339 时间" },
    { "field": "columns[2].formula", "code": "too_long", "message": "超过 4096 字符" }
  ]
}
```

`field` 用**点号与方括号**表达嵌套路径，与请求体结构一一对应，前端才能把错误标到具体输入框上。

## 5. 集合：分页、排序、过滤

### 5.1 两种分页，各有适用面

| 方式 | 参数 | 用在哪 |
|---|---|---|
| **页码分页**（默认） | `page`（1 起）、`size` | 有限集合的管理列表：大屏、模板、用户、点位 |
| **游标分页** | `after`（不透明游标）、`limit` | **时序与大集合**：点位历史、台账记录、日志、审计 |

时序数据**禁止**用页码分页：底层数据在持续写入，`page=2` 与 `page=1` 之间新插入的行会导致重复与遗漏，而这种错误是静默的。

### 5.2 集合响应形状

```jsonc
// 页码分页
{ "code": 0, "message": "ok", "trace_id": "…",
  "data": { "items": [...], "page": 1, "size": 20, "total": 137 } }

// 游标分页（不返回 total——算它要全表扫）
{ "code": 0, "message": "ok", "trace_id": "…",
  "data": { "items": [...], "next": "eyJ0cyI6MTcw…", "has_more": true } }
```

- `items` **永远是数组**，空集合返回 `[]`，不是 `null`、不是缺省。
- `size` 有**硬上限**（默认 20，上限 200），超限直接 400，不静默截断——静默截断会让客户端以为拿全了。
- 游标是**不透明字符串**，客户端不许解析或构造。

### 5.3 排序与过滤

```
?sort=-created_at,name          ← 前缀 - 表示降序，逗号分隔多列
?status=active&kind=gauge       ← 精确匹配
?created_at__gte=2026-01-01T00:00:00Z&created_at__lt=…   ← 区间用 __gte/__gt/__lte/__lt
?q=温度                          ← 全文/模糊搜索统一用 q
```

**可排序与可过滤的字段必须是白名单**，不是"把 query 参数拼进 SQL"。白名单之外的字段直接 400——否则它既是注入面，也是让人不小心对无索引列排序而拖垮数据库的入口。

## 6. 序列化口径

这一节是**最容易静默出错**的地方：写错不会报错，只会让数字或时间悄悄偏掉。全服务必须逐条一致。

| 类型 | 口径 | 理由 |
|---|---|---|
| **时间** | RFC3339 / ISO8601，**一律 UTC 带 `Z`**，毫秒精度：`2026-08-10T09:30:00.000Z` | 带偏移量的本地时间会在夏令时与跨时区部署时算错。业务需要的"本地时间"由前端按用户时区渲染，不由后端替它决定 |
| **日期**（无时间） | `2026-08-10`，且必须说明它属于哪个时区口径 | "8 月 10 日的用电量"依赖业务时区，见 §6.1 |
| **时长** | 整数毫秒，字段名带 `_ms` 后缀 | 避免 `1.5` 到底是秒还是分的歧义 |
| **精确小数**（台账值、金额、公式结果） | **JSON string**：`"12.340"` | float64 无法精确表示 0.1，累加会漂移。前端用 decimal 库解析 |
| **测量值**（点位实时值） | JSON number | 传感器精度本身低于 float64，包一层 string 是纯负担 |
| **大整数** | 超过 2^53 一律 **string** | JS 的 `Number` 只有 53 位安全整数，静默丢精度 |
| **UUID** | 小写带连字符：`3fa85f64-5717-4562-b3fc-2c963f66afa6` | —— |
| **枚举** | **字符串字面量**，snake_case：`"pending"` | ⚠ **禁止数字枚举**——改一个枚举名不会动数字，但改顺序会静默改变全部已存数据的含义 |
| **布尔** | 真正的 `true`/`false` | 不用 `0/1`、不用 `"Y"/"N"` |
| **空值** | `null` 表示"有这个字段但没有值"；字段**缺省**表示"本次不涉及"（用于 PATCH） | 两者语义不同，不许混用 |
| **空集合** | `[]` | 不是 `null` |
| **单位** | 值与单位分开两个字段（`value` + `unit`），不拼进字符串 | —— |

### 6.1 业务时区

存储与传输一律 UTC，但**聚合口径**（日报的"一天"、月报的"一个月"）按**业务时区**切分，业务时区是一个显式配置项，不取服务器本地时区。

⚠ 任何按天/月聚合的接口，都必须能说清它用的是哪个时区口径，并在响应里回显。"服务器碰巧在东八区"不是口径。

## 7. 幂等

| 方法 | 幂等要求 |
|---|---|
| GET / HEAD | 天然幂等，**不许有副作用** |
| PUT / DELETE | 必须幂等：重复调用结果一致，删已删的返回 204 而不是 404 |
| PATCH | 应当幂等 |
| POST | 默认不幂等，**但下列必须支持幂等键** |

必须支持 `Idempotency-Key` 请求头的端点：**创建资源**、**触发长任务**（渲染、重算、训练）、**向 PLC 下发写值**。

服务端按 `(端点, 幂等键, 调用者)` 缓存首次结果（TTL ≥ 24h），重复请求直接返回首次结果而不重复执行。

⚠ 下发写值这条是硬要求：网络抖动导致的客户端重试，在没有幂等键时会向物理设备**写两次**。

## 8. 内部 API

服务之间调用的端点与对外面**物理分离**：

```
/internal/v1/<资源>        ← 不经边缘网关暴露，边缘对 /internal/ 一律 deny
```

- 认证用**服务级密钥**（`X-Service-Key`，逐字 `hmac.compare_digest` 比较），不是用户权限码——权限码挂在人身上，而这里要挡的是"任何人"（[ADR-0005](../adr/0005-实时通道与边缘网关的职责分界.md)）。
- **fail-closed**：密钥未配置时一律拒绝，不是放行。
- 内部 API 同样遵守本文的信封、错误码与序列化口径，只是不对外承诺稳定性——它可以随双方同步发布而变。
- 调用方必须透传 `traceparent` 与调用者身份头。

## 9. OpenAPI 与前端类型

后端的 FastAPI 自动产出 `openapi.json`，它是**前后端之间唯一的类型真源**：

1. 每个服务在 CI 中导出 `openapi.json` 并**提交进仓**（`server/services/<svc>/openapi.json`）。
2. 前端由它生成 TS 类型到 `@dt/contracts`，**不手写**后端返回的类型。
3. CI 校验：重新生成后与仓库中的文件**逐字节一致**，不一致即失败——这让"改了接口忘了同步"变成红灯而不是运行时惊喜。
4. 破坏性变更由 diff 检查拦截（删字段、改类型、改必填性），命中则要求走 §2.2 的弃用流程。

⚠ 生成的类型只保证**形状**一致，不保证**语义**一致。语义（这个字段什么时候为 null、这两个字段的互斥关系）仍然要靠契约测试锁定，见 [`testing-standard-python.md`](testing-standard-python.md) §1 L3。

## 10. WebSocket 消息契约

WebSocket 走 `realtime-hub`，消息也是统一信封：

```jsonc
// 服务端 → 客户端
{ "type": "data", "topic": "dashboard:3fa85f64-…", "ts": "2026-08-10T09:30:00.000Z",
  "seq": 128, "payload": { … }, "trace_id": "…" }

// 客户端 → 服务端
{ "action": "subscribe", "topic": "dashboard:3fa85f64-…", "req_id": "c1" }
```

| 规则 | 说明 |
|---|---|
| `topic` 形状 | `<域>:<标识>`，冒号分隔，域名与 REST 资源名一致 |
| `seq` | 每个 topic 单调递增，**客户端据此发现丢帧**；重连后由服务端告知当前 seq |
| `type` | `data` / `event` / `error` / `ack` / `system`，字符串枚举 |
| 载荷序列化 | 与 §6 完全相同的口径，不另起一套 |
| 错误 | `type: "error"` + §4 的 `code`/`message` |

⚠ **WebSocket 的鉴权路径与 HTTP 不同**：token 在子协议里传递，HTTP 头上的鉴权中间件对它不生效。它必须单独实现、单独测试（见 [`testing-standard-python.md`](testing-standard-python.md) §7.1）。

## 11. 反模式

- **恒 200 + 只看 body 里的 code**：见 §3.2，会让整条基础设施链失明。
- **在 `message` 里塞异常原文**：泄漏内部结构，且前端会开始按文案做判断。
- **用 GET 触发动作**：会被浏览器预取、被 CDN 缓存、被爬虫触发。
- **分页无上限**：一个 `size=1000000` 就是一次 OOM。
- **把 query 参数直接拼进 ORDER BY**：注入面 + 无索引列排序拖垮数据库。
- **数字枚举**：改顺序会静默改变全部历史数据的含义。
- **时间不带时区**：naive datetime 一旦落库，就再也说不清它是哪个时区的了。
- **为单个前端页面定制端点**（`/dashboard-page-data`）：它会随页面改版而腐烂，且无法复用。要聚合，用明确的资源加参数。
- **服务各自定义错误体**：前端就要写 N 套错误处理。
