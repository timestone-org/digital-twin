# 空调开机数据与建模设计

从时序数据里抽出「每一次开机」，生成开机预测的训练数据，并处理同一房间多台
空调的开机组合。原始数据面的口径见 [`AC_DATA_DESIGN.md`](AC_DATA_DESIGN.md)。

本期（第一阶段）只做**抽取与管理页**，不做训练。理由见 §9。

---

## 1. 通用语言

| 词 | 指什么 | 不叫什么 |
|---|---|---|
| **开机事件** `startup episode` | 一个房间从全停到达标的一次完整过程 | 不叫开机记录 / 启动 |
| **运行组合** `running set` | 这次开机里同时运行的那几台空调 | 不叫机组 / 分组 |
| **达标时长** `time to compliance` | 从起始时刻到房间达标的分钟数 | 不叫开机时长 |
| **抽取批次** `extraction batch` | 一次抽取跑出来的一整份事件数据 | 不叫任务 / 版本 |
| **人工排除** `manual exclusion` | 人工把某次开机标记为不可用于训练 | 不叫删除 |

⚠ **开机事件是房间级的，不是空调级的。** 房间的温湿度是一个共享状态，把它记在
某一台空调名下，等于把整个房间的响应算作那一台的功劳——这正是参考实现
（`../Baoding/api/apps/kt_predict`）的缺陷，也是本期要修的东西。

## 2. 外部数据的既成事实（实测）

除 [`AC_DATA_DESIGN.md`](AC_DATA_DESIGN.md) §2 已记的之外，本期实测新增：

- **卷包生产线是全场唯一的多空调房间**：K11–K16 六台。其余 11 台各自独占房间。
- **它们确实是同一个热力空间**：同分钟跨设备温度中位差 0.62 °C、湿度 2.42 %RH，
  两两相关系数 0.90–0.96（温）/ 0.98–0.99（湿）。作为对照，贮叶间 K05 与它们
  相差 3.5 °C、相关系数 0.17。
- ⚠ **但它是梯度不是分区**：单台自身 30 天标准差约 0.9 °C，组内 0.24 °C 的差异
  是自身波动的约 27%。六个探头在同一个大厅的不同角落，不是同一个探头的六份读数。
- ⚠ **整行清零的采集缺陷**：存在**全部 17 台同时**报 `fan_frequency = 0` 且
  `workshop_temp_avg = 0` 的分钟，下一分钟全部恢复。180 天内 596 行。按
  `fan_frequency > 0` 朴素判定会凭空造出开停机对——K11 的「1–5 分钟运行段」
  在掩掉这类行之后从 **51 段降到 0 段**。**判定前必须掩掉 `workshop_temp_avg = 0` 的行。**
- ⚠ **温度尖峰**：原始数据里有 K12 最大 273305、K13 最大 24228 这类值。它们只会
  把某一帧推出达标范围，因此后果是少算事件而不是算错事件，但训练前要过滤。
- **数据完整度**：全房间六台同时有效的分钟占 99.3%；1.57% 的分钟整行缺失；
  NULL 成片出现在约 10 天里，每次 130–165 分钟。
- **运行模式正在迁移**：full-5 组合占运行分钟的比例，2026Q1 为 71.4%、Q2 为 34.7%、
  Q3 只剩 15.3%，而 K11+K12+K14 升到 42.5%。⚠ **这意味着历史样本最多的组合，
  恰好是正在被弃用的那个。**

## 3. 开机事件的判定规则

**这一节是本期的核心，每一条都直接决定标签的对错。**

一次开机事件的抽取，按顺序：

1. **冷启动前提**：房间内**全部**空调连续全停 **≥30 分钟**。
   ⚠ 只认冷启动。半途加开一台形成的「热启动」不作为训练样本（记录但不训练）。
   实测停机间隔中位数约 390 分钟（夜间停机），30 分钟这条线几乎不丢真实冷启动。
2. **起始时刻** = 第一台空调 `fan_frequency > 0` 的那一帧。
3. **运行组合的确定：10 分钟滚动窗**。此后每有一台启动，只要距**上一台**不超过
   10 分钟就并入组合；从第一台起累计不超过 10 分钟。
   ⚠ 人工逐台启动会有间隔，固定窗会把一次正常的顺序启动误判成中途变更——实测
   固定 3 分钟窗会因此丢掉 96 次（占候选的 10%）。
4. **窗口关闭后，运行组合必须全程不变**，直到达标。任何一台启动或停止即
   **整条丢弃**（记录并标注原因，不参与训练）。
5. **达标判定**：房间内**每一台**空调各自的 `workshop_temp_avg` 与
   `workshop_humidity_avg` 都落在**它自己**配置的上下限内（闭区间），六台同时成立。
   达标时刻 = 首个满足的帧。
   ⚠ 达标窗口做成配置项，默认 **1 帧**；改成 N 帧要求连续 N 分钟满足。
   改这个值必须全量重算。
6. **上限**：100 分钟内未达标即丢弃并标注。
7. **数据质量**：窗口内出现连续 **>3 分钟**的缺失 / NULL / 清零，整条丢弃并标注。
   孤立单分钟缺口跳过、**不插值**——插出来的值会让「何时进入范围」变成我们
   自己编的答案。

判定顺序上的两处约定：

- 达标与运行集变更落在同一分钟时，**达标优先**（事件已经结束）。
- 无效分钟会打断「全停 ≥30 分钟」的连续计数。

## 4. 我们自己的数据（`platform` schema）

### 4.1 `hvac_ac_startup_batches` — 抽取批次

`id` · `room_id` FK · `params_fingerprint` text · `logic_version` int ·
`window_start` / `window_end` timestamptz · `status`（`running`/`ready`/`failed`）·
`is_current` bool · `shard_total` / `shard_done` int · `episode_count` int ·
`created_at` / `updated_at`

- 部分唯一索引：一个房间只能有一个 `is_current`。
- ⚠ **先算新批次、校验通过再原子切换**。绝不先删后算——中途失败会同时失去新旧两份。
- 每个房间保留最近 **3** 个批次，更老的清理。

### 4.2 `hvac_ac_startup_episodes` — 开机事件（事实，不含特征）

`id` · `batch_id` FK · `room_id` FK · `started_at` timestamptz ·
`running_set` text[]（空调 serial 升序）· `complied_at` timestamptz null ·
`duration_minutes` int null · `outcome` text（`usable` / `set_changed` /
`timeout` / `data_gap`）· `readings` jsonb（起始帧上每台的原始读数）·
`created_at` / `updated_at`

- 唯一约束 `(batch_id, started_at)`。
- ⚠ **只存事实，不存特征**（§6）：特征工程的迭代频率远高于事件定义，混在一张表
  里会让快的那个拖着慢的那个全量重算。

### 4.3 `hvac_ac_startup_exclusions` — 人工排除

`id` · `room_id` FK · `started_at` timestamptz · `reason` text ·
`excluded_by` text · `created_at`

- 唯一约束 `(room_id, started_at)`。
- ⚠ **按自然键挂，不挂事件行**：重算会换掉整批事件行，挂在行上的人工判断会被
  静默清空。重算后按键重新套用，并在批次摘要里报告**有多少条没能对上**——参数
  一变，某些事件的起始时刻会平移，旧键就落空了，这必须说出来。

## 5. 抽取的运行时

- **`worker` 角色 + Redis Stream**（ADR-0002）。⚠ **API 角色永不跑重任务**：
  HTTP 只负责入队与查进度。
- **分片按「房间 + 月」**，每片独立幂等，失败可单独重试。
  ⚠ **写入按起始时刻归属分片，读取必须向两侧越界**：向前 30 分钟（判冷启动）、
  向后 100 分钟（判达标上限）。读取也卡死在月界内的话，跨月的那次开机会在
  1 月分片里被判成「没达标」、在 2 月分片里根本看不到起始——**一次开机凭空消失，
  而两个分片都报成功**。
- 消费者必须幂等（队列是 at-least-once）。「先查再插」不算幂等——用自然键 upsert。
- **重算期间页面显示上一批次的完整数据** + 一条进度提示。⚠ 让人看到半份数据比
  看到旧数据危险：半份数据看起来是完整的，没有任何迹象说明它只抽到 6 月。
- **参数指纹** = 全部抽取参数的取值 + `logic_version`。指纹与当前数据不符即在
  页面上提醒重算。⚠ `logic_version` 由改抽取逻辑的人手动 +1；不对代码求哈希，
  否则一次格式化就触发全量重算提醒，很快没人理它。
  ⚠ 「手动」不等于「靠记」：改了 `ac_startup_rules.py` 或 `ac_startup_frames.py`
  的**代码**却没改 `LOGIC_VERSION` 的 PR，会被 `scripts/gates/check_logic_version.py`
  报红。否则一次没改参数的纯行为改动指纹分毫不变，页面会把旧规则算出的数据
  当成当前的。只改这两个文件里的 `#` 注释不算——+1 的代价是全量重抽一次。

## 6. 建模方案（本期不实现，先定口径）

### 6.1 预测目标

给定房间的当前条件与一个运行组合，预测**多久达标**。对外的用法是「现在这样开着，
几点能达标」，多台时对若干组合各出一个时间。

### 6.2 模型粒度

**一个房间一个模型，运行组合作为特征。** 不做每组合一个模型。

⚠ 理由是数据量：实测六台房间全史只有几百条可用事件，而 63 个子集里只有个位数
能攒够样本。每组合一个模型等于拿几十分之一的数据把同一套物理重学几十遍；把
组合编码成特征，则房间的共性（初始条件、时段、季节）由全部样本共同支撑，组合
只负责解释差异。

### 6.3 特征（约 19 个，训练时现算）

| 组 | 特征 | 个数 |
|---|---|---|
| 房间初始条件 | 各台温度均值、湿度均值、**最不利那台**的温度与湿度 | 4 |
| 距达标的距离 | 温度、湿度各自距范围边界的距离 | 2 |
| 运行组合 | 每台一个 0/1 指示 + 台数 | 7 |
| 蓄热状态 | 本房间全停时长 | 1 |
| 时段与季节 | hour 的 sin/cos、是否工作时段、月份的 sin/cos | 5 |
| 外部条件代理 | 运行机组的新风温度、新风湿度均值 | 2 |
| 供冷能力代理 | 运行机组的冷冻水供水温度均值 | 1 |

⚠ **「最不利那台」必须进特征**：达标由它决定（§3 第 5 条），只给均值的话模型
看不见真正卡住达标的那个量。
⚠ **特征数必须与样本量匹配**。参考实现有 64 个特征，而本房间可用样本是几百条量级；
照搬必然过拟合。

### 6.4 样本加权

**时间衰减权重**，并把季节放进特征。⚠ 运行模式正在迁移（§2），全史等权会让模型
以为 full-5 仍是常态；而只用近期数据则只覆盖一个季节——冬天的样本只存在于老数据里。

### 6.5 组合的可服务性判定

**按预测不确定度门控，不用硬样本数门槛。**

⚠ 硬门槛回答的是「这个组合我见过几次」，而操作员要问的是「这个数我能信几分」。
实测：可用样本第 3 名有 110 条、第 4 名只有 12 条，而第 4 名恰好是当前的主力
模式——任何介于两者之间的硬门槛，都会让工具无法回答现场今天真正在问的问题。
结构化模型（§6.2）可以从相邻组合借力预测它，代价是区间更宽；把区间宽度直接
呈现出来，比用样本数替它做决定更诚实。

## 7. 对外接口

沿用 `ac:view` / `ac:manage`，不新开权限码。

```
GET  /api/v1/platform/rooms/{room_id}/startup-episodes   （游标分页，可按组合/结果过滤）
GET  /api/v1/platform/rooms/{room_id}/startup-batches    （批次列表与当前批次）
POST /api/v1/platform/rooms/{room_id}/startup-batches:rebuild   （入队重算）
PUT  /api/v1/platform/rooms/{room_id}/startup-exclusions/{started_at}
DELETE /api/v1/platform/rooms/{room_id}/startup-exclusions/{started_at}
```

⚠ `:rebuild` 是动作端点，POST；它**只入队**，不在请求里干活。

## 8. 页面

`/hvac/startups`，进主导航（房间作为页内筛选），沿用 `ac:view`。

- 事件列表：起始时刻、运行组合、达标时长、结果（可用 / 各类丢弃原因）。
- 组合覆盖度：每个组合各有多少可用事件。
- 单条下钻：复用原始数据页的折线，画出这次开机的温湿度曲线。
- 人工排除：带原因，**被排除的事件置灰保留、不消失**。
- 参数指纹不符时给出重算提醒；重算中显示进度且仍展示上一批次。

## 9. 本期有意没做

- **不做训练与预测**。先把事件抽出来、能在页面上看和改——开机事件的边界有一堆
  只有把真实数据摆在眼前才能确认的情况，在标签没被人眼验过之前训练，等于拿没
  校对的标签去拟合，而模型只会给你一个看起来合理的 MAE。
- **不做未见组合的外推**。
- **不把热启动收作训练样本**。
- **不在事件表里存特征**（§4.2）。
