# 空调预测下发与每日增量抽取设计

把 [`AC_MODEL_DESIGN.md`](AC_MODEL_DESIGN.md) 的预测结果**周期性写进 OPC UA 点位**，
让上位系统（SCADA/MES）不经人、不经页面就能读到「现在该开哪几台、各要多久达标」；
并把 [`AC_STARTUP_DESIGN.md`](AC_STARTUP_DESIGN.md) 的开机事件从「人工按钮触发的全量
重算」补上一条**每日增量**，让当天的开机第二天就能进训练集。

这两件事都是 `AC_MODEL_DESIGN.md` §7 与 `AC_STARTUP_DESIGN.md` §9 记的「本期有意
没做」，本期做掉。做法上有意与那两处的顾虑对齐：§7 担心「加调度器是在没有心跳的
系统里多养一个会静默失败的组件」，故本文档 §5.4 把心跳做成可见的——每个模型行上
都有「上次发布是什么时候、成没成、没成是为什么」。

---

## 1. 通用语言

| 词 | 指什么 | 不叫什么 |
|---|---|---|
| **发布配置** `publication` | 一个模型往哪台 OPC UA 实例、哪些点位下发 | 不叫绑定关系 / 订阅 |
| **区域推荐点位** `recommendation node` | 承载「推荐开哪几台」的那个字符串点位 | 不叫结果点位 |
| **组合时间点位** `set duration node` | 承载某个服务组合预测达标分钟数的那个数字点位 | 不叫预测点位 |
| **绑定完整** `fully bound` | 实例 + 区域点位 + **每一个**服务组合的点位都已绑 | 不叫已配置 |
| **一拍** `tick` | 发布循环的一个周期，默认 60 秒 | 不叫轮询 / 刷新 |
| **日增量** `daily append` | 每天 00:00 把刚过去那一天的开机事件补进当前批次 | 不叫增量重算 |

⚠ **「区域」在库里就是房间 `Room`**（`AC_STARTUP_DESIGN.md` §1、`models/room.py`）。
本文档不引入新的空间层级：模型本来就是房间级的，「每个区域一个字符串点位」落到
实现上即「每个模型一个字符串点位」。

⚠ **同一房间可以有多个模型**（模型名在房间内唯一即可）。它们各有各的发布配置、
各写各的点位。要让两个模型写同一个点位是配置错误，由 §3.3 的唯一约束挡住。

## 2. 为什么要在 opcua-server 上新开内部端点

opcua-server 当前只有一条写值路径：`POST /api/v1/opcua/instances/{id}/nodes/{node_id}:write`，
它要 `opcua:operate` 权限，而权限来自**边缘网关注入并签名的 `X-Auth-*` 身份头**——
那是一条为「浏览器里的人」铺的路。platform-server 的发布循环不是人，它没有、也不该有
一个人的令牌。

`CONTEXT.md` 把「桥接内部点位」列为非目标，理由是不想让 opcua-server 反向依赖采集
运行时。本期不违反它：**依赖方向仍然是 platform-server → opcua-server**，opcua-server
不知道模型、房间、组合是什么，它只认「把这个值写进这个节点」。

故新增两个内部端点，挂 `require_service_key`（`deps.py` 里已经有这个依赖，此前从未被
任何 router 用上）：

```
POST /internal/v1/opcua/nodes:resolve   批量取节点的数据类型与 NodeId（绑定时校验用）
POST /internal/v1/opcua/nodes:write     批量写值，逐项回执
```

- **批量不是为了省事，是为了超时预算**：一个模型一拍要写 1 + N 个点位，逐个打就是
  1 + N 次往返，每次都要各自的超时，加起来会超过一拍。批量把它压成一次。
- **逐项回执、允许部分失败**：某一个点位被人删了不该让另外几个也写不进去。整体
  失败与逐项失败在回执里分得开。
- ⚠ **`:resolve` 是必需的，不是锦上添花**。没有它，platform-server 只能在写的那一刻
  才发现「这个点位是 boolean，塞不进分钟数」——而那是每分钟发现一次、永远发现下去。
  绑定时问一次，把类型错挡在配置面。

### 2.1 类型口径

| 用途 | 允许的 `data_type` | 理由 |
|---|---|---|
| 区域推荐点位 | `string` | 组合名是文本 |
| 组合时间点位 | `float` / `double` | 分钟数是小数；⚠ 整数型放不下 `12.4`，也放不下 §4.3 的 `-1` 语义之外的小数部分 |

⚠ opcua-server 声明了 15 种 `data_type`，但运行时 `runtime/datatypes.py` 只映射了 7 种。
上面这三种都在那 7 种里，本期不碰这处既有的口径差（见 §7）。

## 3. 数据（`platform` schema，两张表）

### 3.1 `hvac_ac_model_publications` — 发布配置

`model_id` PK+FK（CASCADE）· `opcua_instance_id` uuid · `recommendation_node_id` uuid ·
`recommendation_identifier` text · `is_enabled` bool · `last_published_at` timestamptz null ·
`last_status` text null（`ok`/`degraded`/`failed`）· `last_error` text null ·
`created_at` / `updated_at`

- 一个模型至多一份发布配置，故 `model_id` 直接做主键。
- ⚠ **`opcua_instance_id` 与 `recommendation_node_id` 不是外键，也不可能是**：它们是
  opcua-server 自己库里的行，跨服务无外键（一库多 schema、写独占读放行）。代价是
  实例或节点被删掉时这里会留下悬空的 id——处置见 §5.5，**不静默跳过**。
- `recommendation_identifier` 是**快照**：只为页面与日志好读。判等一律用 id。

### 3.2 `hvac_ac_model_set_bindings` — 组合 → 时间点位

`id` · `model_id` FK（CASCADE）· `set_key` text · `node_id` uuid · `identifier` text ·
`created_at` / `updated_at`

- 唯一 `(model_id, set_key)`。
- `set_key` 沿用 `modeling/evaluation.py` 的那一个：serial 升序用 `+` 连接。
  ⚠ **不存 `running_set` 数组**：数组作唯一键要靠排序约定，而 `set_key` 已经是模型
  内部、工件里、指标里到处都在用的那把钥匙，再造一把只会有两把不同步的钥匙。
- 模型的 `serving_sets` 改了之后，落空的绑定**留着不删**：改组合是就地重汇总
  （`AC_MODEL_DESIGN.md` §5），改回去时绑定还在。页面把落空的那些标出来。

### 3.3 一个点位只能有一个来源

部分唯一索引 `(opcua_instance_id, recommendation_node_id)`、
`(model_id 所属实例, node_id)`——两个模型同时往一个点位写，上位机读到的值会在两个
模型之间反复横跳，而两边的日志都报成功。⚠ 这条必须由**数据库**挡，不能只在应用里
校验：绕开应用直接改库同样能造出双写，而它看起来与正常配置毫无区别。

实现上组合点位的唯一性跨了两张表（实例 id 在发布配置上、节点 id 在绑定上），故在
绑定表上冗余一列 `opcua_instance_id`，与发布配置同事务写入并由 CHECK 对齐。

## 4. 写进点位的到底是什么

### 4.1 区域推荐点位（字符串）

排第一名的那个服务组合的 `set_key`，逐字如 `K11+K12+K14`。

⚠ **不写 JSON、不写带单位的句子**：上位系统拿它去做画面显示与联锁判断，多一个
字符就要多一处解析。要更多信息，绑更多点位，不要把点位当消息队列。

### 4.2 组合时间点位（数字）

该组合的 **p50 达标分钟数**，浮点，如 `12.4`。

- 口径同 `:recommend` 的 `p50`：「按当前实时工况，开这个组合，多半 12.4 分钟后房间达标」。
- ⚠ **`0` 是合法值不是缺省值**：现网 48.7% 的可用开机「一开机就已达标」，p50 = 0 的
  语义是「多半一开机就达标」。所以「算不出来」绝不能用 0 表示——见 §4.3。

### 4.3 算不出来的时候写什么

**数字点位写 `-1`，字符串点位写以「无预测：」开头的人话原因。**

| 情形 | 区域点位 | 该组合的时间点位 |
|---|---|---|
| 一切正常 | `K11+K12+K14` | 各自的 p50 |
| 模型没训好 / 工件不可用 | `无预测：模型还没有一次成功的训练` | 全部 `-1` |
| EMS 外库不可达 | `无预测：EMS 数据源不可达` | 全部 `-1` |
| 某组合含工件不认识的机组 | 照常写第一名 | **只有该组合**写 `-1` |
| 全部组合都被跳过 | `无预测：服务组合里的机组都不在训练时的清单里` | 全部 `-1` |

- ⚠ **降级要写进去，不是不写**。保持上一次的值意味着上位机读到的是几小时前的结论
  而无从分辨；`docs/adr/0006` 的「返回陈旧数据必须标注为陈旧」在只有一个数字的点位
  上，唯一可行的标注方式就是不返回它。
- ⚠ **`-1` 这个取值本身要在页面上说清楚**，且不可配置。可配置的哨兵值等于每个现场
  一套语义，而上位机的联锁逻辑是照着文档写死的。
- opcua-server 自己不可达时**什么都写不进去**，这一档只能落在 `last_status=failed`
  上由页面报出来——这是唯一一处「点位停在旧值」的情形，无法避免。

## 5. 发布的运行时

### 5.1 角色与单活

**`worker` 角色里的第三条循环**，与分片消费、训练消费并列。

- ⚠ **必须单活**：worker 会有多个副本，不加租约就是每个副本每分钟各写一遍同一批
  点位。用 `platform:ac-publish:leader`，renew-or-die，**Redis 不可达一律判非 leader**
  （`runtime-resilience.md` §7）。
- 不放进 `publisher` 角色：那个进程是大屏实时发布的，两件事的故障域、节奏与依赖
  都不一样，混在一个进程里就是一起挂。

### 5.2 一拍做什么

对每个「已启用且绑定完整」的模型，依次：

1. 读房间实时读数（`ac_live_readings.read_live`，打外部 EMS 只读库）
2. `ac_model_predictor.recommend()`（纯计算，读工件）
3. 拼出 1 + N 个写值项
4. 一次 `POST /internal/v1/opcua/nodes:write`
5. 把结果记回 `last_published_at` / `last_status` / `last_error`

### 5.3 超时与重试

- 一拍 60 秒。EMS 读 15 秒、opcua 写 5 秒，逐模型串行但整拍有 45 秒的总预算，
  到点即止，没轮到的模型这一拍不发——**下一拍会轮到，不补**。
- ⚠ **不重试**。这条链路上没有任何一层在重试；下一拍就是重试，而且带的是更新的
  数据。逐层重试会相乘成雪崩，何况重试一个 60 秒后必然重来的动作毫无意义。
- ⚠ **一个模型出错不许打断整拍**：每个模型各自 try，失败只落它自己的 `last_error`。

### 5.4 心跳要看得见

`AC_MODEL_DESIGN.md` §7 反对加调度器的理由是「会静默失败」。对策：

- 每个模型行上有 `last_published_at`，页面按「距今多久」显示；超过 3 拍没更新就标红。
- 每拍开头绑一次新 trace（⚠ contextvars 不跨任务传播，不绑就是一串全零，链路在这
  一跳齐断）。
- 日志的 `event` 是稳定字面量：`ac_publish_tick` / `ac_publish_model_failed` /
  `ac_publish_skipped`。⚠ **跳过与发布成功必须是两个 event**——混成一条的话，一个
  从来没发布过的模型在日志里与正常发布的一模一样。

### 5.5 绑定悬空了怎么办

`:resolve` 报某个节点不存在（实例被删、节点被删）时：**不清绑定、不停发布**，
把这一拍记成 `failed` 并把原因写进 `last_error`，页面在绑定页签上把那一行标红。

⚠ 自动清掉悬空绑定是错的：opcua-server 短暂不可达与「节点真的被删了」在这一层
分不开，而自动清掉的后果是人回来发现配置空了，还以为自己没配过。

## 6. 每日增量抽取

### 6.1 落到哪里

**追加进房间的当前批次**（`is_current` 的那一个），按自然键 `(batch_id, started_at)`。

代价说清楚：批次从此不再是「一次跑出来的不可变快照」。换来的是当天数据次日即可
训练，而不必每晚把厂商外库的三年全史重读一遍（那是几十分钟的白算，且代价落在
别人的库上）。

### 6.2 窗口

在 `acsource_timezone` 的每天 00:00 触发，处理**刚过去的那一天** D：

```
write_start = D 00:00 − compliance_cap_minutes     ← 关键，见下
write_end   = D 24:00
read_start  = write_start − max(cold_off, idle_lookback)
read_end    = write_end + compliance_cap_minutes
```

⚠ **`write_start` 必须往回退一个达标上限**。00:00 这一刻，D 当天最后 100 分钟里
开的机还没跑完——判达标要向后读 100 分钟，而那 100 分钟的数据尚未产生。不往回退的
话，每天 22:20 之后的开机会被永久判成「没达标」并就此定格。往回退一个达标上限，
昨夜那一段就在今晚被**带着完整数据重判一次**，结论覆盖旧的。

D 当天最后 100 分钟的事件，因此在第二天 00:00 才定案——这是数据本身决定的延迟，
不是实现的将就。

### 6.3 整窗替换，不是只插不删

一次日增量**先删掉当前批次在 `[write_start, write_end)` 内的全部事件，再写这一次
算出来的**，同一个事务。

⚠ 只 upsert 不删是不够的：§6.2 的重判可能让某次开机的**起始时刻发生位移**（数据
补齐后状态机认定的第一帧变了），旧那一行的键还在，于是同一次开机在库里留下两条。
整窗替换是这条链路上唯一能自洽的幂等方式。

人工排除挂在 `(room_id, started_at)` 自然键上（`AC_STARTUP_DESIGN.md` §4.3），不随
事件行删除而丢失——这正是当初把它挂在自然键上的理由。

### 6.4 什么时候不追加

| 情形 | 处置 |
|---|---|
| 房间没有当前批次 | 跳过（还没做过全量抽取，没有可追加的地方） |
| 批次的 `params_fingerprint` 与当前规则不符 | **跳过**并记日志：混两套规则算出的事件比缺一天更糟 |
| 批次的 `logic_version` 与当前不符 | 同上 |
| 房间一台空调都没绑数据源 | 跳过 |

⚠ 跳过一律是**显式终态 + 一条独立的 `event`**，不是静默返回。

### 6.5 调度器与消费者要分开

调度器持租约（`platform:ac-startup-daily:leader`）、**只入队**；抽取由新的消费循环
在 `platform:ac-startup:daily` 流上干。

⚠ 这不是照搬架构模板，是租约的硬约束：**锁内禁长 IO**
（`runtime-resilience.md` §7）。调度器要是自己跑抽取，几分钟的外库读会让租约续期
排在后面，租约过期后第二个副本接任，于是同一天被抽两遍——而整窗替换让这个错误
恰好看不出来，直到某天两个副本的读数不一致。

消息是 `(room_id, business_date)`，消费者幂等（整窗替换）。⚠ 每条消息必须停在终态，
与分片消费同一条纪律。

### 6.6 与全量重算的关系

日增量写当前批次，全量重算建**新**批次再原子切换，两者不碰同一行，可以并发。
重算的窗口右端会取到数据源的实际末端（含今天），故切换之后新批次自带这些天的
数据，日增量从下一夜起接着往新的当前批次上追加。

## 7. 顺带发现但本期不修

探查 opcua-server 时发现两处既有的口径不一致，与本期功能无关，**不在本期改**
（一个 PR 只碰一件事），另开议题：

1. `data_type` 声明 15 种、运行时只认 7 种。建一个 `int16` 节点能过 API 与 CHECK，
   热加时才抛；实例当时没在跑的话，会在**下次启动时让整台实例起不来**。
2. `identifier_kind = numeric` 的节点，管理面对外给 `ns=2;i=<id>`，而运行时地址空间
   建的是 `ns=2;s=<id>`。上位机按管理面给的 NodeId 会连不上。

本期的绑定只用 `string` / `double`，且 `:resolve` 回的是节点自己的 `identifier`，
两处都绕开了，但它们仍然是真问题。

## 8. 对外接口

沿用 `ac:view` / `ac:manage`，不新开权限码。

```
GET    /api/v1/platform/ac-models/{id}/publication          （ac:view）
PUT    /api/v1/platform/ac-models/{id}/publication          （ac:manage，整份保存）
DELETE /api/v1/platform/ac-models/{id}/publication          （ac:manage，解绑，幂等）
POST   /api/v1/platform/ac-models/{id}/publication:publish  （ac:manage，立刻发布一次，Idempotency-Key）
```

- `PUT` 是**整份保存**不是补丁：绑定是一组必须同时成立的东西（实例换了，底下所有
  节点 id 都得跟着换），逐字段 PATCH 会让中间态出现「节点 id 属于旧实例」。
- `:publish` 走与循环完全相同的那一条代码路径，只是不经租约——「点一下试试」与
  「每分钟自动跑」必须是同一段代码，否则页面上试通了、循环里还是不通。

opcua-server 一侧（服务级密钥，不进 openapi 的公开面）：

```
POST /internal/v1/opcua/nodes:resolve
POST /internal/v1/opcua/nodes:write
```

## 9. 页面

模型详情页 `/hvac/models/:id` 新增**「点位绑定」页签**（`AC_MODEL_UI_DESIGN.md` §4
的形态纪律照用）。

- 顶部：OPC UA 实例选择 + 实例是否在跑 + 自动发布开关 + 上次发布时刻与结果。
- 区域推荐点位：一个节点选择器，**只列 `string` 类型的节点**。
- 服务组合表：一行一个服务组合，右侧节点选择器**只列 `float`/`double`**；未绑的
  行显著标出，底部一句「N 个组合已绑 M 个 → 未开始发布」。
- ⚠ **未绑完就不发布，这件事要在页面上说出来**，不能只在后端沉默地跳过。
- 落空的绑定（`set_key` 已不在 `serving_sets` 里）单列一段，可一键清理。
- 「立刻发布一次」按钮，回执逐点位显示成没成。

## 10. 本期有意没做

- **不做点位的自动创建**。绑定只从 opcua-server 已有的节点里选；替用户建节点等于
  平台去写别人的地址空间，而地址空间的形状是现场与上位机约好的。
- **不做发布周期可配**。60 秒是数据本身的节奏（EMS 逐分钟写入），做成配置项只会
  让人调到 5 秒然后把外库压垮。
- **不下发 p10/p90 与可靠性**。要它们再各绑一个点位即可，但在没有现场提出之前，
  多写的每一个点位都是多一处要维护的语义。
- **不做日增量的失败重试与补漏**。漏掉的那一天由人看到提示后点全量重算——`§6.4`
  的跳过都是配置问题，重试改不了配置。
