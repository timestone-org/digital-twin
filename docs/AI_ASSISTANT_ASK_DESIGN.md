# 助手向用户提问：给选项，不要让人打字

助手需要用户拿主意时，现在的做法是**在正文里问一句**，然后等用户打字回答。
两个问题：用户得自己把选项想出来；他打的字与模型心里的候选常常对不上，于是
再问一轮。本文把这件事改成**结构化提问 + 前端出选项**。

三条支柱不动（工具两侧分派、POST+SSE 客户端驱动、技能渐进披露）。

---

## 1. 一个工具就够：`user.ask`

它是**客户端工具**——问题要在浏览器里渲染成可点的选项，答案由用户给出。
于是整条「服务端停下 → 前端执行 → 带结果续跑」的既有协议原样复用，
不新增任何协议（ADR-0023）。

```
user.ask(
  question:         str,                       # 一句话问题
  options:          [{value, label, hint?}],   # 必给，2–6 个
  allow_multiple:   bool = false,              # 可多选
  allow_free_text:  bool = false,              # 除选项外还给一个输入框
  free_text_label:  str | null = null,         # 输入框的提示语
) -> { picked: [value], free_text: str | null, is_cancelled: bool }
```

### 为什么 `options` 是**必给**的

做成可选的话，模型会一路退回「不给选项的自由提问」——那正是今天的行为。
真正开放的问题（起个名字、填一个数）用 `allow_free_text=true`，
**并且仍然要给几个常见候选**：给了候选，八成的情况用户点一下就过去了。

### 为什么取消是**成功结果**而不是失败

`is_cancelled: true` 是一条正常回执。⚠ 订阅那一路上**没回执的 tool_call 会把
会话锁死**（见 `llm/codex/wire_names.py` 与 [[codex-route-runtime-facts]]），
所以用户不回答时也必须送一条结果回去。送成 error 的话模型会去排查「工具坏了」；
送成 `is_cancelled` 它才知道该换个方式往下走。

### ⚠ `user.ask` 必须**单独**成一批

一批里除了 `user.ask` 还有别的调用时，**只执行 ask，其余一律回失败**，
失败话术固定：`user.ask 必须单独发：要先拿到用户的回答才能动手`。

理由是这条工具最要紧的用途——确认。模型很容易发出
`user.ask("要覆盖这 12 条绑定吗？") + write_binding × 12` 这样一批；
按顺序跑的话，用户点「取消」而覆盖照样发生了。而「哪个选项算取消」是
模型的语义、前端读不出来，所以只能从批次这一层拦。

## 2. 前端：选项是主路，打字是逃生口

- 时间线上多一类条目 `ask`，由 `AiAskCard.vue` 渲染：问题 + 一排选项按钮。
  `allow_multiple` 时是多选 + 一个「确定」；`allow_free_text` 时多一个输入框。
- **待回答期间禁用输入框**，并在卡片上给一个「我自己说」——点了等于
  `is_cancelled: true`，输入框随即解禁。
  ⚠ 不做成「打字即取消」：那时用户的新消息与正在跑的回合会抢，
  两个回合同时写一条时间线，谁后到谁覆盖。
- 答完卡片就地收起，只留「你选了：…」一行。
- ⚠ **回放不还原可点的卡片**：那一轮早就结束了，点了也没有人在等这个答案。
  历史里它就是一条普通的工具步骤。

---

## 3. 提示词：什么时候该问，什么时候不许问

常驻提示词里「不确定就问」那一条改写成：

- 要用户拿主意就调 `user.ask`，**不要在正文里问一句然后等他打字**。
- **能自己查清的不要问**。哪张大屏、有哪些模块、点位叫什么——先用只读工具查。
  问一句用户要读要想，比你自己查一次贵得多。
- 一次只问一件事。攒着两三个问题一起问，用户答完第一个就忘了第二个。
- 危险动作（覆盖已有绑定、删节点、整屏重排）**先问再做**。
- 选项要能**互斥地穷尽**这一步的分叉，并把最可能的排在第一个。

各技能正文里现有的「问一句」也一并改成指向这个工具。
