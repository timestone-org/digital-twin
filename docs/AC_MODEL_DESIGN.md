# 空调达标时长的建模设计

在 [`AC_STARTUP_DESIGN.md`](AC_STARTUP_DESIGN.md) 抽出的开机事件之上做训练与
预测：给定房间当前条件与一个运行组合，回答「多久达标」。§6 已定的口径本期落地，
本文档只补落地层面的决策；与 §6 相同的内容不重复，只标节号。

---

## 1. 通用语言

| 词 | 指什么 | 不叫什么 |
|---|---|---|
| **模型** `model` | 一个房间的达标时长预测器：一份配置 + 最近一次训练的产物 | 不叫算法 / 任务 |
| **训练** `training` | worker 上跑的一次拟合，产出工件、评估与逐条折外预测 | 不叫作业 / run |
| **服务组合** `serving sets` | 建模时勾选的那几个运行组合：页面重点评估它们、试算默认从它们里选 | 不叫目标组合 |
| **折外预测** `out-of-fold prediction` | 一条事件在**它不参与训练的折**上得到的预测 | 不叫回测 |
| **工件** `artifact` | 训练完序列化存库的拟合结果 | 不叫模型文件 |
| **试算** `what-if` | 给一组假想条件立刻算一个预测，纯计算不训练 | 不叫仿真 |

**「选组合」= 每个组合各训一个专属子模型（拍板于 2026-08-13）。** 每个勾选的
组合，只要攒够 `MIN_SAMPLES`（30）条可用事件，就用**只属于它的数据**训一套
两段模型，预测时各组合各答各的；攒不够的组合由**房间共用模型**（全部可用
事件、组合进特征）兜底，且结果上明确标注 `is_dedicated=false`——兜底不是
失败，但必须说出来。折外评估各归各：专属子模型的指标只由它自己的折外预测
算出。训练一律只用 `outcome=usable` 且未被人工排除的事件。

## 2. 算法与评估

### 2.1 两段混合的随机森林 ×（专属子模型 + 共用兜底）（v2）

⚠ **目标是零膨胀的**：现网实测 48.7% 的可用开机「一开机就已达标」（时长 0），
中位数只有 2 分钟。对这种分布直接回归，学到的就是「多数情况 0 分钟」——v1
的分位数回归正是这样把非零场景稀释没的（93 条实际 >5 分钟被折外预测成 0）。

正解是按分布的真实结构拆两段：

- **阶段 A**：`RandomForestClassifier` 答「会不会瞬时达标」，出 p₀。
- **阶段 B**：`RandomForestRegressor` 只在**非零样本**上答「不瞬时的话多久」，
  区间取树间预测的分位（实用近似，不假装是完整分位数回归森林；偏窄由覆盖率
  指标暴露）。
- **对外三分位走混合分布公式**：水平 q 上的分位 = 0（当 q ≤ p₀），否则为
  条件分布在 (q − p₀)/(1 − p₀) 水平上的分位。p50 = 0 于是有了明确语义：
  「多半一开机就达标」，而不是模型摆烂。

- **区间就是 §6.5 的不确定度门控**：页面按区间宽度标注「可靠 / 参考 /
  仅供参考」（阈值见 `modeling/gating.py`），不设硬样本数门槛。
- ⚠ **随机森林自 sklearn 1.4 起原生吃 NaN**：缺测特征记 NaN，不插值不填充
  ——插出来的值会把「传感器坏了」伪装成「一切正常」。
- 边界情形：训练集全零 → 阶段 B 缺席，混合退化成恒 0；训练集全非零 →
  阶段 A 退化成常量 p₀=0。两者都显式处理，不靠 sklearn 的单类行为。

### 2.2 时间衰减权重 + 季节特征（§6.4）

样本权重 `exp(-age_days / half_life)`，半衰期默认 180 天、可配。月份 sin/cos
进特征，冬季样本靠特征区分而不是靠丢弃。

### 2.3 评估 = 时序分块 K 折的折外预测

按 `started_at` 排序切成 K 个连续时间块（默认 5），每折用其余折训练、对本折
预测。每条可用事件恰好有一次「模型没见过它」的预测——评估指标与页面上的
逐条对比**全部**来自折外预测，最终工件另用全量数据拟合。

- ⚠ **不随机打乱**：运行模式在迁移（§2 实测），随机折会把未来的模式泄给过去，
  指标虚高且方向不可知。时序分块的代价是指标偏保守——它同时在考「模式变了
  还准不准」，这正是上线后要面对的问题。
- 指标：MAE、MedAE、RMSE、区间覆盖率（实际值落进 [p10,p90] 的比例，标称 80%）、
  平均区间宽度、R²（折外 p50 对实际的决定系数，可为负；⚠ 实际值没有离散度
  （含单样本）时无定义，给 null 不给 0/1）；总体一份、每个服务组合各一份。
- ⚠ **覆盖率显著低于 80% 要在页面上标出来**：区间本身在撒谎，比 MAE 高更危险。
- ⚠ **热行（实际 > 0）单独一份统计**（2026-08-13 拍板）：零占比高达五到八成，
  整体 MAE 被大量「误差为零的零行」灌水，看着 3 分钟其实热行 MAE 是 14 分钟。
  每个指标块另报：热行的六元组统计、零行数、**判零率**（零行被判 0 的占比）与
  **判出率**（热行被判出非零的占比，漏报的补）。页面以热行统计为主口径。

### 2.6 超参与零值处理——现网数据的折外对比实验（2026-08-13）

用两个现网房间（生产线 785 条/零 49%，加香间 975 条/零 77%）跑时序分块
5 折折外，对比了基线、log1p 目标、叶子下限、max_features、类权重、零样本
降采样与判零门槛位移共 14 个变体。结论：

- **赢家（现行配置）**：两段森林叶子下限 5→2；时长森林 **log1p 尺度** +
  `max_features=0.5`。生产线共用热行覆盖率 58%→70%、MedAE 11.7→9.9；
  专属 K01+K03+K04 覆盖 73%→79%；加香间热行 MAE 3.2→2.6。log 尺度是
  `DurationForest` 的内部约定（进出都是分钟），改它动了工件语义 →
  `FORMAT_VERSION` 3。
- **零值剔除/降权实测无增益，不引入**：判零分类器本来就 98–100% 准，类权重
  balanced、零样本降采样到 1:1/2:1 都没有改善热行漏报；判零门槛位移能压一点
  漏报（18%→16%）但判零率掉 6 个点、覆盖率也掉——用概率失真换小利，放弃。
  零膨胀的「剔除」正确位置在结构里：阶段 B 只用非零样本，这一点 v2 起就有。
- 漏报的真正解是分类器叶子 2（K01+K03 漏报 18%→14%、判零 100%）。

### 2.4 特征（`FEATURE_VERSION = 2`，N+23 个；卷包房间 N=6 即 29 个）

§6.3 的表落到代码里的口径（`modeling/features.py` 是唯一真源）：

| 组 | 特征 | 说明 |
|---|---|---|
| 房间初始条件 4 | 温/湿度均值；最不利那台的温/湿度超限量 | 超限量 = max(下界−值, 值−上界, 0)，全达标为 0 |
| 距达标距离 2 | 温/湿度的房间级带内余量 | 负 = 已在带内的富余，正 = 距带边的欠账 |
| 运行组合 N+1 | 房间内每台一个 0/1 + 台数 | N 按房间定（卷包 6，独占房间 1） |
| 蓄热状态 1 | 全停时长（分钟，截断在回看上限） | 老批次没这列时记 NaN |
| 时段季节 5 | hour sin/cos、是否工作时段、月份 sin/cos | 按 `acsource_timezone` 折算本地时 |
| 外部条件 2 | 运行机组新风温/湿度均值 | 缺测记 NaN |
| 供冷能力 1 | 运行机组冷冻水供水温度均值 | 缺测记 NaN |
| 设定值距离 2 | 温/湿度距设定值的平均差 | 控制器追的是设定值不是达标带 |
| 空气状态 3 | 运行机组回风温/湿度、送风温度均值 | 回风是房间空气的近端读数 |
| 房间梯度 2 | 温/湿度全房间极差 | 没混匀就要等最慢的角落 |

⚠ `FEATURE_VERSION` 与 `LOGIC_VERSION` 同一纪律：改特征算法手动 +1，模型上
存着训练时的取值，页面据此提示「特征口径已更新，建议重训」。

### 2.5 蓄热特征要抽取侧补一列

事件表只存事实（§4.2），但「全停时长」是抽取状态机数出来的事实而不是特征——
它记在事件上（`idle_minutes`，可空）。配套：

- 新规则参数 `idle_lookback_minutes`（默认 720）进指纹；分片读取的向前越界量
  从 `cold_off_minutes` 扩到 `max(cold_off, idle_lookback)`。
- ⚠ 数出来的全停时长**截断在回看上限**：序列开头之前看不见，只认亲眼数到的。
- `LOGIC_VERSION` 1 → 2，全量重抽一次。老批次该列 NULL，特征层按 NaN 处理，
  不擅自编一个值。

## 3. 数据（`platform` schema，三张表）

### 3.1 `hvac_ac_models` — 模型

`id` · `room_id` FK · `name`（房间内唯一）· `description` · `serving_sets`
jsonb（组合列表，每个组合是 serial 升序数组）· `half_life_days` int ·
`status`（`queued` / `training` / `ready` / `failed`）· `error` text ·
`feature_version` int · `trained_at` · 训练出处快照（`batch_fingerprint` /
`logic_version` / `window_start` / `window_end` / `sample_count` /
`usable_count`）· `metrics` jsonb（总体 + 按服务组合）· `created_by` · 时间戳

- ⚠ **训练出处是快照不是外键**：批次每房间只留 3 个（§4.1），外键会让老模型
  跟着批次清理一起消失或挡住清理。快照记「当时用的哪份数据」，页面比对当前
  批次指纹给出「数据已更新，可重训」提示。
- 状态机只有一条路：`queued → training → ready|failed`；重训回到 `queued`。
  ⚠ 重训失败**保留上一份工件与评估**并标 `failed` + 原因——坏一次训练不该
  把能用的模型变成不能用的。

### 3.2 `hvac_ac_model_artifacts` — 工件

`model_id` PK+FK（CASCADE）· `payload` bytea（joblib：三个估计器 + 特征列名 +
房间机组序号表）· `digest`（SHA-256）· `format_version` int ·
`sklearn_version` · `python_version` · `trained_at`

- 单独一张表：列表页查模型不该把几百 KB 的字节拖出来。
- ⚠ **加载前三道护栏**（照 BK 的 D9a）：摘要不符拒载、`format_version` 不识
  拒载、`sklearn_version` 主次版本不符拒载，拒载一律给人话原因落在接口上，
  不静默降级。工件只有应用自己写入（写面全在 `ac:manage` 后面），摘要防的是
  存储损坏与手改库，不防拿到 DB 写权限的攻击者——那时输的就不是这一层了。

### 3.3 `hvac_ac_model_predictions` — 折外逐条

`id` · `model_id` FK（CASCADE）· `started_at` · `running_set` text[] ·
`actual_minutes` int · `p10` / `p50` / `p90` real · `fold` int ·
唯一 `(model_id, started_at)`

- 「历史每一条的预测与实际对比」的落点。派生数据，重训在同一事务里整体换掉。
- real 够用：达标时长本身是分钟粒度的整数，预测保留一位小数只为排序稳定。

## 4. 训练的运行时

- 沿用 worker 角色 + Redis Stream（ADR-0002），新流 `platform:ac-model:train`，
  worker 进程里第二个消费循环与分片消费并行。API 只入队。
- ⚠ **拟合进进程池**：训练是 CPU 密集，几秒的阻塞会卡住 worker 事件循环上的
  另一条消费循环与租约心跳（async 里禁阻塞、线程池救不了 GIL）。进程池单
  worker，喂纯数据（特征矩阵 + 配置），收纯数据（工件字节 + 指标 + 逐条预测），
  两头都可 pickle。
- ⚠ **子进程是 spawn 起的**（Windows 上只有 spawn）：它的 `sys.modules` 是空的，
  喂进去的函数与入参在那边**从零 import**。故 `modeling/*` 必须是不指回
  `services/` 的叶子——`services/__init__.py` 是桶式公开面，一条反向边就绕成
  循环 import，子进程解 pickle 时当场死掉。房间机组与达标范围的值对象因此放在
  `apps/hvac/rooms.py`。父进程与 Linux（fork）都撞不上这条：前者 services 早已
  装好，后者直接继承父进程的 `sys.modules`。
- ⚠ **池坏了必须换池**：子进程一旦猝死，`ProcessPoolExecutor` 就被永久标记为
  坏，此后每次 `submit` 都秒抛 `BrokenProcessPool`，这个 worker 进程再也训不了
  任何模型。超时与整池损坏两条路径都走 `TrainerPool.recycle()`。
- 工件的 pickle 里写死了成员类的模块路径（`RoomUnit` / `MetricBand`）：类可以
  搬家，但旧路径下必须留得住同名的名字，否则存量工件一起拒载。形状与语义没变
  就不动 `FORMAT_VERSION`——为一次搬家逼所有房间重训是白付的代价。
- 消息只带 `model_id`（+ traceparent）。消费者幂等：重复消息=按行里的当前配置
  再训一次，结果覆盖写，收敛到同一状态。⚠ 消息不带配置快照：以行为准，改配置
  后的重复旧消息训出来的就是新配置的结果，这正是想要的。
- 入队沿用 `request_rebuild` 的先例：**建行的事务自己提交，之后才投消息**
  （FastAPI 的 after_commit 不可信，见 §5 的教训）。
- 每条消息停在终态：训完 `ready`、炸了 `failed` + 原因、行已删则确认后丢弃。
  超时按不可重试处理（写操作）。
- 训练输入在 worker 里现读：当前批次的全部 `usable` 事件，剔除人工排除
  （按自然键 join），按 §2.4 现算特征。⚠ 样本不足（可用 < 30）直接 `failed`
  并说清缺多少——训一个几条样本的模型比不训危险。

## 5. 对外接口

沿用 `ac:view` / `ac:manage`；`/api/v1/platform/*` 的兜底路由规则已覆盖，
不动种子。

```
GET    /api/v1/platform/ac-models                 （?room_id= 过滤）
POST   /api/v1/platform/ac-models                 （建模并入队训练，202）
GET    /api/v1/platform/ac-models/{id}            （含指标、出处、过期提示位）
PATCH  /api/v1/platform/ac-models/{id}            （name/description/serving_sets；改组合就地重汇总，不重训）
DELETE /api/v1/platform/ac-models/{id}
POST   /api/v1/platform/ac-models/{id}:retrain    （重训入队，202）
GET    /api/v1/platform/ac-models/{id}/predictions（折外逐条，页码分页，可按组合过滤）
POST   /api/v1/platform/ac-models/{id}:predict    （试算：组合+各台读数 → p10/p50/p90 + p₀ + 可靠性）
POST   /api/v1/platform/ac-models/{id}:recommend  （推荐：全部服务组合同台比 → 排序 + 推荐标）
GET    /api/v1/platform/rooms/{room_id}/live-readings（房间绑定机组的实时读数，ac:view，外库不可达 503 不出旧数据）
```

- `:predict` 纯计算：读工件、算特征、出数，不碰外库。`at` 可省（默认当下，
  决定时段/季节特征）；`idle_minutes` 可省（省了记 NaN）。
- ⚠ 对**服务组合之外**的组合试算不拒绝，但结果上带 `is_in_serving_sets: false`
  ——外推要说清楚，不替用户挡住。
- `/predictions` 用**页码分页**而不是游标：折外预测是训练时整体替换的**有界
  快照**（api-contract §5.1 的「有限集合」），不是追加型时序流；总数可知，
  页码直选对用户更顺手。

### 5.4 推荐口径

`:recommend` 与 `:predict` 同一套起始条件入参，但不选组合——组合就是被比的
对象：每个服务组合各出 p10/p50/p90 + 瞬时达标概率 p₀ + 专属/兜底标注。

- **排序**：p50 快者优先 → 再比 p90 → 最后少开机组优先（同样快就选省电的）
  → set_key 兜底保证确定性。第一名带 `is_recommended`。
- ⚠ 服务组合里含**工件不认识的机组**（训练后新加的）：该组合跳过不出数——
  静默给数比拒绝危险；全部被跳过则 422 提示重训。
- 权限：与 `:predict` 一样是纯计算读操作，auth catalog 窄规则（priority 906）
  放给 `ac:view`。**部署后要重跑 auth seed。**
- 校验：组合必须是房间机组的非空子集且去重；`half_life_days ≥ 7`；房间必须
  有当前批次才能建模（没数据训什么）。

## 6. 页面

`/hvac/models` 进主导航（`ac:view`），详情 `/hvac/models/:id`。

- **列表**：房间、名称、状态、样本量、MAE、区间覆盖率、训练时间；`ac:manage`
  给「新建 / 重训 / 删除」。训练中的行轮询刷新。
- **新建**：选房间 → 组合覆盖度列表（复用 startup-batches 的覆盖度数据，带
  可用事件数）勾选服务组合 → 半衰期（默认藏在「高级」里）→ 提交。
- **详情**：
  - 评估卡：**热行口径为主**——样本（热/零拆开）、热行 MAE / MedAE / 覆盖率 /
    区间宽度 + 可靠性、判零率 / 判出率；整体 MAE 退居次要。
  - 按组合表：每个服务组合的热行 n 与 MAE / 覆盖率 / 宽度、判零率、可靠性。
  - 预测-实际散点（折外）：x=实际 y=p50，对角线为理想；零行淡化显示，
    区间没盖住的点标警示色。
  - 逐条表：**页码分页（页码直选 + 每页条数）**，时刻、组合、实际、
    p50 [p10, p90]、误差；按组合过滤。
  - 实时测试弹窗：取房间实时读数（`/rooms/{room_id}/live-readings`）当起始
    条件 → 全部服务组合同台比，第一名带推荐标。形态、状态机与缺数/不可达的
    处置以 `docs/AC_MODEL_UI_DESIGN.md` §4 为准。
  - 出处条：训练用的数据窗口、批次指纹是否已过期、特征版本是否已更新。
- ⚠ 训练中**详情继续显示上一次的评估**并挂进度提示——同 §5「重算期间显示
  上一批次」的理由：半份/空数据比旧数据危险。

## 7. 本期有意没做

- **不做定时自动重训**。数据每月更新一次量级，人按「数据已更新」提示点重训
  足够；加调度器是在没有心跳的系统里多养一个会静默失败的组件。
  ⚠ 后来确实加了两个调度器（预测下发与每日增量），但它们各自带着看得见的
  心跳：前者把「上次发成没成」记在配置行上、后者把跳过与追加分成两个 event。
  这一条的顾虑没变，变的是「有没有心跳」这个前提。
- **不做模型版本历史**。一个模型只留最近一次成功训练；要对比就建两个模型。
  版本链等「谁在什么数据上比谁好」成为真实问题再说。
- ~~**不做在线自动预测**（开机时自动出「预计几点达标」）。它需要常驻的最新帧
  订阅与推送面，是另一期的实时功能；本期试算面板覆盖「现在这样开能几点达标」
  的人工问法。~~ **已在 [`AC_PUBLISH_DESIGN.md`](AC_PUBLISH_DESIGN.md) 落地**：
  worker 每分钟取一次实时读数、推荐一遍、把结果写进 OPC UA 点位。当时顾虑的
  「常驻订阅面」最后没有出现——下发是拉不是推，一分钟一拍现读现算。
- **不出「建议开哪几台」**。那是反问题（给定目标时间选组合），要在预测可信
  之后才有意义。
