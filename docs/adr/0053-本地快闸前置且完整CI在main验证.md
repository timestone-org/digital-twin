# ADR-0053：本地快闸前置，完整 CI 在 main 验证

- 状态：已采纳
- 日期：2026-09-08
- 影响范围：工程协作规范、本地验证与 main 合并流程
- 调整：[ADR-0050](0050-PR不设统一变更行数上限.md) 中的合并前验证要求

## 背景

主流水线只在 `main` 的 push 上运行，覆盖静态检查、真库测试、覆盖率、契约、构建与
供应链。过去要求每次合并前再用 act 本地完整复制同一条流水线，单次耗时长，并与
main 上的正式运行重复；linked worktree 还可能因为容器只拿到 `.git` 指针文件而
无法解析真实仓库，产生与代码无关的失败。

本地快闸已经覆盖结构、格式、Lint、类型、静态契约和 OpenAPI 同步。日常改动再补上
修改范围内的定向测试，可以在提交前挡住大多数低成本问题。真库、覆盖率与产物验证
继续由 main 上的正式流水线负责，交付者监控到终态。

## 决策

1. 日常提交前必须运行 `scripts/ci-local.sh --fast`，并运行与修改范围相称的定向测试。
2. `scripts/ci-local.sh --all` 不再是每次合并的前置条件。迁移、鉴权、并发、跨服务
   契约、CI 自身改动等高风险变更，或任务明确要求时可以选跑。
3. 改动合并并推送到 `main` 后，交付者必须监控该次 push 对应的正式 CI 到终态。
4. 正式 CI 失败时，先依据失败作业和日志定位根因，再决定修复或回滚；不在根因未明
   时预先猜改，也不把红灯拖到下一个无关提交。
5. 需要在合并前使用 GitHub 真运行器验证分支时，使用 `workflow_dispatch`，不造空
   提交触发流水线。

## 理由

快闸前置保留了最短反馈环：格式、类型、结构和静态契约仍在提交前发现。完整流水线
集中到 main 后只运行一次，减少本地容器启动、依赖安装和重复测试的等待，同时最终
结论来自与生产分支一致的正式运行器。

监控不是可选步骤。把完整验证后移到 main，意味着交付者必须跟住对应运行；否则只是
把合并前等待换成无人处理的主干红灯。

## 代价

- 某些只有真库、覆盖率或构建才能发现的问题会在进入 main 后才暴露。
- CI 失败时主干会短暂处于红灯状态，需要立即判断修复还是回滚。
- 连续合并必须控制节奏，确保每次 push 对应的运行能够被识别和处理。

## 否决的替代方案

### 每次合并前强制 `--all`

它能更早发现完整流水线问题，但把同一轮验证在本地 act 与 GitHub 上重复两次，日常
成本过高；linked worktree 的仓库解析差异还会制造环境性失败。

### 只跑快闸，不监控 main CI

这会让真库、覆盖率、构建与供应链检查变成无人负责的事后告警，与“main 永远可发布”
冲突。
