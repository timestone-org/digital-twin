# ADR 0046：台账重算给 `PREDICT` 加一趟批量相位，命不中一律现算

- 状态：已接受
- 日期：2026-09-03

## 背景

[ADR-0045](0045-模型本体走对象存储的二进制通道.md) 让树模型能上线之后，它们与
线性那一族在台账里走的是同一条路：求值器逐行调 `model.predict(args, at)`。

对线性模型这没问题——一行就是几个乘加。对树模型不是：一次 `sklearn.predict`
即使只算一行，也要付一次 Python → C 的往返、一次数组构造、一次树遍历的调度，
大约 100 µs。一张两万行的台账重算一次就是**两秒钟纯开销**，而同样这两万行整批
算只要几十毫秒。差着两个数量级。

问题在于**求值器是逐行的，而且必须逐行**：`PREV` 与窗口函数要看已经算完的前几
行，所以第 n 行的输入依赖第 n-1 行的输出。一次把所有行的实参收齐再算——这条路
在这个结构下走不通。

## 决策

**一、加一趟**收集相位**：空跑一遍全部行，把每一次 `PREDICT` 调用记下来，一次
算完存进备忘；然后真实相位再跑一遍，读备忘。**

备忘的键是 `(公式标识, 实参元组, 这一行的时刻)`——**这次调用的全部输入**。

**二、备忘是纯函数的记忆，因此批量相位只加速、不改结果。**

这是整个决策的支点。命中与否与行序无关；真实相位里**命不中的照样逐行现算**。
于是无论批量相位收齐了多少、收漏了多少，算出来的数与不开批量时逐字节相同。

收得漏是有的，而且是意料之中的：某条公式列的 `PREDICT` 实参若引用了另一条
`PREDICT` 算出来的列，收集相位那一轮拿到的是 `None`，记下来的实参就不是真实参。
真实相位那次调用命不中，落回逐行现算——**慢，但对**。

否掉的三种：

- **一次收齐所有行的实参再算**——`PREV` 与窗口让第 n 行依赖第 n-1 行的输出，
  收不齐。
- **让备忘只按实参建键、不带时刻**——带时间特征的模型会拿上一行的答案填这一行。
  数看着完全正常。
- **收不到就给空**——那就成了一个与行序有关的静默缺陷：同一批数据，某几格有数
  某几格没有，取决于公式之间的引用关系。

**三、只有模型自己说「整批算划算」时才跑收集相位。**

`BatchAnalysisModel.should_batch`。通道 A 的模型如实回答「不划算」：为它们多跑
一趟收集是净亏——多一遍全表求值、多一次整列聚合查询，换回来的是几个乘加。

**四、收集那一趟不写记录。**

它算出来的那些 `None` 是占位。落库的表现是「重算一次先把整列清空」，而中途失败
就把用户的数据留在了清空状态。

**五、推理链上一步都不许增删行，由契约测试钉住。**

整批算是把 n 行一次喂进整条推理链。任何一步增删行都会让答案与行错位——而错位
不报错，每一行都拿到了一个看着正常的数。目前 `CHANGES_ROW_COUNT` 的算子恰好
都是 `ENABLED_IN_SERVING=False`，但那是巧合，得钉住。

## 影响

- `apps/dataset/formula/analysis.py` 多一个协议 `BatchAnalysisModel` 与一个
  `ModelMemo`；主协议 `AnalysisModel` 一个字没改——绝大多数模型不必知道有这回事。
- `CompiledModel.predict_many` 把整条推理链在一张 n 行的帧上跑一遍。实参有空的
  那些行**不进批**：它们的答案恒为 `None`，混进去会让缺失值参与拟合链上的变换，
  算出一个看着正常的数。
- 收集相位多一次 `load_whole_stats` 查询。只在真有通道 B 模型绑上去时才付。
