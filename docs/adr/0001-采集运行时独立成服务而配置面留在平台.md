# ADR-0001：OPC UA 采集的运行时独立成服务，点位配置面留在平台

- 状态：已采纳
- 日期：2026-08-10
- 影响范围：`server/services/collector-server/`、`server/services/platform-server/apps/opcua/`、`server/domain/timeseries/`

## 背景

系统要从工厂的 PLC 采集点位数据。围绕 OPC UA 有两类完全不同的东西：

**运行时**——建立并维持与 PLC 的会话、订阅节点、接收数据变更、写实时快照与历史归档。它必须部署在能路由到工控网的机器上；它按 PLC 分片扩展而不是按 QPS；它的典型故障是重复会话击穿 PLC 的会话上限，而工业设备的会话上限往往只有个位数。

**配置面**——点位服务器与节点的增删改查。它是普通的表 CRUD，按 QPS 扩展，挂了不会影响任何物理设备。

两者的运行时边界毫无重叠，该分开。真正的问题是**这条线切在哪**。

## 决策

**只有运行时进 `collector-server`，配置面留在 `platform-server`。**

| 进 `collector-server` | 留在 `platform-server` |
|---|---|
| 连接池、会话、订阅、采样循环 | 服务器与节点的 API、CRUD、模型、权限码 |
| 地址空间浏览的执行端 | 地址空间浏览的发起端 |
| 快照写入、归档缓冲、归档落库 | 快照读取、历史查询、实时计划构建 |
| 命令总线消费端 | 命令总线发送端 |

`collector-server` 只认识**采集计划**：服务器端点 + 节点集合 + 采样参数。它不认识大屏、绑定、台账。

## 理由

### 一、把配置面一起搬走，会造出一条反向 RPC

删除一个点位节点必须先问"还有没有大屏绑着它"；构建实时下发计划必须读绑定表。这两个问题的答案都在 platform 的表里。

配置面跟着运行时走，意味着 collector 要为每次删除守卫、每次计划构建反向调用 platform——形成**双向 RPC 依赖**。两个服务互相同步等待对方，是分布式死锁与级联超时的标准配方，而它换来的好处是零。

配置面留在 platform，这些查询就是普通的进程内调用。**这条切线让跨服务的调用方向保持单向。**

### 二、单向依赖是 collector 能被搬走的前提

collector 对 platform 的依赖只有一条：拿到采集计划。这条依赖走内部 API + Redis 变更通知，不碰 platform 的数据库。

于是 collector 具备了"整体挪到工控网侧独立机器"的能力——它需要的只是能访问 Redis 与一个 HTTP 端点。**如果它直连 platform 的 schema，这个能力就没有了**，因为数据库连接会成为跨网段的第二条硬依赖。

### 三、浏览走命令总线，不走共享连接

浏览 PLC 地址空间必须由持有连接的进程执行。platform 发命令、collector 执行并回值，经 Redis 命令总线。

替代方案是让 platform 也建一条 PLC 连接——那会**在物理设备上叠加会话**，正是第一条判据要避免的事。命令总线多一跳延迟，但浏览是低频的人工操作，用户感知不到。

## 代价

- 采集计划是一份需要维护一致性的下发数据：platform 改了点位配置，collector 必须及时收到。用"全量计划 + 版本号 + 变更通知"承担，collector 侧按版本号判断是否需要重拉，而不是靠增量消息（增量丢一条就永久错位）。
- collector 启动时若拿不到计划，**必须空转并响亮告警，不允许用过期缓存猜**——用错的计划采数据，比不采更糟：它会写出看似正常的错误历史。
- 浏览操作多一跳 Redis 往返。
