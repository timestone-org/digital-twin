# ADR 0043：解析后端分「本地库解」与「外部服务解」两路，外部一期只留端口

- 状态：已接受
- 日期：2026-09-03
- 落地：2026-09-03 接上了第一路外部后端 `MineruBackend`（`parsing/mineru.py`）。
  决策六里那句「一期一个实现都没有」自此是历史，其余决策一字未改——接它确实
  只加了一个实现文件、装配里读一格配置、一条契约测试，没有动任何调用方。
  ⚠ 一处**当时没料到**的收尾：`accepted_suffixes()` 与 `external_for()` 原先
  各带一个「空元组」缺省值，而三个调用点都不传参——于是「接了却不生效」
  在类型上完全合法。现在那个形参是必填的，漏传是类型错误。

## 背景

[ADR-0033](0033-知识来源与解析按注册表分层.md) 把解析层的扩展点定成「一种格式
一个 `DocumentParser`」：显式白名单、同步、阻塞、由调用方扔进进程池。这个形状
对本地库解那一路是准的——`python-docx` / `openpyxl` / `markdown-it-py` 都是在
本进程里烧 CPU 的库。

但工业现场真正难解的是扫描件与复杂版面，而那一档的方案（MinerU、
PaddleOCR / PP-Structure 这一类）**根本不是这个形状**：

| | 本地库解 | 外部解析服务 |
|---|---|---|
| 一个后端吃几种格式 | 一种（顶多一族） | 多种，且名单由它自己说了算 |
| 跑在哪 | 本进程 | 另一个进程 / 另一台带 GPU 的机器 |
| 是什么活 | 阻塞的 CPU | 网络 IO |
| 多久回 | 毫秒到秒 | 几十秒到几分钟 |
| 回什么 | 直接就是块序列 | markdown + 版面 JSON |
| 失败长什么样 | 这份文件解不动 | 那边此刻不可达 / 回了解不开的东西 |

硬把它塞进 `DocumentParser`，第一件坏掉的事就是「解析是阻塞 CPU、必须进进程
池」这条口径：一个 `async def parse` 混进同一个 Protocol 之后，那句注释与
`run_in_executor` 里那一行就同时是错的，而**没有任何一处会报错**——把外部后端
交给进程池，pickle 会先在一个看不懂的地方炸；忘了 `await`，一个协程会被当成
`ParsedDocument` 一路带到切块层。

## 决策

**一、扩展点分两级。** `ParserBackend` 只回答「这一路后端认哪些原件」
（`name` / `suffixes` / `media_types`），往下扩两个：

```python
class DocumentParser(ParserBackend, Protocol):
    def parse(self, raw: RawItem) -> ParsedDocument: ...          # 同步、阻塞、进进程池

class ExternalParserBackend(ParserBackend, Protocol):
    async def parse_remote(
        self, raw: RawItem, timeout_s: float
    ) -> ParsedDocument: ...                                       # 异步、网络 IO、必须有超时
```

⚠ **两个方法故意不同名**。同名的话，把外部后端当本地的调用会拿到一个没
`await` 的协程当 `ParsedDocument` 用，而那既不是类型错误也不是运行期异常——
它只表现为「这份文档解出来是空的」。不同名之后，接错线在装配那一步就是
`AttributeError`。

**二、两路后端产出同一个 `ParsedDocument`。** 外部服务回的 markdown + 版面
JSON，**在那一路后端的实现里**翻成带 `locator` 的 `Block` 序列（版面 JSON 里
的页码进 `locator.page`，markdown 的标题层级进 `locator.path`），翻不动就抛
`ExternalParseFailed`。

⚠ 不许为了接外部后端把产出放宽成一坨 markdown 字符串。那条缝
（ADR-0033 决策三、四）是「加一种格式 / 换一个后端」与「改切块策略」解耦的
全部依据：放宽之后，切块层要么各认各的格式，要么退化成定长切；而 `locator`
一旦在这里丢掉，后面任何一层都补不回来——表现是答得头头是道却指不出出处。

**三、挑后端的判据显式且只有一处。**

- 候选名单 = **已配置的外部后端**（按注册序）→ **本地后端**（按注册序）。
- 每一路里都是先按后缀、再按 media type，先到先得（与 ADR-0033 同一条规矩）。
- 外部那一路没配就没有候选，于是整条链路与「没有这一层」逐字相同。

外部排在本地之前，是因为接一路外部解析服务的动机就是让它接管它更擅长的那几种
格式；接了却不生效等于白接，而那件事在界面上看不出任何异常。

**四、accept 名单是两路的并集。** `accepted_suffixes()` 摊平两路并去重，
界面照它下发。接了一路能吃 PDF 的后端之后，上传面必须当场收 PDF——否则那一路
接了也用不上。

**五、两条口径的运行期约束不同，写在端口上。**

- 本地那一路：同步、阻塞、**必须**由调用方扔进进程池；`parse_local()` 是模块级
  函数，因为进程池只传得动 picklable 的东西。
- 外部那一路：**每次调用必须有超时**（runtime-resilience §2），实现自己守住
  `timeout_s`，管线外面再包一层 `asyncio.timeout` 兜底——一个不守约的实现会把
  整条消费循环占死，而现象仍是「队列不动了」。
- 两路都**不自动重试**：摄取那条链只有人按「重新解析」那一层负责重试
  （runtime-resilience §4、KNOWLEDGE_BASE_DESIGN §1.2）。外部服务此刻不可达
  与这份文件解不动，在管线里都写成 `failed` + 一句人话。

**六、一期外部那一路一个实现都没有。** `EXTERNAL_BACKENDS` 是空元组，
`/capabilities` 的 `parsing` 一格如实报「本地装了哪几路、外部接了哪几路、
没接的原因」。

⚠ **不留半吊子 stub。** 一个「看着能用、调下去报奇怪错」的占位比缺席更糟：
缺席能被能力面如实答出来，而占位会让界面写着「接了 MinerU」、用户传上去拿到
一句谁也看不懂的错。

## 理由

- **会变的那一维要放在最外面。** 三年后「本地用哪个 Python 库解 docx」大概率
  还是那一个，而「这套部署有没有一台带 GPU 的解析服务」在每个现场都不一样。
- **两条口径的区别是运行期的，不是风格上的。** 一个是 GIL 之内的 CPU，一个是
  跨机的网络 IO；混成一个签名之后，这两条约束就只剩注释在维持，而注释不是闸门。
- **`ParsedDocument` 是这一层唯一对外的东西。** 它稳住，后面四层就不用知道这
  一份是本地解的还是 MinerU 解的。

## 后果

- 接一路外部后端 = 一个实现文件（HTTP 客户端 + 把上游产出翻成块序列）+
  `EXTERNAL_BACKENDS` 里一行 + 装配里把配置读出来 + 一条契约测试。**不动任何
  调用方**，也不动切块以后的任何一层。
- 那个实现要自己承担三件事：守住 `timeout_s`、把任何上游失败翻成
  `ExternalParseFailed`、把 markdown + 版面 JSON 翻成带 `locator` 的块。
  这三件事写在端口的 docstring 上，不是靠人记。
- 多了一格配置 `KNOWLEDGE_EXTERNAL_PARSE_TIMEOUT_S`，一期没有生效路径。
- 一期没有 PDF 这件事因此有了两条出路：加一个本地 `PdfParser`，或者接一路外部
  后端。两条都只加文件，不改调用方。

## 备选与为什么不选

| 备选 | 不选的理由 |
|---|---|
| 让 `DocumentParser.parse` 变成 `async` | 本地那三路是纯 CPU 的活，声明成 async 之后它照样阻塞事件循环，而「必须进进程池」这条口径连个落脚的地方都没有了 |
| 一个 Protocol、两个方法名都叫 `parse` | 把外部后端当本地的调用会拿到一个没 await 的协程当 `ParsedDocument` 用，而那不报错——它表现为「这份文档解出来是空的」 |
| 外部后端产出 markdown 字符串，切块层自己再解一遍 | `locator` 在这一步就丢了，后面任何一层都补不回来；而切块层要认「这一坨是哪种 markdown」，等于把格式知识又漏回去 |
| 一期就写一个 MinerU 客户端 | 没有真实端点可验，写出来的是一份猜的线形；而半吊子实现会让能力面报「接了」，比缺席更难查 |
| 本地优先、外部只当兜底 | 那样接了外部服务也只对「本地解不了的格式」生效，而它真正的价值是把扫描件与复杂版面从「解得动但解得烂」变成「解得对」 |
| 摄取管线自动重试外部服务 | 一条链路只有一层负责重试（runtime-resilience §4），而那一层是人按的那一下；管线自动重试会与人按的那一下相乘 |
