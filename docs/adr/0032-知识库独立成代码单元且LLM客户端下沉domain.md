# ADR 0032：知识库独立成第 7 个代码单元；LLM 与嵌入客户端下沉 `server/domain/llm/`

- 状态：已接受
- 日期：2026-09-01

## 背景

要建一个知识库：可扩展的文档解析、AgenticRAG 检索，且后期要能从别的系统取知识。
落点有三个候选，而它们的差别不在目录，在**要不要复制一份 LLM 客户端**。

- 助手（`ai-assistant`）手里握着全仓唯一一套 LLM 与嵌入客户端：模型注册表、
  两路模型来源、断路器、思考过程的抽取、凭据加密。
- 助手的上下文文档写死了它是**纯消费方**：只写自己的 `assistant` schema，
  业务数据一律经 platform 的 HTTP 面拿。
- 知识库是**数据属主**：它拥有文档原件、块、向量与来源配置，还要跑重活
  （解析、嵌入）与长任务（外部系统同步）。
- 服务之间不许互相 import（CLAUDE.md）；`domain/*` 的入场券是「已有 ≥2 个服务
  真实消费」。

## 决策

**一、知识库是新的代码单元 `server/services/knowledge-server/`。**
端口 8009、schema `knowledge`、服务段 `/api/v1/knowledge`、错误码领域号 23。

**二、它有两个部署单元：`api` 与 `worker`（`KNOWLEDGE_APP_ROLE`）。**
与 platform 的三角色同一口径（ADR-0002）——重活用运行角色，不为它另建服务目录。

**三、LLM 与嵌入客户端下沉到 `server/domain/llm/`。**
下沉的是**无状态的调用面**：模型来源的 Protocol、OpenAI 兼容的对话与嵌入客户端、
断路器、错误分档。**不下沉**的是助手自己的东西：技能、工具、提示词分层、
会话与凭据的 ORM。

⚠ `domain/*` 不许含 ORM 模型、CRUD 与依赖注入件（结构闸 `check_domain_has_no_persistence`
扫 `DeclarativeBase` / `mapped_column` / `Mapped[` / `Depends(` / `APIRouter`）。
所以模型凭据那张表**留在助手**，`domain/llm` 只收一个「给我一个可用的客户端」的工厂。

**四、知识库不回调助手，助手也不代理知识库。**
两边都直接用 `domain/llm`。让知识库经助手去调模型的话，就是一条双向同步 RPC
（ARCHITECTURE §6 明令禁止），而且助手的会话语义在这条路上没有任何用处。

**五、`platform_server/stream.py` 上移到 `server/lib/stream/`。**
它的文件头本来就写着「零业务名词，第二个消费方出现时可以整体上移到 `lib`」——
知识库的摄取队列就是那第二个消费方。

**六、落地顺序是：知识库骨架先落，`domain/llm` 的抽取后落。**
反过来做的话，抽取那一刻只有一个消费方，不满足 domain 的入场券。

## 理由

- **知识库是数据属主，助手是纯消费方，这两件事放在一个上下文里会互相污染。**
  把知识库塞进助手，最先坏的是助手那条「不读别人的库、不当越权通道」的不变式——
  而它是助手唯一的安全条款。
- **重活与对话的扩缩曲线完全不同。** 一次批量摄取会把进程池占满几十分钟，
  而对话要求毫秒级响应。同一个部署单元里，前者的抖动直接表现为后者的超时。
- **抽 `domain/llm` 不是为了优雅，是因为别无选择。** 服务之间不许互相 import，
  而知识库的 `agentic` 策略与嵌入都要调模型。剩下的路只有复制一份——
  复制品会漂，而漂的表现是「同一个端点，助手调得通、知识库调不通」。
- **两个部署单元而不是两个服务**：扩缩与故障隔离在部署层解决，这是本仓已有的口径。

## 后果

- 全仓变成 **7 个代码单元 / 11 个部署单元**。`CONTEXT-MAP.md`、
  `ARCHITECTURE_MICROSERVICES.md`、compose、边缘配置、CI 作业矩阵、
  `check_migrations_touch_one_schema_only` 的 `known` 集合都要跟着加。
- `domain/llm` 的抽取是一次**机械搬迁 + 助手侧改 import**，横跨两个服务，
  与「PR 只碰一个服务」正面冲突。走 `check_pr_policy` 的 `[机械]` 豁免，
  并且**不许在同一个 PR 里改行为**——机械移动与行为改动混在一起时，评审会跳过其中一半。
- 助手的 `CONTEXT.md` 要改：`llm/` 那一层不再住在它这里。
- 多一套服务的样板（settings/container/deps/app/Dockerfile/alembic/openapi）。

## 备选与为什么不选

| 备选 | 不选的理由 |
|---|---|
| 塞进 `ai-assistant` 的 `apps/knowledge/` | 助手从纯消费方变成数据属主，那条不变式是它唯一的安全条款；且摄取的重活会把对话的延迟拖垮 |
| 塞进 `platform-server` 的 `apps/knowledge/` | platform 一行 LLM 代码都没有，嵌入客户端得从零接；且它已有 6 个 app，是全仓最大的一个 |
| 知识库复制一份 LLM 客户端 | 复制品一定会漂，而漂的表现是「同一个端点，一边通一边不通」，从外面看不出是哪一边错了 |
| 知识库经助手的 HTTP 面调模型 | 双向同步 RPC，ARCHITECTURE §6 明令禁止；且助手的会话语义在这条路上毫无用处 |
| 先抽 `domain/llm` 再建服务 | 抽的那一刻只有一个消费方，不满足 domain 的入场券「≥2 个服务真实消费」 |
