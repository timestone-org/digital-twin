# ADR-0007：达标时长建模走专用管线，而非通用建模流水线

- 状态：已采纳
- 日期：2026-08-13
- 影响范围：platform-server 的建模模块、worker 角色、`scikit-learn` 依赖、
  `platform` schema 三张表

## 背景

要对开机事件做训练与预测（`docs/AC_MODEL_DESIGN.md`）。参考实现
（`../DigitalTwinBK/apps/modeling`）是一套通用算子流水线：用户在画布上摆
「取数 → 预处理 → 特征 → 切分 → 训练 → 评估」的图，5500 行，算子只有线性回归。

两条路：把那套通用流水线搬过来再补算子，或为达标时长这一个问题写专用管线。

## 决策

**专用管线。** 特征、切折、加权、算法、评估全部写死在代码里，页面上可配的只有
业务参数（服务组合、半衰期）。

理由：

1. **用户要回答的是一个固定问题**（这样开机多久达标），不是「让现场人员自由
   建模」。通用画布把 19 个特征的口径决定权交给每次操作的人，两个模型的差异
   从此说不清是数据变了还是有人少勾了一列——参考实现自己就有这个缺陷
   （目标列曾散在三处配置）。
2. **口径要能被闸门守住**。特征算法在代码里才有 `FEATURE_VERSION` 纪律与
   逐行评审；在图的 JSON 里就只能靠人眼。
3. **规模差一个量级**：专用管线连测试千余行；通用流水线 5500 行起步还没包含
   分位数回归、时序折、加权这些本问题真正需要的件。

同时从参考实现**抄走**它对的部分：工件存库不落盘（每个副本都要能加载）、
加载前验摘要与 sklearn 版本、不可服务必须给人话原因。

## 后果

- 换一种算法 = 改代码发版本，不是页面上换个节点。接受：算法选择是工程决策，
  不是运营操作。
- `scikit-learn` 进 platform-server 依赖（约 30 MB）。只装在它一个服务里，
  镜像层可接受。
- 将来若真出现「现场要自己摆流水线」的需求，本模块的特征/评估函数可以直接
  改包成算子——两条路不互斥，先专用后通用的迁移成本是包装层，反向则是重写。
