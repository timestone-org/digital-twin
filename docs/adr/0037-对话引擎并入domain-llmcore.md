# ADR 0037：对话引擎并入 `server/domain/llmcore/`，助手与知识库各接各的工具

- 状态：已接受
- 日期：2026-09-02

## 背景

知识库要一个**独立的对话页**：多轮、模型自己决定检索几次、会话可管理、歧义时
反问用户并给出选项让他选、工具后期还要往上加。

这些能力在 `ai-assistant` 里**已经全部存在**，而且是按 ADR-0029 三件套装的：

- 回合编排 `planning/turn.py`（438 行）：模型 ↔ 工具循环，直到给出答复或停下来
  等浏览器；
- 工具注册表 `tools/`：显式元组注册、按名字分派、规格在装配期取快照；
- `user.ask` 是一个**客户端工具**——模型要调它，浏览器渲染选项，用户选完把结果
  送回同一个回合。这正是「反问并让用户选」；
- SSE 输出层、上下文分层（短期窗口 / 窗口外折叠 / 常驻提示词 / 每轮重建的状态块）、
  附件解码、按权限收窄、失败步骤的如实回报。

于是问题不是「能不能做」，而是**这套引擎要不要再写一遍**。三条路：

1. 知识库自建一套 —— 把最难的 2700 行复制一份，此后同一个缺陷要修两处，
   而漂了不报错；
2. 知识库复用 `ai-assistant`，只加一个工作面 —— 最省事，但知识库的会话会存进
   `assistant` schema，权限与发布周期也跟着助手走，两个产品被焊死；
3. 抽成 domain 包，两边各接各的工具。

`domain/*` 的入场券是「已有 ≥2 个服务真实消费」（CLAUDE.md），这次正好是第二个。

## 决策

**一、通用对话引擎下沉 domain，并入既有的 `llmcore` 包。**

下沉的是**与产品无关的对话机制**：回合编排与回合内流动的类型、工具注册表与分派、
客户端工具那一路的机制、SSE 事件的摊平、上下文分层的端口与实现（历史窗口、
窗口外折叠、每轮重建的状态块）、按权限收窄、反思验证、附件解码。

**不下沉**的是各家自己的东西：具体的工具与其规格（大屏 / 点位 / 台账 vs 知识库
检索）、常驻提示词、工作面清单与按面挑工具、技能清单、模型档配置、长期记忆仓储。
附件解码与「工作面快照」也留在助手：知识库对话一期不做附件，而 domain 包的
入场券是「已有 ≥2 个服务真实消费」——只有一个消费方的东西下沉是提前抽象。

⚠ **原本打算新开一个 `chatcore` 包，被结构闸推翻了，而它推翻得对。**
`domain/*` 之间**不许互相 import**（CLAUDE.md，`check_structure_python` 里的
`check_domain_stays_flat`），而回合循环要 `llmcore` 的 `ModelChoice`——且必须是
**同一个类型**，否则助手的 `GuardedModel` 与 `Responder` 这个结构化协议在
pyright strict 下对不上。绕法有两种（各自复制一份类型别名、或把它们推进
`lib`），两种都比接受事实差：**没有任何消费方会只要其中一个**——助手两个都用，
知识库将来也两个都用。那它们本来就是一个包。这条规则的用意正是不让 domain
长出依赖图，而它在这里逼出了正确答案。

**二、它不碰 ORM，持久化走端口。**

CLAUDE.md 明令 `domain` 不许含 ORM 模型与 CRUD。这条不是阻碍，它正好切在天然的
缝上——实测 `turn.py`、工具注册表、SSE 输出层**一行 ORM 都不碰**，只有
`history.py` 与 `summarize.py` 引了 `ChatMessage`，而它们只做「库里的一行 ↔
模型认的一条」的转换。

因此 `llmcore` 定义 `SessionStore` / `MessageStore` / `StepStore` 三个 Protocol 与
一个只读的行形状协议；**每个服务用自己的 ORM、自己的 schema、自己的迁移**去实现
它们。会话表因此各存各的：助手的在 `assistant`，知识库的在 `knowledge`。

⚠ 这一条同时挡掉了「两个产品共用一张会话表」那个看似省事的做法：跨 schema 外键
是三条禁令之一（ADR-0003），共表则等于把两个服务的发布周期绑死。

**三、知识库的对话默认跨**全部**库，可由用户收窄：工具带 `base_id`，模型在范围
内自己挑。**

用户拍板。代价是模型可能挑错库而用户看不出来，故**每条召回必须显式标注它来自
哪个库**——答案里的角标要能指回「哪个库 / 哪份文档 / 哪个位置」，三者缺一不可。

⚠ 「跨全部库」是**缺省**不是不变式：范围钉在会话上、由用户自己收窄，收窄之后
工具层硬过滤（[ADR-0044](0044-对话检索范围钉在会话上.md)）。收窄到几个库之后
仍然是跨库的，所以上面那条角标要求一个字不变。

**四、知识库这一路工具是一个 provider，不是写死的分支。**

`kb.list_bases` / `kb.search` / `kb.read_chunk` 装在一路 `KnowledgeTools` 里，走
`llmcore` 的注册表。后期加工具 = 加一个文件 + 注册表一行 + 一条契约测试。

⚠ 知识库对话**不调服务端那条 `:ask`**：`:ask` 是一次性的服务端编排（改写→召回→
评分→补检→合成），而对话里由模型自己决定检索几次——两条编排叠在一起会互相抢，
且用户看不出这一轮到底是谁在决定。`:ask` 保留给不要对话的调用方。

## 后果

- 抽取那一步必须**行为逐字不变**：助手正在生产上跑，它的用例是这次抽取唯一的
  安全网，一条都不许改口径。
- `llmcore` 从此有两个消费方，改它要同时对两边负责——这正是 domain 包该有的
  约束，也是它与「随手抽个 utils」的区别。
- 前端同理：`features/ai` 里的 SSE 帧解析、回合驱动、反问队列是通用的，知识库
  对话页复用它们，而不是再实现一遍。
