# ADR-0018：闸 2 与幂等存储收进 `lib`，服务差异靠参数注入

- 状态：已采纳
- 日期：2026-08-17
- 影响范围：`server/lib/auth/`、`server/lib/web/`、`server/lib/idempotency.py`、`server/services/platform-server/`、`server/services/opcua-server/`
- 相关：[ADR-0004](0004-server分三层且domain承载领域共享包.md)、[`agents/config-and-secrets.md`](../agents/config-and-secrets.md)

## 背景

闸 2（读边缘注入的签名身份头、按权限码放行）此前有**六份**实现：
`platform-server` 的五个功能模块各一份，`opcua-server` 一份。
逐字节 diff 过——`require()` 与 `get_caller()` 在这六处完全相同。

支撑它的两件公共件寄居在业务模块里：

- `caller_from_headers` 住在 `apps/hvac/services/`，被五个功能模块 import；
- `IdempotencyStore` 住在 `apps/dashboard/services/`，采集面也在用。

于是依赖图上有几条纯属历史原因的 `apps/* → apps/*` 边：**采集要从大屏借幂等
存储、从空调借身份头解码**。`apps/collect/deps.py` 自己写了一段注释交代这件事。

跨服务那一份也已经漂了：`IdempotencyStore` 在两个服务里存回放结果时，
一边 `model_dump(mode="json", by_alias=True)`、一边不带 `by_alias`；
身份头解码一边验不过返回 `None`、一边抛五种不同的消息。

安全语义有六个副本，意味着**修一处漏五处**是默认结局，而这一处的漏修是权限
漏洞，不是显示问题。

## 决策

**三件公共件按"零项目名词"收进 `lib`，服务差异一律靠参数注入。**

| 件 | 落点 | 服务差异怎么表达 |
|---|---|---|
| 身份头解码 | `lib/auth/edge_headers.py` | 无差异；`decode_caller` 是纯函数 |
| 闸 2 的 FastAPI 装配 | `lib/web/authdeps.py` | `build_auth_deps(signing_secret_of=…, service_key_of=…, message_of=…)` |
| 幂等存储 | `lib/idempotency.py` | `IdempotencyStore(cache=…, namespace=…)` |

服务根各留一个薄绑定：`platform_server/deps.py`、
`opcua_server/apps/instance/deps.py`。功能模块的 `deps.py` 从此只写自己的上下文——
`collect` 留 `SourceContext` 与三档写上下文，`dashboard` 留 `ValidationContext`，
`hvac` 留 `Dispatcher`，`assets` 留对象存储，`runtime_params` 留配置对象。

### 一、判不可信时给出**稳定的原因字面量**，消息归调用方

`decode_caller` 返回 `IdentityOutcome(caller, reason)`，`reason` 是五个稳定字面量
之一。platform 沿用它那句统一的话；opcua 按 reason 映射回它原来的五句。

合成一句"身份无效"会让现场自己猜是哪一种，而五种的处置完全不同：重新登录 /
必须经网关访问 / 联系管理员查签名密钥。**收敛实现不等于收敛诊断。**

### 二、幂等键的命名空间是参数，且**取值不许随手改**

两个服务共用一个 Redis，命名空间把键分开——不分开的话，同一个端点名撞上同一个
幂等键会互相返回对方的结果。

⚠ 现有取值（`platform:dashboard`、`opcua`）逐字保留。它们是**已经在 Redis 里的
键前缀**，改一次等于把一批还在有效期内（24h）的幂等记录一次作废，而作废的后果
是客户端的一次重试真的又执行了一遍——建两个大屏，或者向 PLC 写两次。
两个 `IDEMPOTENCY_NAMESPACE` 常量各带一行这个告诫。

`by_alias` 的分叉按**带别名的那一侧**统一：不按别名存，回放出来的就是另一套
字段名，而调用方只在重试那一次看到它。

### 三、测试面跟着实现走

`IdempotencyStore` 此前在 opcua 侧暴露了 `replay` / `claim` / `remember` / `release`
四个方法，**只有测试在用**——那是"测试穿过接口"的典型形态。合并后只保留
`run_once` 一个入口，原来的三条用例改成通过它来触发同样的路径（并发同键、
失败后重试）。身份与闸 2 的用例整体挪进 `lib`，服务侧留集成层那几条。

## 理由

### 一、"零项目名词"这条铁律恰好把三件都判进 `lib`

判据是"把它整个目录拷到一个完全无关的新项目里，还成不成立"。
签名头验签、权限码判定、幂等回放——三件都成立。它们进不了 `domain`
（那一层的入场券是"带项目名词且 ≥2 个服务消费"），只能是 `lib`。

### 二、参数注入是本仓已有的表述，不是新发明

[`config-and-secrets.md`](../agents/config-and-secrets.md) 早就写着"产品差异靠参数
注入"。`signing_secret_of` / `namespace` / `message_of` 三个参数，正好覆盖了六份
副本之间**全部**的真实差异——这本身就是"它们本该是一份"的证据。

### 三、安全代码的重复，代价不对称

六份显示逻辑漂了，后果是界面不一致；六份鉴权逻辑漂了，后果是有一个端口不设防。
这类代码的重复不该按"重复行数"衡量，该按"漏修一处的后果"衡量。

## 代价

- **闸 2 变成跨包依赖**：改它要动 `lib`，而 `lib` 的改动影响全部服务。补偿是
  `lib` 的覆盖率水位最高（行 ≥95%），且两个服务的集成用例都真跑一遍 401/403。
- **`build_auth_deps` 在模块顶层调用一次**：它是纯函数、不连任何外部资源，
  与"禁 import 副作用"不冲突；`check_python_runtime` 的判据（顶层不许出现连库、
  起线程）照样通过。
- **依赖注入件的单元测试更难写**：`require_service_key` 现在从 `Request` 上取
  组合根，用一个 `SimpleNamespace` 假容器过不了 `isinstance` 那道守卫。
  正解是这几条用例本就该测 `lib` 的 `build_auth_deps`（那里可以注入任意取密钥
  函数），服务侧靠集成用例守自己的接线——本次照此调整。
