# ADR-0005：实时通道只做通道，网关职责全部归边缘

- 状态：已采纳
- 日期：2026-08-10
- 影响范围：`server/services/realtime-hub/`、`docker/nginx/`

## 背景

系统需要两种基础设施性质的能力：

- **边缘网关**：TLS 终结、按前缀路由到各服务、前置鉴权、限流、静态资源发布。
- **实时通道**：维持大量 WebSocket 长连接、管理订阅关系、把服务端产生的消息扇出给客户端。

这两件事都带有"所有流量都经过它"的气质，很容易被合并成一个叫"网关"的自研服务。一旦合并，它会持续吸附本不属于它的职责：路由规则、限流策略、API 聚合、"顺手在这里查一下权限"。

## 决策

**两件事由两个东西承担，且都不许长出业务知识。**

| | 承担者 | 做什么 | 明确不做什么 |
|---|---|---|---|
| 边缘网关 | `edge-gateway`（nginx） | TLS、按前缀反代、`auth_request` 前置鉴权、限流、静态资源、对象存储只读代理 | 任何需要读库才能回答的事 |
| 实时通道 | `realtime-hub` | 连接管理、订阅关系、消息扇出 | 读任何业务表 |

`realtime-hub` 的名字就是它的职责边界：它是 hub，不是 gateway。

## 理由

### 一、前置鉴权属于边缘，不属于自研服务

每一个受保护的请求都要过一次鉴权判定。把它放在边缘（nginx 的 `auth_request` 子请求打 auth-server），意味着：未通过的请求**根本到不了业务服务**，业务服务不必各自实现鉴权中间件，也不会因为某个服务漏挂中间件而开一个洞。

放在自研网关里，就要自己实现连接池、超时、重试、熔断、大并发下的转发——重新实现一遍成熟的反向代理，换来的只是"我们有一个网关服务"。

### 二、通道服务一旦读业务表，就不再是通道

看板实时发布需要读绑定表、按绑定计划求值、再把结果推给订阅者。把这件事放进 `realtime-hub`，它就同时是通道和业务——名为通道、实为业务的服务，会让每一次业务改动都变成对全站连接层的改动。

因此看板发布器归 `platform-server` 的 `publisher` 角色（[ADR-0002](0002-重任务用运行角色而非独立服务.md)），推送经 `realtime-hub` 的服务端推送端点。

代价是每次推送多一跳（publisher → hub → 客户端）。这一跳换来的是：**通道服务永远不需要认识业务表**，业务改动永远不会威胁到连接层的稳定。

### 三、服务级推送端点不用用户权限码

`realtime-hub` 的推送端点是服务→服务通道，调用方是别的微服务而不是浏览器。用用户权限码表达"只有服务能调"表达不了——权限码挂在人身上，而这里要挡的正是"任何人"。

因此它用**服务级密钥**（逐字比较，`hmac.compare_digest`），并且 **fail-closed**：密钥未配置时一律拒绝。未配置说明这条通道还没接好，此时放行等于把"向全站广播"暴露给任何拿到路径的人。

## 代价

- 边缘配置（nginx）是一份需要与服务清单同步维护的产物：新增服务要加 upstream 与 location。它必须像代码一样进版本库、进评审、有变更验证，不能靠登机器改。
- `auth_request` 让每个受保护请求多一次内部子请求。auth-server 的 `/verify` 因此是全站最热的端点，必须有专门的性能下限断言。
- 推送多一跳。可接受，因为实时推送的延迟预算在百毫秒级，而一跳内网往返在毫秒级。
