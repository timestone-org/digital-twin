# ADR 0016：复杂 config 段由清单声明的整页子编辑器接管

- 状态：已接受
- 日期：2026-08-15

## 背景

大屏模块的属性面板是**泛型渲染**的：读 `configSchema`，按 `ConfigField.type` 查控件
注册表，两列表单自动铺出来。新增模块不用写一行表单代码就有完整属性面板
（DASHBOARD_DESIGN §5.2），这条是模块体系能扩展的前提。

数字孪生打破了这个前提。它的 `twin` 段是一整棵树：模型摆放、部件与它们指向的
模型节点名、锚点、信息牌与牌上的字段、箭头、能量流的路径、视点、以及五类元素
各自的显隐与距离规则。里面既有 `Vec3` 元组，也有互相引用的 id（信息牌引锚点、
能量流引一串锚点、视点切换控件引视点），还需要一个 3D 视口才能配得准——
「这个锚点该放哪」不看着模型是定不下来的。

两列通用表单表达不了这些。而现状是：没声明 `fields` 的 object 字段降级成 JSON
编辑框，用户在一个文本框里手写这棵树。

## 决策

**一、清单上加 `subEditor` 声明，属性面板只读声明。**

```ts
subEditor?: {
  configKey: string    // 被接管的 config 键
  routeName: string    // 跳哪个路由
  label: string
  hint?: string
}
```

属性面板遇到 `subEditor.configKey === field.key` 的字段，画入口按钮，不画通用控件；
其余字段照旧泛型渲染。

**二、绝不按模块类型分支。** 编辑器与运行时里不许出现 `if (type === 'twin-view')`。
这条已有 grep 闸门守着（`dashboard-module-literals.contract.spec.ts`）。

**三、子编辑器是独立路由，参数是 `dashboardId` + `nodeId`，直接落库。**
落库走大屏的整树替换，与大屏编辑器同一个写入口、同一套乐观版本。

**四、`subEditor` 不进 `module_types.json`。** 它纯粹是编辑器的事，
服务端读了没有用处——与 `component` / `preview` / `configPresets` 同一档。

## 理由

- 按类型分支的代价不是这一处难看，是**第三方模块永远开不出自己的子编辑器**，
  而且既不报错也不失败。声明式让这个能力对所有模块一视同仁。
- 子编辑器另开一页而不是弹一个大 modal：3D 视口要占满屏才配得动，
  而且深链一个孪生场景（发给同事「你看这个锚点」）是真实需求。
- 落库而不是把结果交回大屏编辑器的内存草稿：草稿的恢复是要问用户的
  （「发现本地草稿，要恢复吗」），从子编辑器回来时弹这个框会让人莫名其妙。

## 后果

- ⚠ **`routeName` 写错既不报错也不失败**，用户看到的是「点了没反应」
  （`router.push` 抛的异常没人接）。由 `sub-editor-routes.contract.spec.ts`
  逐条核对：路由存在、路由接得住两个参数、`configKey` 真在这个模块的 schema 里。
- ⚠ 子编辑器落库会推进大屏行版本，大屏编辑器手里的**本地草稿随即失效**
  （`readDraft` 按 `basedOnUpdatedAt` 比对，对不上就静默丢弃）。所以入口在跳转前
  必须处理脏状态：脏着先问、存成功才跳，存失败留在原地。这条由
  `useSubEditorEntry.test.ts` 守。
- 一个模块只能有一个子编辑器段。真出现第二段时把 `subEditor` 改成数组，
  属性面板那一处判断跟着改即可，声明式的形状不用动。

## 备选方案

- **把 `TwinConfig` 摊成几百个 `ConfigField`**：字段数量本身不是问题，问题是
  数组内嵌数组（牌 → 字段）、元组（Vec3）与跨集合引用（牌 → 锚点）这三样
  通用控件表达不了，而且没有 3D 视口配不准坐标。
- **保留 JSON 编辑框**：能改，但没人改得对；一个逗号写错整段配置回到缺省。
- **弹全屏 modal 而不是新路由**：省一个路由，但失去深链，且 modal 里再开
  素材选择器就是第二层弹窗。
