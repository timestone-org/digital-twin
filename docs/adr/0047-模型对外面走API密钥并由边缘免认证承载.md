# ADR 0047：模型对外推理面走 API 密钥，由边缘一条免认证 location 承载

- 状态：已接受
- 日期：2026-09-04

## 背景

模型训出来、发布成版本之后，本系统内部有两条用法：绑成公式进台账，或在建模页
里试算。系统**外**一条都没有。

而现场的实际形态是：MES 要在排产前问一句「这批料按这个工况，能耗大概多少」；
EMS 要按预测值提前调负荷。它们是独立部署的第三方系统，既没有本系统的会话，也
不该为了调一次预测去走一遍登录。

## 决策

**一、「部署」是新的一等概念，与「绑定」并列而不是替代。**

```
模型版本 ──┬── 绑定 ─────▶ 公式库条目 ──▶ 台账列        （进系统内）
           └── 部署 ─────▶ 一个 URL + 一组 API 密钥      （出系统外）
```

两者都钉一个不可变的版本，换版本都是显式动作。互不依赖：可以只绑不部署、
只部署不绑、也可以都有。

**二、URL 段是部署自己的 `code`，不是版本 id。**

换版本时第三方不必改代码。反过来做的话，每次重训都要通知每一家对接方改配置,
而漏通知一家的表现是那家一直在用一个旧模型——没有任何一侧会报错。

**三、凭据是 API 密钥，由 platform-server 自己核对，不进 auth-server。**

密钥是**业务资源**：挂在部署上、由建模模块的 `modeling:publish` 管、跟着部署
一起删。放进 auth-server 就要在两个服务之间同步一张表的生死，而 `/verify` 是
全站每个请求都要过的热路径——为一个低频端点给它加一条分支不划算。

安全性由「面足够小」来保证：这条前缀之下**只有两个端点**，都在
`api/open_models.py` 一个文件里，都以同一个鉴权依赖开头，并配一条契约测试逐个
扫描。漏挂一个的表现是那条路径整个匿名开放，而它不会报任何错。

**四、匿名可达性由边缘那条免认证 location 提供，照 `public-dashboards` 的先例。**

```nginx
location ^~ /api/v1/platform/open-models/ {
  limit_req zone=open_model burst=40 nodelay;
  client_max_body_size 256k;
  proxy_pass http://$platform_upstream$request_uri;
}
```

auth-server 的规则表里单列一段，并写明「真正的匿名可达性由边缘那条免认证
location 保证」——那条规则本身是「任意已登录用户」，不是匿名放行。

**五、密钥只存摘要，明文只在铸出来那一次的回执里出现。**

`sha256(明文)` 加前 12 位可见前缀。明文是高熵随机串不是口令，不需要慢哈希；
但比对必须 `compare_digest`——普通 `==` 逐字节短路，比对耗时会泄漏前缀。

「找回密钥」这件事在设计上就做不到。做得到就意味着存在一个能读出全部密钥的接口。

**六、拒绝的时候一个字都不多说。**

不存在、不属于这个部署、已撤销、已过期——四种失败**同一个状态码、同一句
「密钥无效」**。分开报等于送一个枚举接口。

同理，部署 `code` 不存在与「存在但停用了」的区分只对**带对了密钥**的人可见：
鉴权在状态检查**之前**。

**七、三层配额，缺一层就绕得过去。**

| 层 | 按什么限 | 谁执行 |
| --- | --- | --- |
| 边缘 `limit_req` | 来源 IP | nginx |
| 服务侧令牌桶 | **密钥** | platform-server |
| 单次行数上限 | 每个部署自己配 | platform-server |

只有边缘那层的话，一把密钥换台机器就绕过去了；只有服务侧那层的话，拿错密钥
猛打的流量根本到不了限流那一步就已经把连接池占满了。

按密钥而不是按部署：一个部署可以发给几家对接方，一家把量打满不该把别家挡住。

**八、对外只回预测值与告警。**

不回列统计、不回训练区间的具体数值、不回任何台账编码。超出训练区间**照样给
数**，但要标注出来——树模型尤其要说，它不外推，区间之外一律给边界值，而那个数
看着完全正常。

**九、调用记录只记行数、耗时与状态码，走自己的事务。**

不记入参与出参：那是业务数据、可能含敏感值，而且体积会压垮这张表。排查具体一次
调用靠 `trace_id` 去结构化日志里找——日志里同样不记入参。

⚠ 记录必须走**自己的**事务：请求那条在出错时整个回滚，靠它记的话，「这次调用
失败了」恰恰是唯一记不下来的一种。⚠ 反过来，记不上也**不许**把这次调用拖垮——
数已经算出来了。

⚠ 鉴权与限流那几种失败**不记**：它们还没归到任何一个部署的账上，而记下来正好
给了拿错密钥猛打的人一个撑爆这张表的办法。

**十、一期跑在 `api` 角色，不新开部署单元。**

推理在通道 A 上是几次乘加，通道 B 上是一次 sklearn 往返，配额已经把量级压住。
触发另开 `ROLE=serving` 的条件现在就写下来，免得以后凭感觉拍：①对外调用的 P99
开始影响同副本上的业务接口；②单个部署的配额需要超过 600 次/分钟；③需要给对外
面单独的伸缩策略或单独的网络入口。

## 影响

- 三张新表 `modeling_deployments` / `modeling_api_keys` / `modeling_call_logs`，
  纯扩展步。版本外键是 `RESTRICT`——还有第三方在调的版本删不掉。
- `modeling-deployments` 管理面沿用 `modeling:view` / `modeling:publish`，不新增
  权限码：开一个对外服务的爆炸半径与发布同级。
- 边缘两份配置（Linux 模板与 Windows 那份）都要加那条 location 与那个
  `limit_req_zone`。⚠ 只改一份的表现是「一边通、一边 401」。
