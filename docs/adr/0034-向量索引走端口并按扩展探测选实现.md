# ADR 0034：向量索引走端口；bytea 是持久真相，pgvector 是可选的加速物化

- 状态：**部分作废**（决策二至五由 [ADR-0045](0045-向量与关键词索引改为硬依赖.md)
  取代；决策一的端口分层保留，只是每个端口从此只有一个实现）
- 日期：2026-09-01

## 背景

助手的长期记忆把向量存成 `bytea` 并在应用层算余弦（ADR-0030），理由是那张表的写入
来源只有两个显式工具、条数天然有限。知识库不是——一个库几百份文档、几万到几十万块，
全表扫描算余弦的表现是「检索越来越慢」，而它不会报任何错。

实测本机的库（`timescale/timescaledb:latest-pg17`）里 `vector 0.8.1` 与 `pg_trgm`
都在 `pg_available_extensions` 中、尚未 install。但**现场那台库有没有，尚未确认**，
而且将来换一台库时这件事会再问一遍。

直接在迁移里 `CREATE EXTENSION vector` 并建 `vector(N)` 列有两个硬问题：

1. 迁移是 compose 的前置作业。目标库装不上扩展时迁移当场失败，**整栈起不来**。
2. `CREATE EXTENSION` 是**库级**动作，落点在 `public`，而结构闸明令
   「一个服务的迁移不许动别的 schema」。

## 决策

**一、检索走 `VectorIndex` 与 `KeywordIndex` 两个 Protocol，各带两个实现。**

| Protocol | 首选 | 回退 |
|---|---|---|
| `VectorIndex` | `PgVectorIndex`（`vector(N)` + HNSW） | `BruteForceIndex`（bytea + 应用层余弦） |
| `KeywordIndex` | `TrgmKeywordIndex`（`pg_trgm` GIN） | `LikeKeywordIndex`（`ILIKE` 扫描） |

**二、`kb_chunk_vectors.embedding` 是 `BYTEA`，全环境都有，由主线迁移建。它是真相。**

**三、加速结构不进 alembic。** `kb_chunk_vectors_pgv(chunk_id, embedding vector(N))`
与它的 HNSW 索引由一步**显式的运维动作**建（`python -m knowledge_server.index --enable`，
向量与关键词两路一起开），
文档里写清。装不上就不装，主线 schema 全环境一致。

**四、服务启动时探测，据此选实现；探测结果如实进 `/capabilities`。**
⚠ 这是把「装没装扩展」变成**取值**而不是**行为**（config-and-secrets §5：
环境差异只能是取值不能是行为，禁 `if env == "prod"`）。

**五、回退是明说的，不是悄悄的。** 走在 `BruteForceIndex` 上时，
`/capabilities` 与管理页上都要写着「未启用加速索引」。悄悄退化的表现是
「检索有点慢」，没有任何一处会报错，于是没有人会去查。

**六、`embedding_model` 与 `dimensions` 钉在**库**上，不钉在块上。**
一个库里混两种维数算不出有意义的余弦，而表现只是「召回忽然变差了」。

## 理由

- **迁移失败等于整栈起不来，这个代价不能为一个可选加速付。** 把 `CREATE EXTENSION`
  挪出迁移之后，最坏情况从「服务起不来」降级成「检索慢一点，且界面上写着为什么」。
- **双份存储是有意付的代价。** 1536 维一条 6 KB，十万块就是两份 1.2 GB。
  换来的是**重建索引不必重新调一遍嵌入 API**——那是真金白银，而且重建索引这件事
  一定会发生（换索引参数、修数据、迁库）。
- **向量单独一张表**：检索先按向量收窄再回表取正文，而列表页永远不需要向量。
  挂在 `kb_chunks` 上的话，一次「列一下这个库有哪些块」就把几千条 6 KB 一起拖出来。
- **端口而不是配置分支**：`if pgvector_enabled:` 会散布到每个查询点，
  而其中一处漏判的表现是「有时候检索结果不一样」。

## 后果

- 部署手册多一节「启用加速索引」，且它是**可选**的一步。
- 启用/停用加速索引要有一条把 bytea 物化进 `vector` 列的补数路径（worker 批处理，
  不在迁移里回填——迁移里禁止回填数据）。
- 两套实现都要有真库集成测试，否则「回退那一路」会长期没人跑过。
- 换嵌入档 = 整库重嵌，界面上要明说，且要挡在 `knowledge:manage` 后面。

## 备选与为什么不选

| 备选 | 不选的理由 |
|---|---|
| 迁移里 `CREATE EXTENSION vector` + `vector` 列 | 目标库装不上时迁移失败，而迁移是 compose 前置作业——整栈起不来 |
| 只用 bytea + 应用层余弦（沿用 ADR-0030） | 几万块起就是全表扫描，表现是「越来越慢」且不报错 |
| 条件迁移（探测到扩展才建列） | 同一个 alembic head 在不同环境结构不同，是最难查的一类漂移 |
| 独立向量库（Qdrant/Milvus） | 多一个部署件要运维；且双写一致性要自己兜，漏一半的表现是「删了的文档还能被检索到」 |
| 向量列挂在 `kb_chunks` 上 | 列表页把几千条 6 KB 向量一起拖出来，只表现为「有点慢」 |
