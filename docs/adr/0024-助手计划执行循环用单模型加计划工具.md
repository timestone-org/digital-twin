# ADR 0024：助手的计划执行循环用单模型 + 计划工具，不建 planner/executor 双层

- 状态：已接受
- 日期：2026-08-25

## 背景

助手一期是单回合 ReAct：用户说一句，模型想一轮、调几个工具、给个答复。
多步任务（「把这屏十二个卡片全绑上点位再排整齐」）在这个形态下要么被模型一口气
做到步数上限，要么中途停下来把没做完的当成做完了——用户看不见它打算做什么、
做到了哪一步。

主流 agent（Claude Code 等）的通行形态是：先产出一份 TodoList，逐项执行、
逐项勾掉，界面全程可见。

## 决策

**一、计划是一个服务端工具，不是一个独立的编排阶段。**

`plan.write` 整份重写计划（标题 + 项列表，每项带状态）。模型被提示词纪律要求：
多步任务先写计划再动手，每完成一项立刻更新。不新建 planner/executor 双模型、
不给回合图加计划节点。

**二、计划落库在 `chat_sessions.plan_json`，每轮渲染进系统提示词。**

api 角色无状态（ADR-0023），计划放内存续跑就丢。渲染时当前项单独点名——
「你正在做第 N 项：…」就是每一步的专属提示词，不需要另一个模型来生成它。

**三、计划快照走新 SSE 事件 `plan`，前端渲染成可勾选的清单。**

事件集从 5 个扩到 6 个，仍是闭合集合。快照整份下发，前端无需增量合并。

**四、`turn.done` 到达而计划未完时，前端自动续推，有上限。**

模型停下而活没干完，浏览器代用户说一句「按计划继续」（默认最多 3 次），
用户随时能停。上限之外还没完，就停下如实交待。

**五、设计类计划的收尾项固定是截图验收。**

布局/外观类任务的最后一项是 `dashboard.capture` 自检；不满意就往计划里
追加修正项，看过图才许收尾。

## 理由

- **单模型 + 计划工具在回合边界上是零侵入的**：客户端驱动的 POST/SSE 循环、
  `awaiting_client` 待续、混批先跑服务端——全都不用动。planner/executor 双层
  则要把「计划到一半停下来等浏览器」这种状态再发明一遍。
- **计划渲染进提示词，比「给每步现生成一段提示词」可靠**：后者是把上下文
  切碎再拼回去，每一步都可能丢掉前几步刚查到的东西；前者天然带着全部工具结果。
- **整份重写（TodoWrite 式）比增量更新可靠**：增量要 id 对齐与合并语义，
  模型在这两件事上的错误率远高于「把整份列表再说一遍」。
- **自动续推放在前端**：服务端续推需要它自己再造一个「用户说继续」的消息，
  等于服务端替用户说话；前端发起则与既有回合协议完全同构。

## 后果

- 事件契约两侧同步四处：`events.py`、`api/advance.py` 分帧、
  `contracts/assistant.ts`、`turnRunner.ts`——契约测试跟着扩。
- `chat_sessions` 加一列可空 JSONB（扩展步）。
- 提示词多一段常驻的计划纪律（约 150 字）与一段计划快照（活跃时才有）。
- 计划纪律管不住模型乱写计划的场合，靠 `plan.write` 的入参校验兜底
  （≤30 项、状态闭合、最多一项 in_progress）。

## 备选与为什么不选

| 备选 | 不选的理由 |
|---|---|
| planner/executor 双模型分层编排 | 与客户端驱动的回合边界正交性差；每步重拼上下文丢信息；成本翻倍 |
| 计划放 `chat_steps` 逐条落库 | 计划是「当前工作状态」不是审计事件；步骤表已如实记录了每次 `plan.write` 调用 |
| 增量式计划工具（add/update/remove 一套） | id 对齐与合并语义把错误面做大；整份重写一次说清 |
| 服务端自动续推（图里加循环） | 服务端替用户说话；且一条流会长到边缘超时，拆成多次推进反而稳 |
