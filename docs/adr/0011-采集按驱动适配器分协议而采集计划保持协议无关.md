# ADR-0011：采集按驱动适配器分协议，采集计划与归档保持协议无关

- 状态：已采纳
- 日期：2026-08-14
- 影响范围：`server/services/collector-server/`、`server/services/platform-server/apps/collect/`、`server/domain/timeseries/`

## 背景

一期只采 OPC UA，但现场迟早要接 Modbus TCP、MQTT、以及厂商私有的 HTTP 轮询接口。
问题不是"要不要支持多协议"，而是**第二个协议进来时，改动落在哪里**。

有两种走法。一种是先把 OPC UA 写到底，等第二个协议出现时再抽象——代价是那时
`collector-server` 的每一层都已经拿着 `NodeId`、`DataValue`、`StatusCode` 说话，抽象要动全部代码，
而"动全部代码"意味着这件事永远不会发生，最终结局是复制一份采集器出来。

另一种是现在就划一条缝。缝划错的风险是真实的：过早抽象常常抽出一个只有一种实现能满足的接口。
但这条缝有个可靠的判据——**归档表里存的是什么**。历史宽表里没有 `NodeId`，只有
"某个点位在某个时刻的值"。既然落地形态与协议无关，那么从"值离开驱动"那一刻起，
后面的整条管道就都与协议无关。

## 决策

**协议知识只允许存在于驱动（driver）内部。驱动之外的一切——采集计划、快照、归档、状态、命令总线——都只认识协议无关的点位。**

### 一、驱动接口

`collector-server` 定义一个驱动接口，每种协议一个实现，注册进驱动表：

```
connect(source)              建立并维持一个数据源会话
subscribe(points, on_value)  订阅一组点位，值变化时回调
read(points)                 一次性读取
write(point, value)          下发写值（带幂等键）
browse(node_path)            浏览地址空间（协议不支持时明确报"不支持"，不返回空列表）
close()                      释放会话
```

一期只有 `OpcuaDriver` 一个实现。**接口不为未来的协议预留字段**——预留的字段没有实现能验证它，
到真接第二个协议时，它多半是错的。接口只覆盖 OPC UA 已经需要的能力，
第二个驱动进来时按实际差异调整接口，那时有两个实现可以互相校验。

`browse` 是唯一一个"某些协议根本没有"的能力（Modbus 没有地址空间）。它**不允许**用返回空列表表示不支持——
空列表和"这台设备确实没有节点"分不开，会让配置界面静默地摆出一棵空树。不支持就抛明确的领域异常，
配置面据此不显示浏览入口。

### 二、采集计划的形状与协议无关

计划是 platform 下发给 collector 的唯一输入（[ADR-0001](0001-采集运行时独立成服务而配置面留在平台.md)）。它的形状是：

```
数据源：id、protocol、endpoint、凭据引用、连接参数
点位：  id、node_key、数据源 id、采样参数、协议寻址串（address）
```

`address` 是**对驱动不透明的字符串**：OPC UA 里是 `ns=2;s=Temp1`，Modbus 里是 `holding:40001`，
MQTT 里是主题。计划的加载、比对、版本判断都不解析它，只有对应驱动解析。
这样一来，新增协议不改计划的表结构、不改计划下发、不改 collector 的调度骨架。

### 三、`node_key` 是全系统的点位标识，且不含协议

归档表、Redis 快照、大屏绑定、前端取数，一律用 `node_key` 指代一个点位。它的口径与拆分规则
定在 `server/domain/timeseries/`，由 collector（写）与 platform（读）共同消费——这正好满足
[ADR-0004](0004-server分三层且domain承载领域共享包.md) 的 domain 入场券（≥2 个服务真实消费）。

**`node_key` 里不许编码协议名。** 一旦编码了，同一个物理测点从 OPC UA 换成 Modbus 采集，
它的历史就断成两段，而这两段本该是同一条曲线。协议是数据源的属性，不是点位的身份。

### 四、归档接口在驱动之上，一份实现服务全部协议

归档管道接收的是 `(node_key, ts, value, quality)` 四元组，不接收任何驱动类型。
因此"每一个数据采集都能归档"不是靠给每种协议各写一套归档，而是**归档只有一套，
它在协议无关的那一侧**。新增协议自动获得归档能力，不需要为它写任何归档代码。

质量位（quality）是协议无关的三档枚举（`good` / `uncertain` / `bad`），由驱动把各协议自己的
状态码映射过来。**不透传原始状态码**——OPC UA 的 `StatusCode` 是 32 位掩码，Modbus 根本没有对应物，
把它存进归档表等于让读侧去认识协议。

## 理由

### 一、缝的位置由数据的落地形态决定，不由代码量决定

判断抽象是否过早，最可靠的问法是"这条缝两边的东西，会不会因为同一个原因一起改"。
驱动内部会因为"OPC UA 的重连语义变了"而改；归档管道会因为"保留期策略变了"而改。
这两个原因从不重合，说明缝划在这里是真实的边界，而不是想象出来的。

### 二、不为未来预留字段，是这条决策能成立的前提

多协议抽象最常见的失败形态，是接口上挂满了"给将来某个协议用"的可选参数，
每个参数只有零个或一个实现真的用它。这类参数无法被测试证伪，只会在第二个实现进来时被发现全都不对。

本决策明确接受"第二个驱动进来时要改接口"。改一个有两个实现的接口是安全的——
两边都会编译失败，改漏了立刻可见；而改一个只有一个实现的接口，是在猜。

### 三、归档在协议无关侧，才谈得上"扩展协议不丢能力"

如果归档写在 OPC UA 的订阅回调里，那么接 Modbus 时"归档"这件事要重写一遍，
而重写出来的那份会在保留期、批量大小、乱序处理上与原来那份微妙地不一致——
这类不一致不会报错，只会让两种协议的历史数据有不同的可信度。

## 代价

- 多一层间接：OPC UA 的值要经过一次到协议无关四元组的转换才进管道。转换本身极薄，
  但它意味着驱动必须把协议特有的信息（`ServerTimestamp` 与 `SourceTimestamp` 的取舍、
  状态码的档位映射）**在驱动内部就决断掉**，决断的理由要写在驱动里，
  否则后来的人只看到管道侧干净的四元组，不知道信息是在哪一步丢的。
- `browse` 的"不支持"是一条真实存在但一期无人走的分支。它必须有测试覆盖，
  否则接第二个协议时才发现配置面对这个异常没有处理。
- 采集计划的 `address` 不透明，意味着**计划里的寻址串写错，只有到驱动订阅时才会失败**。
  配置面因此必须在保存点位时就调一次对应驱动的校验，而不是等采集起来才报错。
