# ADR-0007：实时通道薄化——开放主题命名空间，订阅授权由推送方声明

- 状态：已采纳
- 日期：2026-08-12
- 影响范围：`server/services/realtime-hub/`、`server/services/opcua-server/`

## 背景

[ADR-0005](0005-实时通道与边缘网关的职责分界.md) 划下了 `realtime-hub` 的边界：只做通道，不读任何业务表。那是边界，不是实现。落到实现上，第一个绕不开的问题是——**hub 凭什么知道一个主题存不存在、谁有资格订阅它？**

现成的参考实现（兄弟项目的自研网关）给出的答案是：每个主题在进程内注册一个 handler 类，或者落一张主题表。这套答案在本仓会当场破掉 ADR-0005。

同时本系统有一类主题是**运行时才产生**的：OPC UA 服务实例由用户在页面上随时新建、随时删除，每个实例一个主题。任何"主题清单写在代码里"的模型都接不住它。

## 决策

**`realtime-hub` 采用开放主题命名空间：它不预置主题清单，不解析标识，不理解任何业务语义。主题由推送方登记，并在登记时声明订阅它所需的权限码。**

1. 主题是字符串，形状照 [`agents/api-contract.md`](../agents/api-contract.md) §10 的 `<域>:<标识>`。hub 只把它当不透明键。
2. 推送方在业务实体创建时调 hub 的内部端点登记主题、声明所需权限码，实体删除时注销。
3. hub 的订阅授权只有一次比较：**用户的权限码集合是否包含该主题声明的码**。没有第二处判断，不回调业务服务。
4. 登记时校验声明的权限码**存在于 auth-server 的权限码目录**（`catalog.py`），不存在即拒绝登记。
5. **订阅未登记的主题一律拒绝**，不允许"先订后建"。开放命名空间的代价是主题名拼错不再是语法错误，若放行未登记主题，一个拼错名字的客户端会安静地永远收不到数据——这是最难查的那类故障，必须在订阅时就响亮失败。
6. 落库只剩两张表：主题声明、用户订阅。两张表都不含业务字段——`realtime` schema 永远不长业务列。

另有三条随之确定的口径：

- 对外仍只有两类接口，照 ADR-0005：客户端 WebSocket 端点（token 走子协议），服务端推送端点（服务级密钥，`hmac.compare_digest` 逐字比较，fail-closed）。
- **长连接的授权是有时效的**：token `exp` 到期前要求客户端走一次 reauth，逾期关连接（close code 4001）；权限上下文按 TTL（默认 60 秒）复核，**权限不再满足时只退订相关主题，不断整条连接**——断整条会把该用户正在看的其它无关主题一起牵连。
- **推送节流归推送方**：按实体维度的合并窗口批推、单条消息的条目上限与分片，都在推送方做。hub 一旦知道"哪些载荷可以合并"，就又长出业务知识了。

## 理由

### 一、handler 注册表里装的就是业务知识

参考实现中，每个主题对应一个 handler 类，类的配置上直接写着它要求的权限码，方法里写着订阅时该做什么。看板那个 handler 走得更远：它在订阅与退订时维护一份 Redis 的"活跃看板 / 观看者"登记，供业务服务判断某块看板还有没有人在看——**这是通道服务替业务服务保管业务状态**。

一旦接受这个模型，ADR-0005 那条"不长业务知识"就只剩一句口号：每加一个业务主题就要往通道服务里加一个认识该业务的类，业务的每一次改动都变成对全站连接层的改动。

### 二、注册表模型接不住运行时创建的实体

handler 写在代码里，意味着新增一个主题要改代码、重新发布。而 OPC UA 实例是用户点一下就有的，主题随实体生灭。

参考实现自己撞上了这堵墙，补丁是给注册表加一层"前缀处理器"——用两个前缀兜住按看板、按服务器维度动态生成的主题。**那个补丁本身就是模型不适配的证据**：真正动态的那部分被迫从注册表里逃出来，而逃出来之后，前缀的优先级与最长匹配又成了新的复杂度。

开放命名空间没有这层结构：动态主题和静态主题是同一种东西。

### 三、授权判断交给推送方，是让 hub 不认识业务的唯一办法

"谁能订阅某个 OPC UA 实例的主题"，这个问题的答案在 opcua-server 手里。要让 hub 自己回答，它就得认识实例、认识实例的权限模型——回到第一条。要让 hub 每次订阅都回调业务服务问一次，就在最热的路径上叠一次跨服务同步调用，还形成 hub → 业务服务的反向依赖。

让推送方在登记时把答案一次性交出来，hub 只做集合包含判断：**判断快、无依赖、无业务知识**。

## 代价

- **授权的正确性被让渡给了推送方。** 某个服务登记主题时若声明了一个过宽的权限码——比如声明成任意登录用户都持有的码——hub 拦不住，它没有判断"宽窄"的依据。
- 唯一的堵法是决策第 4 条：登记时校验权限码存在于权限码目录。它挡得住"编造一个不存在的码"，**挡不住"故意声明一个存在但过宽的码"**。后半截只能靠权限码目录本身的评审兜——目录是全系统权限口径的唯一真源，新增码要同批加规则与契约测试，声明过宽会在那里被看见。**这是评审约束不是机器约束**，必须承认。
- 主题登记是一份要与业务实体保持一致的旁路数据：实体删了而主题没注销，会留下一个谁也推不到、却仍可被订阅的空主题。注销按 at-least-once 处理，且必须有一条对账，不允许静默失败。
- **`seq` 的归属落在 hub 身上，且它的单调性要跨重启成立。** api-contract §10 让客户端靠 `seq` 发现丢帧，而本决策下主题是动态的：主题重新登记、hub 重启、副本切换，任何一处让计数器倒退或归零，客户端都会把它读成丢帧。因此 `seq` 必须随主题声明一起持久化，且重连时由服务端明确告知当前值——客户端不许自己推断。
- hub 不做业务级合并，意味着每个推送方都要各自实现节流。重复实现的成本，换来的是通道层永远不需要知道"哪些载荷可以合并"。
