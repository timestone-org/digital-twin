# ADR-0012：大屏组态以节点为可寻址资源，写入不走整文档替换

- 状态：已采纳
- 日期：2026-08-14
- 影响范围：`server/services/platform-server/apps/dashboard/`、`web/packages/runtime/`、`web/app/src/pages/`

## 背景

大屏是一棵节点树：容器套模块，每个模块有配置与若干数据绑定。参考实现（兄弟项目）
把它的写入面做成了**一个端点**——`PUT /dashboards/{id}/layout`，请求体是完整的 `modules[]`，
服务端删掉全部行再重新插入。

这个形态对"一个人开着编辑器拖控件"是够用的。本仓要接的下一件事不是这个：
用户明确要求后续由 **AI Agent 来设计大屏、连接点位**。同一套接口要同时服务
"人在画布上拖" 与 "Agent 说'把这块 KPI 卡绑到 1 号机组出口温度'"。

把参考实现的这套接口交给 Agent，会撞上五类问题。它们不是缺陷，是那个形态的直接推论：

1. **改一个字段要重传整棵树。** Agent 必须先 GET 全文、在本地改、再 PUT 回去。
   期间任何并发编辑被静默抹掉——而 Agent 与人同时在场正是本功能的目标场景。
2. **绑定 id 每次保存都重新生成。** 参考实现的 `BindingPayload.id` 字段存在但从不被读取，
   每次保存都新建行拿新 `uuid4`。于是"我上一步创建的那个绑定"在下一步就不可寻址了，
   而实时推送的关联键正是 `binding_id`。
3. **读出来的顺序不确定。** 关系上没有 `order_by`，两次导出同一张未修改的大屏不保证逐字节相同。
   Agent 无法靠 diff 判断自己这一步到底改了什么。
4. **写错了不报错，只是静默降级。** `parent_client_key` 指向不存在的键 → 节点悄悄变成顶层；
   模块 `type` 拼错 → 照常入库、前端渲染成兜底块；`source_kind` 拼错 → 永远不产数据。
   全部返回 200。Agent 拿不到任何可据以自我纠正的信号。
5. **模块有哪些类型、每个类型吃什么配置、有几个绑定槽——服务端不知道。**
   这些只存在于前端的 manifest 里。Agent 要生成一张大屏，得先去读前端源码。

## 决策

**节点与绑定各自是可寻址资源，有稳定 id、有独立的增删改端点；整文档替换降级为一个显式的批量操作，且必须带版本断言。**

### 一、写入面

```
POST   /api/v1/platform/dashboards/{id}/nodes            新增一个节点
PATCH  /api/v1/platform/nodes/{node_id}                  改配置/几何/父子/显隐
DELETE /api/v1/platform/nodes/{node_id}                  删除节点及其子树
POST   /api/v1/platform/nodes/{node_id}/bindings         新增一个绑定
PATCH  /api/v1/platform/bindings/{binding_id}            改绑定
DELETE /api/v1/platform/bindings/{binding_id}            删除绑定
POST   /api/v1/platform/dashboards/{id}:replace-layout   整棵树替换（编辑器保存走它）
```

嵌套不超过两层（[api-contract](../agents/api-contract.md) §1），所以 `nodes` 与 `bindings`
在第二层之后升为顶层资源，按 `?dashboard_id=` / `?node_id=` 过滤。

`:replace-layout` 保留，因为编辑器一次拖拽会产生几十处变更，逐条发是错的。
但它**必须带 `expected_version`**，与库里不符即 `409`，不再是无条件覆盖。

### 二、id 稳定

节点与绑定的 id 一经创建**永不改变**，包括走 `:replace-layout` 的整树替换：
替换按 id 做三路比对（新增 / 更新 / 删除），不再"删光重插"。

请求方可以在创建时提供 `client_key`（编辑器的本地稳定键），服务端保证
`(dashboard_id, client_key)` **唯一**——参考实现这里是 `setdefault` 静默"先到先得"，
撞键的第二个节点会被安静地丢给第一个节点的 id。

### 三、顺序确定

节点按 `(parent_id, z_index, id)` 排序，绑定按 `(field_key, id)` 排序，写死在查询里。
两次读取同一张未修改的大屏，逐字节相同。

### 四、写错就响亮失败

以下一律 `400`（`details[]` 指到具体字段，见 api-contract §4.3），不许静默降级：

| 情况 | 参考实现 | 本仓 |
|---|---|---|
| `parent_id` 不存在 | 静默变顶层 | `40010` 父节点不存在 |
| 父子成环 | 不检查，落库 | `40010` 节点树成环 |
| 模块 `type` 未注册 | 照常入库 | `40010` 未知模块类型 |
| `source_kind` 未注册 | 照常入库、永不产数据 | `40011` 未知绑定来源 |
| 绑定的 `field_key` 不在该模块的绑定槽里 | 不检查 | `40010` 该模块没有这个绑定槽 |
| 绑定指向的点位不存在 | 不检查 | `40011` 点位不存在 |

### 五、模块清单是服务端可发现的

```
GET /api/v1/platform/module-types            列出全部模块类型
GET /api/v1/platform/module-types/{type}     单个类型的配置字段与绑定槽
```

返回 `displayName` / `category` / `defaultSize` / `configSchema` / `bindings`，
即前端 manifest 中**与渲染无关的那部分**。

⚠ 这里有一处必须承认的重复：manifest 的单一真源在前端包里（渲染组件与它同处一地才不会漂），
服务端这份是**由前端在构建期导出的产物**，进版本库、由契约测试锁死两侧一致。
不这么做的话，Agent 要么读不到清单，要么服务端得反过来解析前端源码。

### 六、文档格式版本是一个显式字段

大屏文档带 `schema_version` 整数。参考实现靠"坐标是不是整数、在不在范围内"这类结构启发式
判断该不该做坐标迁移——那意味着一份由 Agent 生成的、恰好全是整数坐标的合法文档，
会被误判成旧格式并把每个坐标乘上栅格宽。

`version`（行版本，用于乐观锁）与 `schema_version`（文档格式版本）是两个字段，不许合并。

## 理由

### 一、可寻址性是 Agent 能自我纠正的前提

Agent 的工作方式是"做一步、看结果、决定下一步"。这要求每一步都有**可以指回去的名字**。
绑定 id 每次保存重生成，等于每一步之后 Agent 的全部指针都失效——它只能重新拉全文、
靠位置和字段值猜出"哪个是我刚建的那个"，而位置在无序返回下也不可靠。

这一条对人类编辑器同样是收益：实时推送的 `binding_id` 关联键不再被每次保存打断。

### 二、静默降级对人尚可忍受，对 Agent 是致命的

人拖错了会看见画布上的结果不对，当场改。Agent 看不见画布，它只有响应。
一个返回 200 却把节点悄悄挪到顶层的接口，会让 Agent 认为这一步成功并继续往下走，
错误累积几步之后才在完全无关的地方暴露出来。

**这不是"给 Agent 加个校验"，而是把本来就该有的校验补上**——参考实现把防环的责任
写在模型注释里交给前端，那条注释本身就是这个洞的自述。

### 三、整树替换不该消失，只该被降格

逐节点写不适合编辑器的一次保存：拖动一次可能动几十个节点，发几十个请求既慢又不是一个事务。
所以 `:replace-layout` 保留，只是从"唯一写入面"降为"批量写入面"，并补上版本断言。

两条路径共用同一套校验与同一套 id 保持逻辑，**不允许批量路径走一条更宽松的校验**——
那会让"先用批量接口写进去，再用单条接口读出来"成为绕过校验的后门。

## 代价

- 写入面从 1 个端点变成 7 个，每个都要有权限、校验、审计与测试。这是实打实的成本。
  换来的是每一步可寻址、可校验、可重试。
- **模块清单在两处存在**（前端 manifest 与服务端导出产物），必须有契约测试锁一致性。
  漏了这道测试，Agent 会按一份过期的清单生成配置，而生成出来的配置在前端渲染成空白——
  这正是本 ADR 想消灭的那类静默故障，只是换了个位置。
- `expected_version` 让编辑器必须处理 `409`。参考实现的最后写入者获胜虽然是错的，
  但它从不失败；现在编辑器要真的实现"你的版本旧了，重新加载"这条路径。
- 逐条写入意味着 Agent 可以把大屏改到一个中间的、不自洽的状态（建了节点还没绑点）。
  这是可接受的：大屏没有"必须原子生效"的业务语义，且渲染侧对未绑点的槽本来就有
  `unbound` 状态。真需要原子性时用 `:replace-layout`。
