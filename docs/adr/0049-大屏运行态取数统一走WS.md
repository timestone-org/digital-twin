# ADR 0049：大屏运行态取数统一走 WebSocket，首帧也由发布器推送

- 状态：已接受
- 日期：2026-08-02
- 来源：从 Claude 项目 memory `dashboard-ws-unification` 迁入；实现与 `docs/DASHBOARD_DESIGN.md` §6.1 已核对

## 背景

大屏运行态曾同时存在两套取数路径：OPC UA 快照走 WebSocket，归档窗口与台账值由浏览器每 5 秒发 HTTP 请求。台账产生新行通常还要经过分钟级采集与聚合周期，大多数轮询只会取回同一个值；两条路径也分别维护窗口换算、初值与错误状态，长期会出现口径分叉。

## 决策

大屏**运行态**的全部绑定值统一由 `platform-publisher` 经 `realtime-hub` 推送，包括冷启动首帧。浏览器按 `dashboard_id` 识别帧，按稳定的 `binding_id` 增量合并槽值，不保留“推不到就改走 HTTP”的运行态回退路径。

新观看者出现时，发布器推送一次全量帧；后续更新按数据源节拍与脏信号发送。是否为新观看者按 hub 的连接记录判断，而不是按用户人数或大屏是否已活跃判断。设计态预览仍可走专用 HTTP 端点，但与发布器共用同一组数据源适配器。

数据可见范围以大屏权限为边界：能查看一张大屏，就能看到它绑定并由服务端推送的数据。慢源未到节拍时可以不占本帧；客户端必须保留上一帧中未被本帧覆盖的槽。单帧条目上限必须保留，避免大窗口时序载荷越过 Redis Pub/Sub 的输出缓冲上限。

## 理由与取舍

单一路径让首值与增量、窗口换算、截断标记和错误状态只实现一次，也消除了大量无效轮询。代价是实时通道断开时运行态不会自行改走 HTTP；界面必须把最后已知值标为陈旧或明确显示通道已断开。这样故障是可见的，不会由两套数据口径拼出一张看似正常但含义不一致的大屏。

本决策只约束大屏运行态。管理页查询、编辑态绑定预览以及其它低频 HTTP 读取不在范围内。
