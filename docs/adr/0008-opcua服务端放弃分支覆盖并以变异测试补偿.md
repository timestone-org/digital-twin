# ADR-0008：opcua-server 放弃分支覆盖，以变异测试补偿

- 状态：已采纳
- 日期：2026-08-12
- 影响范围：`server/services/opcua-server/`、[`agents/testing-standard-python.md`](../agents/testing-standard-python.md) §4.1、`.github/workflows/{ci,nightly}.yml`

## 背景

[`testing-standard-python.md`](../agents/testing-standard-python.md) §4.1 要求全仓分支覆盖 ≥75%、增量分支 ≥85%，`coverage-baseline.json` 逐单元棘轮。这条对所有服务一视同仁。

`opcua-server` 的测试必须启动真实的 `asyncua.Server`：会话追踪走的是 `InternalServer` 子类注入这个未文档化的扩展点（[ADR-0006](0006-opcua服务端独立成代码单元.md)、`CONTEXT.md` §5），不真的握一次手就验证不了它还成立；而同源自测本身也不足以证明上位机连得上——这一点已经被一个真实缺陷证实：`set_application_uri` 缺失导致服务器宣告的 ApplicationUri 与证书 SAN 不符，任何真实上位机都会拒绝连接，而不起客户端的测试全绿。

## 决策

**`opcua-server` 单元关闭分支覆盖，只采集行覆盖，且必须以 `COVERAGE_CORE=sysmon` 运行；作为补偿，把它的运行时层纳入 nightly 的变异测试。**

## 理由

### 一、这不是取舍，是唯一可跑的配置

`asyncua` 的标准地址空间由一个约 78000 行的生成函数建起。coverage 的追踪器会被它拖死——**即便 `asyncua` 根本不在 `source` 范围内**。实测（`Server().init()`，本机）：

| 配置 | 结果 |
|---|---|
| 不开覆盖率 | **0.5 秒** |
| 默认追踪器 + 分支 | >200 秒未返回 |
| 默认追踪器 + 仅行 | >200 秒未返回 |
| `COVERAGE_CORE=sysmon` + 分支 | >200 秒未返回 |
| **`COVERAGE_CORE=sysmon` + 仅行** | **0 秒** |

四种组合里只有一种可用。整套用例不开覆盖率是 37 秒，开了之后**单条**起服务器的用例就超过 200 秒不返回。这不是"慢"，是流水线挂死。

⚠ 两个开关是**一对**：`pyproject.toml` 里的 `branch = false` 与 CI 里的 `COVERAGE_CORE=sysmon` 缺任何一个都会挂。两处都写了指向本文的注释。

### 二、被否决的替代方案

**把起真实 Server 的用例排除在覆盖率之外**（另跑一次不带 `--cov`）。分支覆盖对其余部分确实可行——不起服务器的 118 条用例带分支覆盖只要 6 秒。但代价是运行时层里**只被这 45 条用例走到的路径全部计为未覆盖**，于是要么增量覆盖 ≥90% 直接红，要么为了凑数去补一批不启动服务器、因而验不到真东西的用例。用"看起来的覆盖率"换掉"真的验过握手"，方向反了。

**为该服务单独记两条基线**（全量仅行 + 子集分支）。技术上可行，但一个单元两条棘轮会让"覆盖率降了吗"这个问题需要先问"哪一条"，而闸门的价值恰恰在于答案唯一。

### 三、变异测试是更强的替代物，不是安慰剂

分支覆盖回答"这个分支被走到了吗"，变异测试回答"改坏它会不会有用例红"。后者能抓到前者抓不到的那类失败——分支走到了，但断言不足以发现它算错了。

因此 nightly 把 `apps/instance/runtime` 纳入 mutmut。**这段是补偿控制而非锦上添花**：撤掉它，该服务的运行时层就既无分支覆盖也无变异守护。这一点写进了 nightly 的注释里，防止将来被当成可省的慢作业删掉。

## 代价

- **全仓的分支覆盖口径出现一个例外。** §4.1 的"全服务一视同仁"从此有一条注脚，而注脚是会被援引的——本 ADR 的适用范围仅限 `opcua-server`，任何其它单元想关分支覆盖都要另写 ADR 并给出同等强度的实测。
- **变异测试跑在 nightly，不是 PR 闸。** 意味着运行时层的断言质量问题最多晚一天被发现，而不是在 PR 上被拦住。这是慢闸门的固有代价，与 E2E、a11y 同档。
- **`coverage-baseline.json` 里的 `opcua-server.branches` 是 `0.0`**，那不是"分支覆盖崩了"，是根本没采集。⚠ 由此棘轮在分支这一维**对本单元不起作用**：将来任何取值都 ≥ 0。重新打开分支覆盖时必须同时把基线抬到真实水位，否则会静默留下一个永远拦不住任何倒退的维度。
- **失效条件要盯着**：这条决策的根据是上游的病理性交互。coverage 或 asyncua 任何一方修好之后，本 ADR 应当**撤回**而不是沿用——届时把 `branch = true` 改回来、跑一次基线即可。判断方法就是上表：重跑那四种组合，只要"默认追踪器 + 分支"能在秒级返回，本 ADR 即失效。
