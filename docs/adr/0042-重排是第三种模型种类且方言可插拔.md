# ADR 0042：重排是第三种模型种类，线形方言按注册表可插拔

- 状态：已接受
- 日期：2026-09-03

## 背景

知识库的混合检索按名次融合（RRF）给出结果（[ADR-0035](0035-检索编排是策略注册表.md)、
`KNOWLEDGE_BASE_DESIGN` §4.1）。融合解决的是「两路量纲不同」，解决不了「这十条里
哪一条真的答得上这句话」——工业资料里同一台设备的十来段文字彼此高度相似，
向量与关键词都只能把它们一起捞上来。

**重排（rerank）** 就是补这一刀：把 query 与一批候选一起交给一个交叉编码模型，
拿回一份真正针对这句话的相关度。它与已有的两种模型都不一样：

- 不是对话模型：它不回文字，回的是一串分数；
- 不是嵌入模型：嵌入是**每条文档各算一个向量并落库对账**，重排是**一次调用里
  query 与整批文档一起打分、什么都不落**。

而最麻烦的一点是：**重排不在 OpenAI 兼容口径里**。`/v1/chat/completions` 与
`/v1/embeddings` 有事实标准，重排没有——Jina 定的那套形状被 Cohere、TEI、
Xinference、vLLM 一起用着，阿里云百炼则挂在自己的原生面上，路径与请求体都不同。

## 决策

**一、模型种类多一档 `rerank`，与 `chat` / `embedding` 并列。**

目录里登记得出重排模型，用途清单里多一条 `knowledge.rerank`。种类是闭合集合，
四处逐字一致（llmcore / platform 的 `enums.py` / 前端 `@dt/contracts` / 迁移里的
CHECK），由 `llm-shapes.contract.spec.ts` 逐字比。

**重排模型没有维数那一格。** 给它一格的话，读侧会把它当成嵌入模型；而更要紧的是，
**换重排模型不作废任何存量向量**——界面上绝不许把它说成「换了要重建」。

**二、调用侧按「线形方言」挑实现，方言是一张注册表。**

`llmcore/rerank/` 下一副 `ports.py` + `registry.py` + 实现文件（ADR-0029 的三件套）。
一期装两路：

- `jina` —— `POST {端点根}/rerank`，请求体 `{model, query, documents, top_n}`。
  Jina、Cohere、TEI、Xinference、vLLM 都说这一套，故按**线形**命名而不是按厂商——
  按厂商分的话，接第五家时要再抄一遍同一份实现。
- `dashscope` —— 原生 text-rerank 那一套，请求体分 `input` 与 `parameters` 两段，
  回包多包一层 `output`。它的端点根**不是**兼容口径那一个，要在目录里单独建一路
  供应商填原生面的根（「档位即供应商」，[ADR-0040](0040-供应商按接入形态配置且档位即供应商.md)）。

加第三路 = 加一个文件 + 注册元组一行 + 一条契约测试。传输、失败分档与
「解不动的回包算我们自己配错」这几件事在一份共用的调用面里，方言只写自己不同的
那两件事（拼请求体、读回包）。

**方言码是跨服务契约。** 平台侧配得出的与调用侧装了的必须逐字一致；漂开的表现是
「界面上选得中、调用时说不认识」，而两边代码单看都对。同样由前端那条契约用例守。

**三、方言配在供应商上，不配在模型上。**

`llm_providers.options_json` 里的 `rerank_dialect`。方言说的是「打哪个路径、
什么请求体」——它跟着**端点**走。挂在模型上的话，同一路上配两个重排模型就能配出
两套互相矛盾的线形，而只有一套打得通。没配这一格时按默认那一路（`jina`）解，
故存量供应商一行配置都不用改。

**四、知识库多一层 `reranking/`，接进 `hybrid` 与 `agentic`；`naive` 一个字不动。**

- `hybrid`：接了重排就**多召一批**（要 N 条先召 3N，封顶 60 条）再按新分截断。
  只召 N 条的话，重排能做的只有把这几条换个顺序，而它真正的价值是把融合名次里
  排在 N 之外、其实最相关的那一条捞上来。上限是硬的：每条候选的**全文**都随请求
  发出去，一段块按 800 字算，60 条已是四万多字。
- `agentic`：在**合池之后**对着**原问题**排一次，而不是让每条改写式各排一遍。
  几路的分数不是同一个基准，合池之后按它们排序等于按噪声排序；而那笔钱还是按条算的。
- `naive`：基线，也是「召回忽然变差了」时的对照组。在它身上再叠一层就没有对照可言。

**五、这一路只有模型目录一个来源，没有环境变量那一档。**

与对话档、嵌入档不同：重排是新加的，一个存量部署都不是靠环境变量配着它的，
而多一条回退链就多一处「配了没生效」要排查的地方。为此用途面多下发一格
`has_env_default`——界面上「未指定」那一行原本一律写着「沿用该服务环境变量里的
配置」，那句话对这一路是假的，照着它去翻一个不存在的配置项比不说更费时间。

**六、没接就如实不启用；排不成就如实退回，并标注这次没排。**

- 没接：`/capabilities` 的 `rerank` 那一格如实回答，连同「为什么没接」
  （与 `IndexCapabilityOut.reason` 同一条口径，[ADR-0034](0034-向量索引走端口并按扩展探测选实现.md) 决策五）。
  **不**在每次检索的 `note` 里念一遍：那是这套部署的常态而不是这一次的意外，
  每次都念的话，真正的失败反而被淹掉。
- 排不成（端点拒了 / 短路了 / 方言这一侧没装）：**退回融合名次**并把这件事写进
  `note`。重排是排序增强，它挂了不该让用户拿到一句「检索失败」，而资料明明查得到；
  反过来，**不标注**才是那条真正的坑——质量忽然变了，却没有任何一处报错。

打分**只排序不取舍**：得分为 0 的候选一律不返回（`KNOWLEDGE_BASE_DESIGN` §1.3）。

## 后果

- 知识库从六层变七层：`reranking/` 排在 `retrieval/` 之后（能力分层，不是执行顺序）。
- 全仓多一份「跨三处的方言码契约」（llmcore / platform / 前端），加一路方言要动三处。
- 重排单开一个断路器：它与对话档打的不是同一个端点，共用一份的话，重排端点连挂
  几次会把对话面一起短路掉。失败分档沿用 `llmcore/errors.py` 那一套，
  只有「下游此刻不行」那一档计数——「方言配错了」与 401 一样绝不短路。
- 失败分档多一副按 HTTP 状态码判的面孔（`classified_status`）：重排不走 openai
  客户端，手上只有一个状态码。两副面孔必须给同一个答案，否则同一个 401 会在一条
  链路上短路、在另一条上不短路。
- 迁移只放宽用途码那一条 CHECK，纯扩展步。模型种类那一格库上**没有** CHECK
  可放——模型清单存在 `models_json` 里，种类由入参 schema 与 `rules.py` 把关。
- 对话页（`apps/chat`）那条检索链暂时不接重排：它的检索范围是另一条工作流的活，
  在这里顺手接上等于替它改行为。界面上于是也不在对话页说重排——说了就是假话。

## 备选与为什么不选

**把重排当成 `embedding` 的又一种用法。** 省一档种类，但代价是「换重排模型」会被
读成「换嵌入模型」，而那句话的后果是一次全库重建。两者落库与否的差别是本质的。

**在每个适配器里各写一套传输。** 少一层抽象，但失败分档要抄 N 遍，而抄漏的那一份
表现为「换了一家之后，密钥配错也会让断路器打开」。

**方言按厂商命名（`cohere` / `tei` / `xinference` …）。** 直观，但它们说的是同一套
线形：接第五家时要再抄一遍同一份实现，而五份实现迟早漂开。

**让 `naive` 也接重排。** 看着更一致，但它是出问题时唯一的对照组；叠一层之后
「召回变差了」就只能靠感觉判断。

**在每次检索的 `note` 里说「本部署没接重排」。** 更"透明"，但那句话会出现在每一条
结果上，真正要紧的那句（这一次没排成）反而被淹掉。缺席说一遍就够，说的地方是能力面。
