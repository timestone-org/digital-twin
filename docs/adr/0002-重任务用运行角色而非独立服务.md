# ADR-0002：报告渲染、台账重算、建模训练用运行角色承载，不独立成服务

- 状态：已采纳
- 日期：2026-08-10
- 影响范围：`server/services/platform-server/`、部署编排

## 背景

平台有一批 CPU 与内存密集的长任务：报告渲染（docx 与 OOXML 图表）、台账聚合与重算回填、AI 建模训练、3D 模型几何拆分、保留期清理。

它们绝不能和 HTTP API 跑在同一个进程里。一次训练能把一个副本的内存吃满，一次渲染能让事件循环卡住几秒，而 API 副本的职责是在毫秒级响应请求。**这两类负载必须分开跑，没有争议。**

有争议的是"分开"分成什么：**独立的服务**，还是**同一个服务的另一种进程角色**。

## 决策

**用 `platform-server` 的运行角色承载：`ROLE=api` / `ROLE=worker` / `ROLE=publisher`。同一个代码单元、同一个 schema、不同的进程与资源画像。**

API 角色只入队，worker 角色独占进程池并消费队列。

## 理由

### 一、这些任务要写平台的表，而服务之间不许共享写路径

重算要写台账记录、渲染要写报告产物、训练要写模型版本。这些表的属主是 platform（[ADR-0003](0003-一库多schema且写独占读放行.md)：写独占）。

独立成服务后，它要么直连 platform 的 schema 写入——**破坏写独占**，让两个部署单元同时成为同一批表的属主，迁移归属立刻含糊；要么把领域模型与 CRUD 放进共享包——**[ADR-0004](0004-server分三层且domain承载领域共享包.md) 明令禁止**，理由同上，只是换了个位置犯。

第三条路是让 worker 通过 HTTP 调 API 写数据。这条路把"重算十万行台账"变成十万次内网往返，还要在 API 侧为批量写造一套只有 worker 会用的端点。

**要写别人的表，就不该是别的服务。** 这是判据。

### 二、它们与 API 共享的是领域模型，不是接口

worker 和 api 用同一套表结构、同一套业务规则、同一套公式求值。它们的差别是**触发方式**（请求 vs 队列）与**资源画像**，不是领域边界。

服务边界应当划在领域边界上。划在运行形态上，得到的是两个共享一切、只是启动参数不同的"服务"——那是同一个服务的两种角色，只不过被两套 CI、两个镜像、两份依赖清单包装成了两个。

### 三、对比 collector：为什么那个能独立

collector 写的是自己的 `collect` schema，对 platform 的数据**零依赖**（[ADR-0001](0001-采集运行时独立成服务而配置面留在平台.md)）。它与 platform 共享的只有一份表结构契约，放在 `domain/timeseries` 里，不含任何 ORM 模型。

判据在两个 ADR 里是同一条，只是结论相反——这正说明判据是有效的。

## 代价

`platform-server` 是系统里最大的代码单元，承载了绝大部分业务。它必须靠内部纪律维持可拆分性：

- 按 `apps/<feature>/` 划模块边界，模块之间只走对方的公开面。
- 加**跨模块 import 白名单闸**，把跨模块引用锁在低位。白名单频繁被要求放宽，就是模块划错了的信号。
- 角色开关必须**默认关闭重任务**：`api` 角色绝不能因为某个模块顺手在 import 时启动了一个后台循环而变成事实上的 worker。后台任务的启停在组合根统一声明，不散落在各模块的 import 副作用里。
