# ADR-0004：`server/` 分三层，`domain/` 承载可含项目名词的共享包

- 状态：已采纳
- 日期：2026-08-10
- 影响范围：`server/` 的 workspace 布局、结构闸
- 相关：[`agents/project-structure-python.md`](../agents/project-structure-python.md)

## 背景

`lib` 的第一铁律是**零项目名词**，判据是"把它整个目录拷到一个完全无关的新项目里，还成不成立"。这条铁律保证了基础设施可以被独立测试、独立搬走，不会长成一个带产品前缀的四不像。

但系统里会出现一类代码：**多个服务真实共用，却确实带着领域名词**。

台账公式的解析与求值是典型：平台的 API 角色要用它做实时预览，worker 角色要用它做批量重算，报告渲染要用它算指标。它满篇都是台账、公式、列、记录——按铁律进不了 `lib`。

只有 `lib` 与 `services` 两层时，这类代码无处安放：塞进 `lib` 会毁掉铁律；复制到每个服务里，则会在第一次修改时分叉，而分叉的公式求值器意味着同一张报表在两个地方算出两个数。

## 决策

**`server/` 分三层，依赖方向严格单向 `services → domain → lib`。**

```
server/
├── lib/          ← 通用基础设施，零项目名词
├── domain/       ← 领域共享包，可含项目名词
└── services/     ← 可部署单元
```

`domain` 的四条约束：

1. **可以含项目名词**，但**不许含服务名**——它可以知道"台账"是什么，不可以知道"谁在跑它"。
2. **不许含 ORM 模型、CRUD、FastAPI 依赖注入件。**
3. **`domain/*` 之间不许互相依赖**，保持扁平。
4. **入场券是"已有 ≥ 2 个服务真实消费"**，不是"将来可能共用"。

初始只有两个包：`domain/formula`（台账公式的解析与求值）、`domain/timeseries`（点位历史宽表的结构契约与值编解码）。

## 理由

### 一、"不许含 ORM 模型"是这一层不失控的唯一闸门

一旦 `domain` 里出现某张表的 ORM 模型与 CRUD，两个服务共享它就等于共享数据库写路径，[ADR-0003](0003-一库多schema且写独占读放行.md) 的写独占立刻失效——**而且是静默失效**，没有任何编译期或运行期信号，只有几周后对不上的数据。

这条约束也是 [ADR-0002](0002-重任务用运行角色而非独立服务.md) 的支点：重任务之所以不能独立成服务，正因为"把领域模型塞进 domain"这条出路被本条堵死。

### 二、"不许含服务名"划清了它与 `services` 的界

`domain/formula` 里不该出现服务名、不该出现 API 前缀、不该 import 任何服务的配置对象。它是**被调用的能力**，不是**运行的东西**。

判据比 `lib` 松一档但同样明确，且同样可以自动检查。

### 三、扁平约束防止它长成第二个服务层

允许 `domain` 互相依赖，就会出现 `domain/report → domain/formula → domain/timeseries`，几轮之后 `domain` 长成一棵有层次的树——那是第二个服务层，只是不能部署，还没有服务该有的边界纪律。

扁平的代价是偶尔要把一小段代码在两个包里各放一份。这个代价比多一层隐形架构小得多。

### 四、窄入场券防止它变成第二个 `utils`

"将来可能共用"是共享层膨胀的唯一原因。要求两个真实消费方，等于要求共享的**必要性已经被证明**，而不是被预测。

第二个消费方出现时再抽，代价是一次机械移动；预先放宽，代价是一个没人敢改的公共模块。

## 代价

多一层结构就多一处"该放哪"的判断。缓解手段是判据可机械执行：

- 带项目名词 → 不能进 `lib`；
- 带 ORM 模型或服务名 → 不能进 `domain`；
- 只有一个消费方 → 留在那个服务里。

结构闸必须同时检查：`lib` 内无项目名词、`lib` 不 import `domain` 与 `services`、`domain` 不 import `services`、`domain` 之间不互相 import、`domain` 内不出现 ORM 声明基类。
