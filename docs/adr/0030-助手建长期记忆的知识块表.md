# ADR 0030：助手建长期记忆的知识块表，写入只走显式工具，检索不依赖 pgvector

- 状态：已接受
- 日期：2026-08-31

## 背景

`server/services/ai-assistant/CONTEXT.md` §5「一期不做」里有一条：

> 向量检索与知识库（架构里规划的「知识块」表**不建**：空着的表比不存在的表
> 更容易被误用）。

**本 ADR 推翻这一条。** 按 engineering-workflow §4「与既有 ADR 抵触时要明说，
不许默默覆盖」，这里点名它，并说清条件变在哪。

当初不建的真实理由不是「向量检索没用」，而是**没有明确的写入来源**——
架构图上画了一张知识块表，却没有任何一条链路会往里写。空表比不存在的表更容易
被误用：下一个人看见它，会假设里面有东西，然后写出一条永远召回不到的检索。

缺了长期记忆的代价是具体的。会话历史按窗口脱落（`MAX_HISTORY_MESSAGES = 40`、
`HISTORY_DROP_STEP = 10`），窗口一过就忘。于是本项目的口径——「1 号机组指的是
汽轮机组不是锅炉」「这个厂的压力单位一律 kPa」「北京那张屏的卡片都用极简描边」
——用户每开一次新会话都要重讲一遍，而重讲之前助手会按通用常识猜，猜错了才被纠正。

现在写入来源有了：V4 规划把「记住这件事」做成一个用户会主动说的动作。

## 决策

**一、建 `assistant.knowledge_chunks`，写入来源只有两个显式工具。**

| 工具 | 干什么 |
|---|---|
| `memory.remember` | 用户说「记住：本项目 1 号机组指的是…」时写一条 |
| `memory.search` | 动手之前先查一次本项目既有的约定 |

**不去爬大屏、台账、点位的描述文本。** 助手是纯消费方（CONTEXT.md §2），
业务数据一律经 platform 的 HTTP 面拿。把别人的数据抄一份进自己的库，
「谁是这份数据的属主」就搅浑了：那边改了名字，这边的副本不会跟着变，
而召回出来的旧名字看着像一条正常记忆。

写入来源显式，表就一定不空——当初不建的那条理由随之消失。

**二、不依赖 pgvector。嵌入向量存 `bytea`，检索在应用层做余弦。**

库是**外部托管**的（`docker/compose.yml` 里没有 postgres），且一库多 schema、
写独占读放行（ADR-0003）。装一个扩展是运维请求，影响的是同一个库里的**每一个**
服务——为了助手的一张表让所有服务陪着换数据库镜像，代价和收益差得太远。

向量按 float32 紧凑编码存进 `bytea`，检索时全量取回本 scope 的条目、在应用层算
余弦。显式 remember 出来的条目量级是几百到几千条，应用层扫得动。

⚠ **不要把向量存成 `numeric[]` 或 JSON 数组。** 一条 1536 维的向量存成 JSON 是
两万多字符，取回一千条就是两千万字符的解析——而它表现为「检索有点慢」，
没有任何一处会报错。

**三、检索接口是 `LongTermStore` Protocol，pgvector 是它以后的另一个实现。**

接口定在 ADR-0029 的层 4（`services/memory/ports.py`）。换实现时换的是一个实现
文件加一次迁移，**调用方一个字都不用改**——这正是这个 port 买到的东西。

换实现要有触发条件，否则「以后再说」就是永远不说。起手值：

- 单个 scope 的条目数超过 5000，或
- `memory.search` 的 p95 延迟超过 200ms。

⚠ **这两个数没有实测依据，是起手值不是量出来的。** 写在这里只为了让「什么时候
该换」有个可争论的靶子；第一次真实数据到手就把它们改掉。为此 `memory.search`
要记一条耗时指标（标签只有 scope，低基数——observability）。拿一个拍脑袋的数字
当阈值用而不说明它是拍的，比不定阈值更坏。

**四、条目带 `scope` 与 `owner_id`，检索按调用者身份过滤。**

`scope` 取 `user` 或 `project`：前者是这个人自己的偏好，后者是这个项目的公共口径。

⚠ **这是本 ADR 唯一的安全条款。** 助手代表用户行事、原样转发边缘注入的签名身份头
（CONTEXT.md §2），它绝不能让 A 用户 remember 的东西被 B 检索到。过滤条件写在
仓储层而不是调用点——写在调用点的话，下一个调用点漏掉它不会报错，只会多召回几条。
这条**由一条集成用例守**：两个身份各写一条，互相检索必须为空。

**五、嵌入模型是第三路模型来源，走 `EmbeddingAdapter`。**

不复用对话档（V4 规划 §3.3）。嵌入模型的单价、上下文形状、返回类型都与对话模型
不同——返回的是向量不是 `BaseChatModel`，所以它是另一个 Protocol 而不是
`ModelKind` 的又一档。混成一档等于每次 remember 都按对话档计费。

**六、迁移只做扩展步。**

开头设 `lock_timeout`、加列一律可空、索引 `CONCURRENTLY`、**迁移里不回填数据**
（database-standard）。这张表是新建的，「新结构 + 旧代码」天然可用——旧代码不认识
它，也不会去读。

## 理由

- **「有明确写入来源」是这张表该不该存在的唯一判据。** 当初不建是对的：那时它
  确实会空着。现在有两个用户会主动触发的工具，判据翻转了，结论跟着翻转——
  这不是推翻当初的判断，是同一条判据在新条件下的结果。
- **外部托管的库让 pgvector 的成本远高于账面。** 它不是「装个扩展」，是「让同一个
  库里的所有服务陪着做一次数据库变更」。而本期要的检索规模，应用层就够。
- **port 让选型可以晚做。** 先立 `LongTermStore`，实现从最省事的那个开始，
  换实现的触发条件写死。这比一上来就选 pgvector 好：那样会在还不知道真实量级时
  先付一笔运维代价。
- **按身份过滤放在仓储层。** 安全条款只要能被「忘了加一个 where」绕过，
  它迟早会被绕过；放在仓储层则是「取不到」而不是「记得过滤」。

## 后果

- **新表的属主是助手自己的 `assistant` schema**，不违反写独占（ADR-0003）。
  CONTEXT.md §2 的「只写自己的 `assistant` schema（会话、消息、步骤三张表）」
  要改成四张。
- **CONTEXT.md §5 要同步改。** 留着一条与代码相反的话，比没有那条话更糟——
  下一个人会照着它做判断。
- 两个新服务端工具要进 `TOOL_SPECS`，并被某个技能声明。⚠ 规格、实现、技能声明
  三处名字必须逐字相同，漏一处的表现是「模型看得见、调一次失败一次」。
- **嵌入调用失败时 `memory.remember` 仍然写入**：存文本、不存向量，条目上标一格
  「没有向量」，回执如实说「这条暂时检索不到」。与模型不可用时 fail-open 同一口径
  （CONTEXT.md §3 不变式 4）。
  ⚠ 补救走**下一次 `memory.search` 惰性补算**这些条目的向量，补上就正常召回；
  **不另建关键词检索路径**。两条召回路径意味着两套口径，而它们迟早给出不同结果，
  那时「为什么这条查得到那条查不到」没人答得上来。
- `memory.search` 的召回结果会进上下文。它每轮可能不同，故只能挂在末尾的状态块里
  或作为工具结果出现，**不许进常驻提示词**（ADR-0025）。
- 多一路模型来源，`/capabilities` 要如实报「嵌入档配没配」——没配时
  `memory.remember` 仍可用（只存文本），界面要说得出这件事。

## 备选与为什么不选

| 备选 | 不选的理由 |
|---|---|
| pgvector 扩展 | 库是外部托管、一库多 schema，装扩展影响同库所有服务；本期量级应用层就够，收益不抵这次运维变更的代价。留作 `LongTermStore` 的下一个实现，触发条件已写死 |
| 独立向量库服务（Milvus / Qdrant 等） | 新增一个部署单元与一套备份/升级/监控，只为一张几千条的表；且它是第二个数据属主，与「一库多 schema、写独占」的整体口径背道而驰 |
| Postgres 全文检索（`tsvector` + GIN） | 中文要分词，`zhparser` / `pg_jieba` 同样是扩展——绕不开第一行那个问题；而 `pg_trgm` 的二元组匹配对「1 号机组 = 汽轮机组」这类同义召回基本无效 |
| 继续不建，靠用户每次重讲 | 窗口一过就忘是确定发生的，重讲之前助手会按通用常识猜；而当初不建的那条理由（表会空着）已经不成立 |
| 建表但写入靠自动抽取（爬大屏/台账描述） | 把别人的数据抄一份进自己的库，属主搅浑；那边改了名字这边不会变，召回出来的旧名字看着像正常记忆 |
