# ADR-0006：空调原始数据由 platform-server 直读外部 EMS 库

- 状态：已采纳
- 日期：2026-08-12
- 影响范围：platform-server 的数据访问层、`lib` 的只读外库适配件、部署编排与配置模板

## 背景

现场已有一套厂商的能源管理系统（EMS），它的 SQL Server 库里逐分钟记着每台空调的
19 个测点。我们要做的是**查看**这些数据：按时间段翻表格、画折线。

数据不归我们所有——库是厂商的、表结构是厂商的、写入是厂商的。我们只读。

放在哪读，有三档选择：

1. platform-server 直接连 EMS 库，现查现返。
2. collector-server 定期把数据抄进 `collect` schema，platform 读自己的库。
3. platform-server 的 worker 角色定期同步进 `platform` schema。

## 决策

**platform-server 开一个只读连接直查 EMS 库，不落地、不缓存、不同步。**

配套四条约束：

1. **只读到底**：连接只跑 `SELECT`，不建表、不迁移、不写入。EMS 库不进任何一条
   alembic 迁移链。
2. **就绪探针不查它**（`readiness_probes` 里没有 EMS 这一项）。EMS 挂了只让空调
   数据面返回 503，台账页与空间配置页照常工作。
3. **不做缓存兜底**。查不到就明确报「数据源不可用」，不返回上一次的结果。
4. **视图名按形状校验**，不按名字前缀（见「代价」第三条）。

## 理由

### 一、collector-server 还不存在，而它存在了也不该管这件事

按 [ARCHITECTURE §8](../ARCHITECTURE_MICROSERVICES.md#8-建设顺序) 的建设顺序，
collector 是第 5 步，我们在第 3 步。为一个查看页先建一个服务，代价不成比例。

更要紧的是边界：[ARCHITECTURE §3.3](../ARCHITECTURE_MICROSERVICES.md#33-collector-server)
写明 collector 的职责是**持有 PLC 连接**——它认识的是「服务器端点 + 节点集合 +
采样参数」。EMS 是一个已经采集完、已经入库的关系库，读它既不需要长连接会话，也
不需要订阅与断线重连。把它塞进 collector 会让采集运行时长出「还认识 SQL 方言」
这条与它职责无关的知识。

### 二、抄一份进自己的库，是在给一个只读页面造一条数据管道

同步方案要额外造：增量水位、补洞、乱序处理、失败重试、保留期。这些都是真代码、
真缺陷面。而它买回来的是「查询更快」与「厂商库压力更小」。

实测这两条收益都不成立（2026-08-12，`KTStartData_K01`，190 万行）：

| 查询 | 耗时 |
|---|---|
| 游标式取 500 行（`WHERE CT > 锚点`） | **5 ms** |
| 30 天按 30 分钟桶聚合（1472 点） | 177 ms |
| 一年按 6 小时桶聚合（1460 点） | 247 ms |

基表 `KTkgj` 的主键就是 `Ct` 的聚簇索引，时间范围查询本来就走索引序。**为 5 ms
的查询造一条同步管道，是拿确定的复杂度换不存在的收益。**

同步方案还会引入一个原方案没有的缺陷类别：数据延迟。页面上写着 10:55，现场实际
是 11:20，而没有任何地方说得清这 25 分钟差在哪。

### 三、直读的真实代价是「EMS 挂了这个页面就没数据」，而这个代价是诚实的

同步方案在 EMS 挂掉时会展示陈旧数据。按
[runtime-resilience §9](../agents/runtime-resilience.md) 的口径，**任何降级返回的
陈旧数据都必须标注为陈旧**——也就是说，同步方案并没有免掉这个问题，只是把它变成
了「要额外做一套陈旧标注」。

直读方案里，没有数据就是没有数据，503 加一句「数据源不可用」，没有第二种解释。

## 否决了什么

**否决 `aioodbc` / `pyodbc`，改用 `pymssql`。** 兄弟项目 `Baoding/api` 用的是
`mssql+aioodbc`，那是这台服务器上已被验证的路径，因此这是一次有意的偏离：

- ODBC 路线要求宿主装 `unixODBC` + 微软的 `msodbcsql`。platform-server 的运行镜像
  是干净的 `python:3.12-slim-bookworm`，加这条依赖要在 builder 与 runtime 两个阶段
  各挂一层微软 apt 源并接受 EULA。
- 开发机同样要装。本仓实测：`Baoding/api` 的 `.venv` 里 `import pyodbc` 在本机直接
  `dlopen` 失败（缺 `libodbc.2.dylib`）——也就是说那条路线在开发机上本来就是断的。
- `pymssql` 是自带 FreeTDS 的独立轮子，`pip install` 即可用，且原生支持
  `login_timeout` 与查询 `timeout`。

⚠ 兄弟项目的 SQL Server 连接**一个超时都没有配**。本方案把超时当作必配项，见
[runtime-resilience §3](../agents/runtime-resilience.md)。

## 代价

- **平台多了一类外部依赖**。EMS 的地址与凭据成为 platform-server 的必配项，缺失即
  拒绝启动（[config-and-secrets §3](../agents/config-and-secrets.md)）。
- **厂商改表结构会让我们的查询失效**。缓解：绑定时按**列形状**校验，且用契约测试
  锁死 19 列的列名与类型口径。
- **`KTStartData%` 这个名字前缀不可信**。实测该前缀下 20 个视图里有 3 个
  （`06A699`/`6D139C`/`D5A3FA`）只有 4 列且**没有 `CT`**，它们根本不是时序视图。
  因此可绑定对象的发现必须按形状过滤，按名字过滤会把它们放进下拉框。
- **视图名是外部输入**。它来自我们自己的库，但归根结底是人填的，且必须拼进 SQL
  （标识符不能参数化）。防线是白名单正则 + `INFORMATION_SCHEMA` 存在性校验 +
  方括号引用，三条都要有。
- **深翻页很贵**。`OFFSET 400000` 实测 594 ms，是游标式的 118 倍。这条把
  [api-contract §5.1](../agents/api-contract.md)「时序数据禁止用页码分页」从一条
  规范变成了一条性能约束。

## 什么情况下重新审视

- 需要**跨空调聚合**（例如全场达标率排行）时，逐台查 17 次外库不再合适。
- 需要**保留 EMS 已经删掉的历史**时，只读就不够了。
- EMS 的可用性成为投诉来源时，「不缓存」这条要重新权衡——届时按 §9 的口径补陈旧标注，
  而不是偷偷返回旧值。
