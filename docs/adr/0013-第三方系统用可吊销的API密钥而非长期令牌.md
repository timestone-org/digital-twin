# ADR-0013：第三方系统用可吊销的 API 密钥接入，而不是把 access token 的有效期调长

- 状态：已采纳
- 日期：2026-08-14
- 影响范围：`server/services/auth-server/apps/auth/`、全部经边缘鉴权的服务（凭据形态变了，判定路径没变）

## 背景

第三方系统要通过 HTTP 写 opcua-server 的点位（`POST /api/v1/opcua/instances/{iid}/nodes/{nid}:write`）。
认证走边缘的 `auth_request` → auth-server `/verify`，凭据是 `Authorization: Bearer <access token>`。

access token 的有效期是 900 秒。对浏览器这是对的——前端有刷新循环。对一个
无人值守的采集/下发程序，这意味着它必须自己实现「401 → 拿 refresh token 换一对新的 →
重放请求」，而 refresh token 是一次性的、轮换失败即需重新登录（口令得写在它的配置里）。

最直觉的做法是把 `AUTH_JWT_ACCESS_TTL_S` 调大。

## 决策

**新增一种凭据类型：签发给某个账号的、可吊销的 API 密钥。不动 JWT 的任何参数。**

明文形如 `dtk_<8位前缀>_<43位密钥体>`，前缀入库可展示，密钥体只存 argon2id 散列，
明文只在签发响应里出现一次。库表 `auth.auth_api_keys` 带 `expires_at` / `revoked_at` /
`last_used_at`。

分流只有一处，在 `VerifyService._authenticate`：Bearer 值以 `dtk_` 开头就走密钥分支，
否则走原来的 JWT 分支。两条分支收敛成同一个 `Identity`，之后的签名头、规则表、
各服务的闸 2 完全不变——**下游不知道调用方用的是哪一种凭据**。

## 否决的替代方案

### 一、把 `jwt_access_ttl_s` 调大

否决的直接理由：**access token 无法吊销**。吊销名单只在 `consume_refresh` 里查，
`decode_access` 完全不查（这是刻意的——每次请求查一次 Redis 会让全站前置的 `/verify`
多一次往返）。签一枚一年期的 access token，等于签一把在到期前收不回来的钥匙，
而这把钥匙能写现场点位。

次要理由：这个参数是全局的，浏览器会话会跟着一起变长；且 JWT 是自包含的，
账号停用、改角色、降权都要等到过期才生效。

### 二、长期 JWT + 在 `decode_access` 里加一次吊销名单查询

改动量约为本方案的一半，安全性也够。否决的理由是它缺三样东西，而这三样恰好是
接第三方系统时最常用到的：`last_used_at`（哪枚密钥还有人用、被盗的密钥何时活跃）、
多枚密钥并存（一个第三方系统可以有测试与生产两枚）、以及轮换期（先发新密钥、
观察流量切完、再吊销旧的）。

### 三、给密钥自己一套权限范围（scope）

第一版不做。密钥的权限**完全**继承所属账号，多一套权限来源就多一处会漂的真源，
而这一处漂掉的后果是「账号已停用但密钥还能写点位」。要更细的粒度就多建一个账号。

## 后果

### 必须接受的

- **认证热路径上多一次数据库查询**（按 `prefix` 唯一索引取一行）。这是有意的：
  吊销、过期、账号停用因此都是**立刻**生效，而不是等一个缓存窗口。
- **argon2 是刻意慢的**，不能每个请求跑一次——`/verify` 只有 500ms 超时。
  故按密钥缓存「这串明文的摘要曾校验通过」60 秒。⚠ 缓存的只是算力结果，
  且永远在吊销与过期判定**之后**才被读到。
- 这层缓存 **Redis 不可达时退回逐次 argon2，不是拒绝**。它是性能件；
  让它 fail-closed 等于 Redis 一抖第三方系统就全线写不进值。
- `last_used_at` 按 60 秒节流写库，并且随请求事务落库——**只有鉴权也通过的请求
  才留下痕迹**。

### 有意保留的限制

- **密钥不能用于 auth-server 自己的管理面**（`deps.get_identity` 显式判前缀后拒绝）。
  否则一枚被盗的密钥可以给自己再签一枚，吊销永远追不上签发。
- **只吊销不删除**。删掉一行等于让「这枚密钥曾经存在过」从审计里消失。
- **`expires_in_days` 没有默认值**，「永不过期」要显式写 `null`——它必须是有人
  主动选的，不能是漏填字段的结果。

## 与既有规范的关系

- 签发/吊销挂在 `user:manage` 档，并复用 `assert_target_not_higher`：拿到密钥等于
  能以该账号的身份行事，风险与「重置他人密码」同构，闸也应当同构。
- 路由规则新增两条（`/api/v1/auth/api-keys*` 的 GET 与 POST），**部署时要重跑种子**，
  否则受管前缀上「查不到规则 = 拒绝」会让这两个端点全线 403。
