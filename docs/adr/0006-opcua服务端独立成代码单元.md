# ADR-0006：OPC UA 服务端独立成第六个代码单元

- 状态：已采纳
- 日期：2026-08-12
- 影响范围：`server/services/opcua-server/`、[`ARCHITECTURE_MICROSERVICES.md`](../ARCHITECTURE_MICROSERVICES.md) §2、部署编排、PR 规模闸的适用口径

## 背景

系统要对上位系统（SCADA、MES）暴露 `opc.tcp` 端点，让它们把本平台当作一台 OPC UA 服务器来读写。一期是纯人造数据面：节点值由管理接口写入，上位机也可反向写值，不桥接内部点位。

方向与 [ADR-0001](0001-采集运行时独立成服务而配置面留在平台.md) 相反——那里本平台是 OPC UA **客户端**，主动去连 PLC；这里本平台是 OPC UA **服务端**，被上位机连。两者共用协议，不共用运行时，也不共用数据。

它要同时承载多台逻辑上独立的服务器实例：不同端点、不同地址空间、不同凭据。asyncua 的一个 `Server` 就是一个 TCP listener，端点路径不能复用同一端口，因此 **N 个实例必然占 N 个端口**，需要一段预留端口池（`4840`–`4859`）。

有争议的不是"要不要分开跑"，而是**分开分成什么**。按 [ADR-0002](0002-重任务用运行角色而非独立服务.md) 的口径，第一直觉是把它做成 `platform-server` 的又一个运行角色。

## 决策

**独立成第六个代码单元 `opcua-server`，独占 `opcua` schema，单进程内承载多个实例，副本固定为 1。**

同时确定两条配套口径：

- **不做租约竞选**：`replicas: 1` + 进程级重启，不实现 leader 选举与热备。
- **首次落地提交豁免 PR 规模闸**：新代码单元的第一个提交不受 400 行 / 20 文件限制，此后一律照常。

## 理由

### 一、判据是网络形态与副本策略，不是任务轻重

ADR-0002 的判据是"要写别人的表，就不该是别的服务"。`opcua-server` 写的是自己的 `opcua` schema，对平台的表零依赖——这一条不构成留下的理由。

真正的分歧在部署画像。它要长期持有一段 `opc.tcp` 监听端口、在进程内保有实例级本地状态（地址空间、会话、当前值）、并且必须单活；而 `platform-api` 的画像是**完全无状态 + 按 QPS 水平扩展**。把一个必须单活且独占端口的角色塞进 `platform-server`，代价不是多一个进程，而是这个代码单元从此**多出一种不能水平扩展的形态**——伸缩策略、端口分配、调度约束都要为它开特例。

ADR-0002 否决的是"按运行形态划服务"；这里划的不是运行形态，是**网络形态**：一个对外开放非 HTTP 监听端口的服务，与一群只说 HTTP 的服务，边界本来就在那里。

### 二、端口独占让"热备"热不起来

本仓 `collector` 是单活 + 热备（租约竞选，`replicas: 2`），`platform-publisher` 是单活（租约）。这里不照抄，理由是端口。

备副本**不能提前 bind 端口**，否则与主副本直接冲突。所以备副本只能空转等待，切换时仍要从头 bind、重建地址空间、等上位机重连——OPC UA 会话本来就活不过服务端重启，租约省下的只是进程冷启动那几秒。

而端口段是宿主机映射，两个副本调度到同一节点时 `replicas: 2` **根本起不来**——这不是延迟问题，是起不来。

用一整套选举 + renew-or-die + "Redis 不可达一律判非 leader"的机制，换几秒且会话照断的窗口，不值。**代价换成显式的：单副本重启期间端点整体不可用，这一点写进部署手册，作为对上位系统"必须自带重连"的要求。**

没有选举，也就没有"谁是 leader"这个需要外部存储回答的问题。**实例是否在运行，以本地监听端口的实况为准**，不以任何缓存里的标志位为准——标志位与端口不一致时，对外宣称运行中而实际连不上，是最难排查的一类故障。

### 三、落地提交豁免，是为了保住评审质量而不是绕过它

PR 规模闸是 400 行 / 20 文件，测试计入。本次工作量估算 14000–16000 行、150–180 个文件，严守就是 35–40 个 PR；而 20 文件那条比行数更早卡死——一个服务骨架光是 `pyproject`、`Dockerfile`、入口、配置、迁移、模型、CRUD、schema、路由、测试就超 20 个文件。

强行切分得到的不是"更好评审的 PR"，而是一串**互不可运行的半成品**，违背"每一步结束都应当是可部署、可验证的"。

仓里已有先例：`auth-server` 整体由 `13d5d9b` 一个提交落地，**79 个文件、11952 行插入**。

**豁免边界写死，不留解释空间：**

- 只适用于在 ARCHITECTURE §2.1 代码单元表中**新增**的代码单元；
- **一个单元一次**，即该单元的首个提交；
- 该单元此后的任何改动、以及任何触及既有单元（`lib/`、`auth-server/`、`docker/`）的改动，**都不在豁免内**。

这条边界堵的是"什么都叫新单元落地"——一旦豁免可以复述给第二个提交，规模闸就废了。

## 代价

- 又一份 CI 作业、镜像、依赖清单与迁移链。代码单元数从 5 变 6，`ARCHITECTURE` §2、§5、§8 与 `CONTEXT-MAP` 必须同步，否则文档与实现立刻背离。
- 单副本无热备：进程重启期间 `opc.tcp` 端点整体不可用，上位机必须自带重连。这是对接方的硬要求，不是我们可以静默假设的行为。
- 端口段直连宿主机、绕过 `edge-gateway`：这段流量不享受边缘的 TLS 终结、限流与前置鉴权，安全完全由 OPC UA 自身的 SecurityPolicy 与身份令牌承担。且**端口池是部署期常量**，运行期开不出池外的新端口——池满必须响亮失败，不允许静默降级成一个"显示运行中但连不上"的实例。
- 落地提交没有增量评审基准。缓解手段是硬性的：该提交必须同时配齐 ADR 与 `CONTEXT.md`，并在落地后第一时间把该单元写进 `coverage-baseline.json`——基线一旦记上，此后只许上不许下。
