# ADR 0045：向量与关键词索引改为硬依赖，向量只存 pgvector 的 `vector` 列

- 状态：已接受
- 日期：2026-09-03
- 作废：[ADR-0034](0034-向量索引走端口并按扩展探测选实现.md) 的决策二至五（决策一的
  端口分层保留，只是每个端口从此只有一个实现）

## 背景

ADR-0034 把 pgvector 做成**可选的加速物化**：bytea 是持久真相，`vector(N)` 列与
HNSW 由一步显式的运维动作建，服务启动时探测，探不到就退回应用层余弦，并把原因报进
`/capabilities`。当时的顾虑是「现场那台库有没有 pgvector 尚未确认」，而迁移是 compose
的前置作业——装不上就整栈起不来。

跑了两个月，这套设计在真实部署里的样子是这样的：

1. **加速档没人开。** 那一步运维动作要人记得跑。本部署确实跑过一次，扩展与加速表
   都在；但那之后重装、迁库、换机器时没有任何一处会提醒你再跑一遍。
2. **探测失败是静默的。** 实测到一次：worker 在 `05:03:47` 启动，`05:03:52` 探测
   `ConnectionRefused`（库比它晚起来几秒），按「没装」处理并 WARN 一行——此后这个
   进程**一直**跑在回退档上，直到下次重启。探测只在启动做一次，这是 ADR-0034 自己
   定的，而它与「库晚起来几秒」撞在一起就是这个结果。
3. **两档在界面上长得一模一样。** 回退档照样出结果、照样带出处，只是几万块的库上
   全表扫描算余弦，且 `ILIKE` 那一路根本不给分数。差异只表现为「有点慢」「有点不准」。
4. **顾虑本身消失了。** 现场那台库（`timescale/timescaledb:latest-pg17`）
   `vector 0.8.1` 与 `pg_trgm 1.6` 都已装好，且连库账号有 `CREATE EXTENSION` 权限。

同一时期还查到一件相关的事：worker 进程从来没有刷过模型目录（api 那一侧有启动钩子
与能力面，worker 一个都没有），于是 `can_embed` 问的是一份空快照、恒假，**每一份
文档都跳过嵌入走到 ready**。库里 14 个块、0 条向量，而 `/capabilities` 说的是
「嵌入档已接」。这不是本 ADR 引入的问题，但它与「缺一路也照样 ready」是同一种病：
少了的那一半没有任何一处说出来。

## 决策

**一、`vector(N)` 列是唯一的向量存储，bytea 那一份删掉。**

`kb_chunk_embeddings(chunk_id, base_id, embedding vector(N), embedding_model)`，
主键即 `chunk_id`（一个块只有一条向量），两条外键都 `ON DELETE CASCADE`。

原先双份存储买的是「重建索引不必重新调一遍嵌入 API」。单列天然有这件事——数据就在
那一列上，`REINDEX` 读的也是它。既然如此，第二份就只剩成本：1536 维一条 6 KB，
十万块两份就是 2.4 GB，外加每一次写入的双写。

**二、两个扩展与三个索引都由迁移建。装不上就整栈起不来，这是有意的。**

`CREATE EXTENSION vector / pg_trgm`、向量表、HNSW（`vector_cosine_ops`）、`base_id`
的 b-tree、`kb_chunks.text` 的 GIN trigram，全在同一份迁移里。

扩展装进**本服务的 schema** 而不是 `public`：应用连库时 `search_path` 恰好只有本服务
的 schema（`lib.db` 按 `postgres_schema` 设的），装在 public 的话 `vector` 这个类型在
运行期解析不出来，报的是「type vector does not exist」——与「装没装扩展」看起来毫无
关系。ADR-0034 担心的「迁移动了别的 schema」因此也不成立。

**三、没有回退档。** 删掉 `BruteForceIndex` 与 `LikeKeywordIndex`，删掉
`KNOWLEDGE_VECTOR_INDEX` / `KNOWLEDGE_KEYWORD_INDEX` 两个开关，删掉启动探测。
两个端口各留一个实现——端口留着是为了「装配只此一处」（写侧与读侧必须拿到同一对
索引），不再是为了挑档。

**四、算不出向量的文档判 `failed`，不放它到 `ready`。**

摄取管线在取原件**之前**先刷一次模型目录再问 `can_embed`：算不出就以一句点得出名字
的话失败（缺的是模型分配，还是维数对不上），由人配好之后按「重新解析」。

排在取原件之前是因为一份 200 MB 的文档解完再说「这套部署没配嵌入模型」，是把一次
必然的失败拖到最贵的那一步之后。

**五、维数只有一个来源：`KNOWLEDGE_EMBEDDING_DIMENSIONS`。**

它同时是建表时 `vector(N)` 的 N 与环境变量那一路嵌入端点的维数。写入前先比一次，
对不上就抛一条自己的错，里面有两个数字、有那个环境变量的名字、有下一步该干什么；
`/capabilities` 也报同一句——在传第一份文档之前就看得见。Postgres 自己那条
「expected N dimensions」里，模型名与环境变量名一样都没有。

## 代价

- **库的门槛变高了。** 目标 Postgres 必须能装 `vector` 与 `pg_trgm`，且迁移账号有
  `CREATE EXTENSION` 权限。装不上时整栈起不来——这正是 ADR-0034 要避开的那件事，
  现在明确接受它：一套跑不了向量检索的知识库，起来了也没有意义。
- **换嵌入模型的成本明码标价。** 维数变了要改环境变量、跑一次新迁移重建向量表、
  把已有文档重新解析一遍。原先那套也一样要重嵌，只是没人说。
- **存量向量不迁。** 迁移只做扩展步（建新表，不删旧表、不回填）；bytea 那张表与运维
  脚本建的 `kb_chunk_vectors_pgv` 由下一次发布的收缩步删。本部署那张表是空的
  （见背景第 2 条的成因），有量的部署按「重新解析」重算。

## 影响

- `server/services/knowledge-server/migrations/versions/*_require_pgvector.py`：扩展步。
- `services/indexing/`：`pgvector.py` 与 `keywords.py` 各剩一个实现，
  `bruteforce.py` 与 `LikeKeywordIndex` 删除。
- `probe.py` 与 `index.py`（那步运维命令）删除；CI 里对应的一步也删除。
- `worker.py` 把 `catalog.refresh` 接进摄取管线——这一条独立于本 ADR 也必须修。
- `/capabilities` 的 `index.vector` / `index.keyword` 从此恒为 `pgvector` / `trgm`，
  `reason` 改为报维数不一致这类真实毛病。
