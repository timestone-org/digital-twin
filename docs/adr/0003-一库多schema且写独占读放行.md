# ADR-0003：一个 database 多 schema，写独占、读放行

- 状态：已采纳
- 日期：2026-08-10
- 影响范围：全部服务的数据访问层、迁移配置、DB role 授权

## 背景

五个服务的数据要放在哪，有三档选择：共用一个 schema 靠表名前缀区分、一个 database 每服务一个 schema、每服务一个独立 database。

选择要同时满足三件事：**归属清晰**（一张表出问题时知道找谁）、**误写不可能**（不靠自觉）、**将来能分开**（某个服务的数据量或负载特征变了，能独立搬走）。

## 决策

**一个 database，每个服务独占一个 schema。**

| schema | 内容 | 属主 |
|---|---|---|
| `auth` | 用户、角色、权限码、路由规则、API 密钥 | auth-server |
| `realtime` | 主题登记、用户订阅 | realtime-hub |
| `assistant` | 会话、消息、知识块 | ai-assistant |
| `platform` | 大屏、绑定、项目、模板、素材、点位配置、台账、报告、建模 | platform-server |
| `collect` | 点位历史、采集运行态 | collector-server |

三条规则：

1. 一张表只有一个属主服务，**只有属主能写、只有属主管迁移**。
2. 跨 schema **只读**允许，用独立的只读 DB role 授权（`GRANT USAGE ON SCHEMA` + `GRANT SELECT`），不靠自觉。
3. 跨 schema 读**不许经 ORM 模型共享**——共享的是表结构契约（放 `domain/`），SQL 各写各的。

配套三条禁令：**禁止跨 schema JOIN、禁止跨 schema 外键、禁止跨 schema 事务。**

## 理由

### 一、靠表名前缀自觉，在多部署单元下必然失效

单体里改错表会在评审里被看见，因为所有代码在一起。拆成多个部署单元、多条发布流水线之后，看不见了。

而数据库是唯一无法回滚的东西：一个服务误写了另一个服务的表，不会有编译错误、不会有 404，只会有一致性问题在几周后以"数据对不上"的形式浮现。**这类错误必须由数据库本身拒绝，而不是由纪律避免。**

### 二、独立 database 的隔离收益不值它的代价

跨服务读在本系统里是真实存在的：平台的看板发布与报告指标要读点位历史，而历史表的属主是 collector。

独立 database 意味着这些读必须走 HTTP 查询 API。宽表时序查询单次可能返回数千行，走 HTTP 只是把一次索引扫描换成序列化 + 网络 + 反序列化，同时凭空多出一个会超时、会限流、需要重试的失败面。

一库多 schema 拿到了独立 database 的**主要隔离收益**（写权限强制、迁移边界、归属清晰），代价只是共享一个实例的连接数与资源。

### 三、三条禁令是"将来分库"这个期权的行权价

只要没有跨 schema 的 JOIN、外键与事务，任何一个 schema 都可以整体搬到独立实例，只改连接串。这三条一旦破了一条，分库就从"改配置"变成"改代码 + 数据迁移 + 一致性设计"。

因此它们必须由 CI 执行而非评审记忆：迁移文件里出现跨 schema 外键、代码里出现跨 schema JOIN，直接失败。

## 代价

- **新增表要同步授权**：只读 role 的授权在每次新增表时要跟上。默认不授权，于是跨服务读会以权限错误响亮失败——这是想要的行为，比静默读到空结果好。
- **迁移要按 schema 配置**：alembic 各自绑定 `version_table_schema`，五条迁移链互不相干，各自单头。
- **连接数是共享资源**：单实例的连接上限被所有服务分享，必须按服务配置连接池上限并监控，不能任由某个服务把连接吃光。
- **只读方要容忍属主的 schema 演进**：属主改表结构时，只读方的 SQL 可能失效。用契约测试锁死被跨服务读取的那几张表的列口径（见 [`agents/testing-standard-python.md`](../agents/testing-standard-python.md) §1 L3）。
