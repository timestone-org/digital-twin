# ADR 0027：2D 孪生的节点与连线样式是可配置图元文档

- 状态：已接受
- 日期：2026-08-27
- 影响范围：`web/packages/twin2d/`、`web/packages/modules/src/modules/twin-2d-view/`、`web/app/src/pages/Twin2dEditor/`
- 相关：[MODULE_TWIN_2D_DESIGN §2 / §7 / §13.4](../MODULE_TWIN_2D_DESIGN.md)、[ADR-0016](0016-复杂config段由清单声明的整页子编辑器接管.md)

## 背景

参考项目的 2D 拓扑图里，「节点长什么样」是一个 5 值枚举：
`box` / `cylinder` / `tank` / `square` / `text`。渲染层为每一档写一个 DOM + CSS 分支，
那个 SFC 是 **1083 行**。用户自建类型时能挑的只有：这 5 档形状之一、12 个颜色 token
之一、四边中点四个锚点之一、11 枚内置 sprite 或一个 lucide 名或一条素材引用。
**形状本身画不出来。**

这条路走到「画电路图」直接断。电阻、电容、二极管、接地符号没有一个能落进那 5 档，
而每加一个符号要同时改四处：加一个渲染分支、加一份 CSS、加一档枚举、改一次归一化
白名单。终点是十几个 `v-else-if` 与一份没人敢动的样式表。

参考项目还给这条路配了后端：自定义类型库存在项目级的两张表里，配 8 个端点。
**而运行时一处都不消费**——渲染层写死用内置库，于是用户自建的类型在编辑器里长得对、
上大屏一律退化成兜底（`box`、无图标、`fields=[]` 故主显读数消失），全程零报错。

## 决策

**一、节点样式整个下沉成数据。** 一个样式 = `{ 尺寸, 端口[], 槽位[], 图元[], 变体[] }`，
图元四种且闭合：`box`（HTML 盒）/ `vec`（SVG 几何）/ `ico`（图标）/ `txt`（文字）。
形状由 `vec` 的几何决定（`path` 的 `d` / `rect` / `ellipse` / `line` / `poly`），
配色是图元上的一个 CSS 颜色字符串，字段布局是 `box` 的 flex + `txt` 的位置，
锚点是 `ports[]`（周长参数 `t` 或归一坐标），一样都不再是枚举。

**二、内置库只是预置数据，与用户自建样式走完全同一条渲染路径。**
`@dt/twin2d/presets` 下是一批 `Twin2dNodeStyle` 字面量：19 条节点样式（11 种参考项目
类型 + 8 枚 GB/T 4728 电路符号）、25 种子类组合、5 种连线、4 种传感器药丸。
**渲染件里零 `styleId` 分支**——包内 `src/render/` 全目录只有一处出现 `styleId`，
是 `styles.get(node.styleId)` 这一次查表。

**三、内置库是引用式、可覆盖，不 materialize。** 渲染时
`styleMap = merge(BUILTIN_STYLES, config.styles)`，同 id 以文档为准；改内置样式 =
文档里落一份同 id 的覆盖；「恢复内置」= 删掉那份覆盖；「另存为自定义」= 复制一份带新 id 的。

**四、样式库住在文档里，不建后端表**（`config.twin2d.styles[]`，随大屏整树替换落库）。
跨大屏复用靠导出/导入样式包 JSON。真要做项目级共享时再加，**前提是先把运行时的
消费点接上**——参考项目缺的正是这一步。

**五、这一条不靠自觉，靠断言。** §7 那张 100 行「参考项目视觉件 → 新模型如何表达」
对照表逐行有断言：99 行落在 `packages/twin2d/tests/twin2d-preset-fidelity.spec.ts`
（用例名带行号 `§7-1` … `§7-100`），第 100 行的实现在模块目录，断言跟着实现走。

## 理由

- **枚举的成本不在写的那天，在第 12 个形状那天。** 下沉成数据之后，新符号是一条
  数据、一次编辑器里的点选，渲染层一行不改；而枚举那条路每个新符号都要动渲染分支，
  且分支之间没有任何机械约束保证它们表现一致。
- **「内置库只是数据」是可以退化的**，且退化的每一步都不报错：某天为了一个特例在
  渲染件里写下第一个 `if (styleId === '…')`，测试照绿、界面照旧。fidelity 对照表是
  这条决策唯一的机械保证，它红了就说明预置数据正在长回渲染分支。
- **不建表不是省事，是让运行时拿得到。** 大屏运行态（含公开大屏的匿名访问）手里只有
  一份配置；样式在文档里就天然可用，在表里就要多一次请求加一个匿名口子。而参考项目
  证明了：表建好了、端点写好了、运行时没接上，等于没有。

## 后果

- ⚠ **改预置库会改存量大屏的渲染**：所有没覆盖过该样式的节点跟着变。这与
  `ConfigField.default` 是同一条口径（default 会 materialize 进每一次渲染），
  故改预置库按「改存量」评审，不按「改代码」评审。
- ⚠ 不许为了「兼容」反过来搞成「文档里的内置条目一律丢弃、改用代码里的最新定义」。
  参考项目就是那么做的，后果是通过整库替换写进去的改动被静默还原，
  用户以为自己没保存成功。
- **数据化必须配一个画得动的编辑器**，否则「形状可配」只是嘴上说说：样式编辑器
  （图元树、几何取点、变体、端口、槽位）因此是本模块最大的一块，不是可选项。
- **文档变大**：一份自建样式是几百行 JSON，落在 `configJson.twin2d` 里。归一化因此
  必须逐层防御——超深截断、悬空槽位引用、悬空 sprite id 各有断言
  （`twin2d-slot-refs.contract.spec.ts`）。
- **四种图元 kind 是闭合集**，加第五种是一次契约变更（`twin2d-prim-kinds.contract.spec.ts`
  会红）。这是有意的：kind 一多就又回到「按 kind 分支」。
- 包的体量对得起这条决策：`@dt/twin2d` 源 **16 598 行 / 63 个文件**，测试 **23 808 行**。
  枚举那条路省下的是其中的绘制层，代价是形状从此封闭。

## 备选方案

| 备选 | 不选的理由 |
|---|---|
| 沿用 5 值枚举 + 有限自定义 | 电路符号一个都落不进去；每个新形状要改四处，且分支之间无机械约束 |
| 枚举 + 一档 `custom` 走自由 SVG | 两套渲染路径并存，`custom` 一档永远缺内置那档的槽位/变体能力，用户一改就丢 |
| 样式库建后端表（参考项目做法） | 运行时要多一次请求、公开大屏要开匿名口子、PR 从只碰 `web/` 变成碰服务端 + 迁移 + RBAC；而它真正的教训是运行时没接上时这一切等于零 |
| 内置库 materialize 进文档 | 存量大屏再也吃不到内置库的修正；且「恢复内置」变成写死一份当时的数据 |
