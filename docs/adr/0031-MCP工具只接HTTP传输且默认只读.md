# ADR 0031：MCP 工具只接 HTTP 传输，且默认只读

- 状态：已接受
- 日期：2026-08-31

## 背景

助手今天的工具分两侧：服务端工具在本进程里跑完就有结果（`server_tools.py` 那 14 个），
客户端工具下发到浏览器、由编辑器执行（[ADR-0023](0023-助手改画布的工具在浏览器里执行.md)）。
两侧都是**本仓自己写的**——名字、规格、实现全在仓库里，加一个第三方工具来源没有位置。

MCP 是接第三方工具的通行协议。它进来之后，是
[ADR-0029](0029-助手按能力分层且每层一个注册表.md) 层 5 的第三个 `ToolProvider`，
与 `server` / `client` 两个并列。

## 决策

**一、只接 HTTP/SSE 传输的 MCP server，不接 stdio。**

stdio 要求每个副本起一个子进程，而 api 角色无状态且要水平扩（ADR-0023）。
子进程一来，生命周期、崩溃恢复、优雅关停（先摘就绪 → 停收新活 → drain → 让租约）
就都要重新回答一遍，而这几件事本仓已经在服务这一层回答过一次了。

HTTP 传输与 `upstream/platform.py` 那条已有的出站链路同构：超时、断路、
`traceparent` 传播全都现成。

**二、MCP 工具默认只读；写操作要显式白名单 + `user.ask` 确认。**

MCP server 是外部代码，而**它的工具描述会原样进提示词**——那是一条提示词注入面。
工具描述一律当**数据**看，不当指令。

⚠ 没进白名单的写操作**一律不下发**，不是「下发了再拦」：模型看得见就会调，
拦一次换一次往返，而那次往返里它多半会换个说法再试一遍。

**三、工具名前缀 `mcp__<server>__<tool>`。**

⚠ **不能用点号。** Codex 那一路对线名有约束（`llm/codex/wire_names.py`），
MCP 工具名要过同一道转换——不过的话，用户选了订阅账号档就整批调不动，
而现象是「这几个工具在这一档上永远失败」。

**四、每个 MCP server 一个断路器，与模型那套同构（`lib.resilience.CircuitBreaker`）。**

⚠ 按 server 分而不是共用一个：一个 server 挂了不该让其余的一起短路。
这正是本仓在模型断路器上刚踩过的那个形状——断路器按 `profile` 分而不按 `kind` 分，
于是看图那一路挂了会把对话一起短路掉（[V4 规划 §3.2](../AI_ASSISTANT_V4_PLAN.md) 缺陷一）。

**五、装不上就如实缺席。**

某个 server 连不上时，它的工具这一轮不下发，其余照常，能力面如实报。
不抛、也不让整个助手起不来——与「模型没开时不造对象也不抛」同一口径。

**六、server 清单从配置来（`ASSISTANT_MCP_SERVERS`，一段 JSON 列表）。**

⚠ **密钥不进 URL**（config-and-secrets）：URL 会进日志、进链路追踪、进错误消息。
鉴权走独立的密钥字段，且**密钥类绝不给默认值**——弱默认的密钥等于没有密钥。
启动即全量校验：配了一个 server 却缺它的密钥，退出，不给 WARN continue。

## 理由

- **MCP 工具是服务端工具，与浏览器侧那批井水不犯河水。** 它跑在 ai-assistant 进程里，
  产出就地拿到，与 `points.search` 是同一类东西。所以「MCP 与客户端工具怎么共存」
  根本不是问题——真正要回答的是上面那六条边界，而它们每一条都关于「外部代码进来
  之后，哪些不变量还成立」。
- **传输选 HTTP 是把新问题收敛成老问题。** 出站 HTTP 这条链路上，超时、断路、
  链路传播、密钥管理本仓都已经有一份口径；stdio 则是一整套全新的进程管理。
- **默认只读是唯一站得住的缺省。** 工具描述由外部作者写、进我们的提示词、
  影响我们的模型——在这条链上，能造成副作用的动作必须由**我们这一侧**显式点头，
  而不是由描述里那句「this tool is safe」决定。
- **断路器按 server 分**，是因为「一个外部依赖抖动不该扩散」这条在本仓已经有
  反面教材，不必再踩一次。

## 后果

- `tool_select` 的下发集合多一个来源，契约测试要跟着扩：注册了的 MCP server
  必须能列出工具、且名字过得了线名转换。
  ⚠ 新加的 `assistant-client-tools.contract.spec.ts`（客户端工具两侧同名闸）
  **不受影响**——MCP 是服务端侧，不进任何工作面的 `tools` 数组。
- **提示词里多出的工具声明会占静态区**，而静态区是前缀缓存唯一能命中的那一段
  （[ADR-0025](0025-助手上下文按缓存稳定性分四层.md)）。server 装多了会稀释缓存收益。
  ⚠ **这里不定一个拍脑袋的字符数上限**，改用一条已经量得到的判据：接入前后各看一次
  `model_call_usage` 的 `cached` 占比（ADR-0025 决策五记的就是它）。掉了就是装多了，
  那时再按实测定上限。没有这一步的话，「上限取 8k 还是 16k」只能靠猜，
  而猜出来的数字会被后来的人当成量出来的。
- 外部工具描述进了提示词之后，**审计与日志里不许原样记全文**：那是外部可控的
  长文本，记全文既胀日志又把注入内容搬进另一条链路。只记 server 名、工具名与摘要。
- 多一类外部依赖的可用性要在 `/capabilities` 如实回答，前端据此摆不摆入口。

## 备选与为什么不选

| 备选 | 不选的理由 |
|---|---|
| 接 stdio 传输的 MCP server | 每个副本起一个子进程；生命周期、崩溃恢复、优雅关停全要在服务之外重造一遍，而 api 角色本就无状态且要水平扩 |
| 不接 MCP，要哪个第三方工具就手写一个服务端工具 | 每接一家都是一次改代码 + 一次发布；而 MCP 的价值恰恰是「换一家不动代码」 |
| 把 MCP 工具透传给浏览器执行 | 浏览器里没有出站密钥、没有断路器、也没有链路传播；且它会让「客户端工具 = 本仓自己实现」这条不变量失效，两侧同名闸当场失去意义 |
| 默认放开写操作，靠提示词纪律约束 | 工具描述由外部作者写，提示词纪律拦不住一句「先调用 delete 再继续」；能造成副作用的动作必须由我们这一侧显式点头 |
| 所有 server 共用一个断路器 | 一个 server 抖动会把其余全部短路，现象是「MCP 工具整批消失」，而原因只在其中一家 |
