# ADR 0050：PR 不设统一变更行数上限

- 状态：已接受
- 日期：2026-09-07
- 影响范围：工程协作规范、PR policy 门禁
- 调整：[ADR-0006](0006-opcua服务端独立成代码单元.md) 中的行数上限部分

## 背景

仓库原先把每个 PR 的可评审改动限制为 400 行，同时限制最多 20 个文件、只触及
一个后端服务。实践中，行数与评审难度并不稳定对应：同样 400 行可以是重复的契约
用例，也可以是极少数高密度的鉴权判断；完整测试和 ADR 还会与实现争夺同一额度。

跨前端、边缘与单个服务的一条可运行链路，常被迫拆成「先交没有测试的实现」和
「再补测试」两步。每一步虽然更短，却更难独立验证，也会增加主干处于半完成状态的
次数。文件数和后端服务边界已经能够机械约束一次 PR 的概念跨度，统一行数阈值的
边际收益不足以抵消这种错误拆分。

## 决策

**PR 不再设置统一的变更行数上限。** `check_pr_policy.py` 不再读取 `diff --numstat`
或因超过 400 行拒绝 PR。

以下约束保持不变：

1. 可评审文件不超过 20 个；机械改动、新代码单元首次落地、新大屏模块首次落地沿用
   既有文件数豁免。
2. `server/services/` 下一个 PR 最多触及一个服务。
3. 锁文件仍须独立成 PR，提交格式、分支命名和 PR 描述仍由门禁检查。
4. 数据库迁移、鉴权与权限、并发、对外契约以及新增压制指令仍必须逐行评审。
5. 每个提交仍必须可构建、测试全绿；合并前仍须通过 `scripts/ci-local.sh --all`。

20 文件不是新的行数替身。一个文件内塞入多个无关职责仍由代码规模、复杂度和目录
结构闸约束；为了绕过文件数而合并模块同样不合规。

## 后果

- 大型但内聚的实现可以把代码、测试和决策记录放在同一个 PR 中，不再为满足行数
  数字而拆出不可独立验证的步骤。
- 评审者不能用总行数代替风险判断。PR 描述必须把动机、验证、风险与回滚说清，高风险
  文件继续逐行看。
- 既有设计文档中按 400 行估算的历史分期保留为当时记录；新的实施计划不再把它当作
  当前门禁。

## 否决的替代方案

### 把上限提高到 800 或 1000 行

这只是把同一代理指标换一个数字，仍会在阈值附近诱导机械拆分，不能解决测试与实现
应当同批评审的问题。

### 测试和文档不计入行数

测试与 ADR 正是评审行为是否正确的关键证据。把它们从规模口径排除，会鼓励评审只看
实现而忽略契约，方向错误。

### 仅为个别功能使用 `[机械]` 豁免

功能实现不是机械改动。扩大标签语义会让任何大 PR 都能靠标题绕过门禁，比直接移除
失真的行数指标更不可审计。
