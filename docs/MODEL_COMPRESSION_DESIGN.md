# 三维模型压缩分档 — 设计

> 模型传上来之后，由 `platform-worker` 在后台压出**三档派生件**（高 / 中 / 低），
> 与原件一起躺在同一个对象前缀下；素材库逐档显示体积与压缩比，孪生配置**按档引用**。
> 后端在 `platform-server`（`apps/assets` 的数据面 + `worker` 角色的压缩管线），
> 前端在 `@dt/contracts`（档位与对象键）、`@dt/three-core`（解码器）与素材库 / 孪生编辑器。
> 与 [ADR-0015](adr/0015-素材字节走对象存储且浏览器直传直取.md)、
> [ADR-0022](adr/0022-模型压缩分档由worker产出且档位由消费方选.md) 直接相关。

---

## 1. 要解决的问题

现场那台机器要在浏览器里拉一个 **109 MB** 的 `.glb`。大屏一开就是几天，首帧却要等
一分多钟；换一台带宽差些的机器就更久。而同一个模型在不同场合的画质要求根本不同：
孪生编辑器里要看清每一根管子，值班大屏上只要认得出轮廓。

现在只有**一档**——原件。要么全都等一分钟，要么让美术手工导出好几个版本再各传一遍
（而那几个版本之间没有任何东西说明它们是同一个模型的不同档）。

---

## 2. 通用语言

| 词 | 指什么 |
|---|---|
| **原件**（`original`） | 用户传上来的那份字节，一个 bit 都不动。**永远保留** |
| **档位**（`variant`） | 由原件派生出的一份压缩产物。目前三档：`high` / `medium` / `low` |
| **几何压缩** | Draco：把顶点与索引重编码。**拓扑不变、面数不变**，纯压体积 |
| **网格简化** | 按目标比例减面。**画质有损**，是「档」之间真正拉开差距的那一步 |
| **派生件** | 原件之外、由本平台算出来的字节。压缩档是第一批派生件 |

档位的定义（**只有这一处是真源**，服务端 `variants.py` 与前端 `@dt/contracts` 逐字对齐）：

| 档 | 简化到 | 几何压缩 | 什么时候用 |
|---|---|---|---|
| `high` | 100%（不减面） | Draco | 默认档。画质与原件**无差别**，体积通常降到 1/3–1/8 |
| `medium` | 50% 面数 | Draco | 值班大屏、远景 |
| `low` | 25% 面数 | Draco | 缩略预览、低配机器、弱网 |

⚠ **`high` 不是「高压缩」是「高画质」**。三个名字排的是**画质**不是压缩率，
因为选档的人关心的是「够不够清楚」。反过来命名（`low` = 压得少）每次都要在脑子里翻译一次。

## 3. 谁来压：worker，不是浏览器

**决策见 [ADR-0022](adr/0022-模型压缩分档由worker产出且档位由消费方选.md)。** 要点：

浏览器端压缩（上传前压完、每档各自直传）本来是更省事的一条——复用现成的直传三步、
服务端字节面一行不动。但 109 MB 的 glb 在浏览器里解析 + 简化 + 重编码，内存峰值按经验是
**文件体积的 10–20 倍**，标签页在几百 MB 的模型上会直接崩；而且用户得开着页面等几分钟，
关掉就前功尽弃——**上传成功与压缩成功变成了同一件事**，而它们的失败处置完全不同。

worker 端的代价是明摆着的：`platform-server` 的镜像要装 Node 与 glTF 工具链
（实测 817 MB → 1.01 GB）。接受它，
换来的是「传完就能走」，以及压缩失败**不影响素材可用**（原件已经落库了）。

## 4. 字节放哪

对象键沿用 `models/{asset_id}/` 这个前缀，档位就是前缀下的另一个对象：

```
models/{id}/original     ← 用户传的，永不改写
models/{id}/high
models/{id}/medium
models/{id}/low
```

三条既有的性质因此不用动：

- 删素材删的是**整个前缀**（`owned_prefix()`），派生件跟着一起走，不会留孤儿；
- `models/` 在匿名可读的白名单里，大屏机取档位与取原件同一条路；
- 键里不含任何调用方输入，全部由 `(kind, asset_id, variant)` 推导。

⚠ **原件永不改写**。压缩是纯追加：重压一次只覆盖派生件那三个键。原件被动过的话，
「压坏了想退回去」这条路就没了，而那正是最需要它的时刻。

## 5. 库里存什么

新表 `asset_model_variants`，一个素材一档一行：

| 列 | 说明 |
|---|---|
| `asset_id` + `variant` | 联合唯一。⚠ 不用自增主键：重投递是常态，靠这一对做幂等 |
| `status` | `pending` / `ready` / `failed`。⚠ text + CHECK，不用原生 ENUM |
| `size_bytes` / `checksum` | 存储端读回来的事实，压成之前是 NULL |
| `error` | 失败原因，给界面直说。压成时清空 |

**行在 finalize 那一刻就落齐**（三行 `pending`），不是压完才落。理由：界面要能显示
「正在压」，而「没有行」与「压完了但一档都没成」在界面上长得一模一样。

⚠ 不给 `assets` 加 JSON 列。档位是**会一行行变状态**的东西，塞进 JSON 就意味着
每次改一档都要读改写整块，而两个 worker 同时改两档时后写的会把前一档盖回去。

## 6. 任务怎么流

沿用 worker 角色现成的 Redis Stream：

```
finalize（api 角色）
  └─ 落三行 pending  ─┐        ⚠ 同一个事务
     投一条压缩任务  ─┘        （投队列本该在事务外，见下）

platform-worker
  └─ 取任务 → 从对象存储拉原件 → 逐档压 → 传回 → 把那一行改成 ready
```

⚠ **投队列不许放在事务里**（database-standard §4）：事务回滚了消息却已经发出去，
worker 会去压一个不存在的素材。故顺序是「提交事务 → 投队列」，而**投递失败不回滚**——
那时库里留着三行 `pending`，由「重压」入口兜底，比丢掉一个已经传好的素材好。

⚠ **消费者必须幂等**：at-least-once 的重复投递是常态。判据是
`(asset_id, variant)` 那一行的 `status`——已经 `ready` 的直接跳过，不重压。
「先查再插」不算幂等，落行走 `ON CONFLICT DO NOTHING`。

失败不重试到底：一个压不动的模型重试一万次也压不动。失败即写 `failed` + 原因，
**由人在界面上按「重压」**。⚠ 一条链路只有一层负责重试（runtime-resilience §4）。

## 7. 压缩怎么做

工具是 [`@gltf-transform`](https://gltf-transform.dev/)（Node，MIT）。选它不选
`gltfpack`：后者是单个二进制、简化算法更好，但**只出 meshopt 不出 Draco**，
而 Draco 的解码器 three 自带、meshopt 也自带——两者都行，真正的分野是
`gltf-transform` 是库不是命令行黑盒，能把「简化比例」「是否保边界」这些逐档参数写在代码里。

⚠ **Python 侧没有可用的 glTF Draco 编码器**。这是要装 Node 的唯一原因，不是偏好。

管线（每一档一遍）：

```
读 glb → weld（焊接重复顶点，不焊简化会把网格撕开）
       → simplify(ratio)     ← high 档跳过这一步
       → draco 编码
       → 写 glb
```

⚠ `weld` 不能省：导出的 glb 常把每个三角形的顶点各存一份，不先焊接的话
simplify 看到的是一堆互不相连的三角形，减面之后模型会碎成雪花。

## 8. 谁来选档

`TwinModelRef` 加一个字段：

```ts
interface TwinModelRef {
  asset: string          // asset:<uuid>，不变
  variant: TwinModelVariant  // 'original' | 'high' | 'medium' | 'low'
  ...
}
```

⚠ **档位不编进引用串**。`asset:<uuid>` 的语法在服务端、前端、删除时的反查里各有一份
实现，往里塞 `#low` 要同时改三处，而漏掉任何一处都只表现为「取不到」。档位与
`kind` 同性质——**由消费语境决定**，这正是 ADR-0022 沿用 ADR-0015 §4 的那条推论。

存量配置里没有这个字段，规范化时给 **`original`**：既有大屏的表现一个像素都不变。

⚠ **选了一档不代表它已经压好**。孪生渲染侧取档时若那一档不是 `ready`，
**回落到原件**并在编辑器里明说；不回落的话现场就是一块永远转圈的黑屏。

---

## 9. 加载侧要接解码器

three 自带 Draco 解码器（`examples/jsm/libs/draco/`），但当前 `GLTFLoader`
**一行都没接**——现在只吃未压缩的 glb。要让压缩档能加载：

1. 解码器的 `.wasm` / `.js` 拷进 `web/app/public/draco/`，随构建产物一起发；
2. `createGltfSource()` 挂上 `DRACOLoader` 并指到那个路径。

⚠ 解码器**不能走 CDN**：现场那台机器不一定有外网，而没有外网时的表现是
「模型永远加载中」，控制台里只有一条被浏览器吞掉的跨域错误。

⚠ 解码器一挂就是全局的：未压缩的 glb 照常加载（`GLTFLoader` 只在文件真的声明了
`KHR_draco_mesh_compression` 时才会去调解码器），故这一步对存量模型无影响。

## 10. 界面上看到什么

**素材库**（模型类素材的详情面）逐档一行：档名、状态、体积、相对原件的压缩比。
压缩中显示进度态，失败显示原因并给「重压」。

**孪生编辑器**（`ModelInspector`）在挑完模型之后多一个档位选择器，逐档标出体积，
让人按「这块屏要多清楚」直接选。未就绪的档禁选并说明原因。

## 11. 不做的

- **纹理压缩（KTX2 / Basis）**。109 MB 的 glb 里纹理往往占一半以上，不压它体积降不到底；
  但编码极慢（大图几分钟一张）、视觉有损且不可逆，值得单独一轮来做。留作 §12 的第一条。
- **自动选档**（按带宽 / 设备自动降档）。先让人显式选——自动降档在现场表现为
  「今天怎么糊了」，而没有任何一处说得清为什么。
- **原件的清理**。原件是压缩失败时唯一的退路，也是重压的输入，不给「压完删原件」这个选项。
- **非模型素材的压缩**。图片与图标的体积上限本来就是 16 MB / 512 KB。

## 12. 之后可能长出来的

1. 纹理压缩档（KTX2），与几何档正交，可能变成 `high-ktx2` 这样的组合档；
2. 按视距自动切档（真 LOD），那时档位要从「配置项」变成「运行时状态」；
3. 分片流式加载（超大模型按包围盒切块），那会用到 `models/{id}/` 下的清单文件。
