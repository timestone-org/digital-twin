# realtime-hub 上下文

维持 WebSocket 长连接、管理订阅关系、把其它服务推来的消息扇出给客户端。

边界由 [ADR-0005](../../../docs/adr/0005-实时通道与边缘网关的职责分界.md) 划下，
实现形态由 [ADR-0007](../../../docs/adr/0007-实时通道薄化与开放主题命名空间.md) 定：
**开放主题命名空间，订阅授权由推送方在登记主题时声明**。

---

## 1. 通用语言

| 词 | 指什么 |
| --- | --- |
| **主题**（topic） | 不透明字符串，形状 `<域>:<标识>`。hub 只当它是键，不解析、不理解 |
| **声明**（declaration） | 推送方登记的一条记录：这个主题存在，订阅它需要哪个权限码 |
| **推送方**（publisher） | 打内部推送端点的那个服务。第一个是 `opcua-server` |
| **订阅**（subscription） | 某个用户的某条连接正在收某个主题 |
| **扇出**（fanout） | 一条推送 → 该主题的全部订阅连接 |
| **seq** | 每个主题单调递增的序号，客户端据此发现丢帧 |

## 2. 不变式

1. **不读任何业务表。** 它认识的是连接、用户、主题、载荷，不认识实例、点位或大屏。
2. **订阅授权只比一次**：用户持有的权限码集合 ⊇ 主题声明的码。没有第二处判断，
   不回调业务服务（ADR-0007 §决策 3）。
3. **订阅未登记的主题一律拒绝**，不许「先订后建」。开放命名空间的代价是主题名
   拼错不再是语法错误，放行未登记主题会让拼错名字的客户端**安静地永远收不到
   数据**——最难查的那类故障，必须在订阅时就响亮失败。
4. **`seq` 每主题单调，且跨重启、跨副本成立。** 见 §5。
5. **推送节流归推送方。** hub 不做业务级合并——它一旦知道「哪些载荷可以合并」，
   就又长出业务知识了。合并窗口与分片在 opcua-server 那侧。
6. `realtime` schema 永远不长业务列。两张表都只装通道自己的东西。

## 3. 非目标

- 不做 handler 注册表（那是 ADR-0007 否掉的模型）。
- 不做业务级合并、不解析载荷。
- 不判断声明的权限码「宽不宽」——hub 没有判断宽窄的依据，见 §7 的代价。
- 不做消息持久化与补发。断线期间的消息就是丢了，客户端靠 `seq` 发现并自己决定
  是否重新拉一次全量。

## 4. 多副本与扇出

**副本策略是「按连接数」水平扩，所以扇出必须跨副本。** 一条 HTTP 推送只会落在
一个副本上，而该主题的订阅连接分布在所有副本上。

```
opcua-server ──HTTP──▶ hub 副本 A ──写库拿 seq──▶ Postgres
                            │
                            └──PUBLISH──▶ Redis ──▶ 副本 A/B/C ──▶ 各自的本地连接
```

⚠ **每个副本只往自己持有的连接写。** 连接是进程内对象，不可跨副本共享；
Redis 传的是「这条消息该发给哪个主题」，不是连接。

⚠ **不许用 Redis 的消息当权威 seq。** Redis pub/sub 是即发即弃、无序无保证的，
两个副本各自计数必然分叉。seq 只有一个来源，见 §5。

## 5. seq 的归属

`seq` 随主题声明一起落库，推送时在**同一条 UPDATE 里原子自增并返回**：

```sql
UPDATE realtime.topic_declaration SET seq = seq + 1 WHERE topic = :t RETURNING seq
```

三条都是它必须这么做的理由：

1. **跨重启**：进程内计数器一重启就归零，客户端会把它读成「服务端倒退了」。
2. **跨副本**：两个副本各自计数会分叉，同一个主题出现两串 seq。
3. **重连时要能明确告知当前值**：客户端不许自己推断（ADR-0007 §代价）。

⚠ 代价要认下来：**每条推送都要写一次库**。这是 ADR-0007 用「客户端能发现丢帧」
换来的，不是可以顺手优化掉的实现细节。真扛不住时的出路是让推送方加大合并窗口
（少推几次），不是让 seq 回到内存里。

## 6. 连接的鉴权与时效

| 环节 | 怎么做 |
| --- | --- |
| 握手 | token 走 **WebSocket 子协议**，不走 `Authorization` 头 |
| 到期前 | 服务端要求客户端走一次 reauth，换一枚新 token |
| 逾期 | 关连接，close code **4001** |
| 权限复核 | 按 TTL（默认 60 秒）重新取用户的权限码 |
| 权限不再满足 | **只退订相关主题，不断整条连接** |

⚠ **子协议里的 token，HTTP 头上的鉴权中间件对它不生效**：这条链路必须单独实现、
单独测试。闸 1 同样认不出它——`/api/v1/realtime/ws` 在权限目录里是「任意已登录
用户」的空码规则，它的匿名可达性由**边缘免认证 location** 保证，认证在 hub 内部
完成（同 `/auth/sessions*`）。

⚠ **权限不满足时断整条连接是错的**：那会把该用户正在看的其它无关主题一起牵连，
表现为「点开一个没权限的页面，整个大屏黑了」。

## 7. 主题登记

推送方在业务实体创建时登记、删除时注销，走内部端点（服务级密钥）。

1. 登记时**校验声明的权限码存在于 auth-server 的权限码目录**。不存在即拒绝登记
   （ADR-0007 §决策 4）。
2. ⚠ **auth-server 不可达时 fail-closed：拒绝登记。** 这是 issue #5 留给本文件的
   待定项，结论是拒。放行的话，一次 auth 抖动就会让一个**声明未经校验**的主题
   永久留在库里，而登记是一次性动作、没有第二次校验的机会；拒绝的代价只是推送方
   重试一次——它本来就要按 at-least-once 处理注销，重试路径已经存在。
3. 注销按 at-least-once 处理，且**必须有一条对账**：实体删了而主题没注销，会留下
   一个谁也推不到、却仍可被订阅的空主题。不允许静默失败。
4. hub 拦得住「编造一个不存在的码」，**拦不住「声明一个存在但过宽的码」**——
   它没有判断宽窄的依据。后半截靠权限码目录本身的评审兜，这是评审约束不是机器
   约束（ADR-0007 §代价）。

## 8. URL 形状

```
/api/v1/realtime/ws              ← 客户端 WebSocket，token 走子协议
/internal/v1/realtime/topics     ← 主题登记 / 注销（服务级密钥）
/internal/v1/realtime/publish    ← 推送（服务级密钥）
```

`/internal/` 边缘一律 deny，服务级密钥逐字 `hmac.compare_digest` 比较，
**密钥未配置时一律拒绝**（fail-closed）。

## 9. 数据

`realtime` schema，两张表，**都不含业务字段**：

| 表 | 装什么 |
| --- | --- |
| `topic_declaration` | 主题、声明的权限码、推送方、`seq`、登记时间 |
| `subscription` | 用户、连接、主题、订阅时间 |

写独占读放行：只有本服务写 `realtime` schema。
