# 预测后处理作为推理链上模型之后的步骤

预测值常有业务硬约束，例如能耗不能为负。这类修整以 `postprocess` 大类的算子表达，
接在回归模型的打分口之后，发布时冻结进 `serving_json.steps`，排在模型步之后执行。
训练时改写打分帧的预测列，推理时改写模型算出的数，两边共用一个方法，下游评估因此
能看到处理后的指标。

不把它做成模型算子的参数：那样每个模型家族都要各写一份，且看不出评估量的是处理前
还是处理后。也不放在调用方或公式里：训练评估、单行预测、整批重算与开放接口会各走
各的口径。不用入口之前的 `clip_outlier` 代替：它裁的是特征，管不住模型算出来的数。

推理链仍是按拓扑序排成的一条直线，所以保存期图校验要求后处理只接回归模型的打分口且
不许分叉。分类的预测值是类别，异常检测与规则计算的打分帧没有预测列，都不适用。
发布的「模型步看到哪些列」改为按节点取，不再默认是链上最后一步。

可服务格式版本不升：历史版本没有后处理步，计算不变。规则随模型版本冻结，改规则要
发布新版本，部署换版沿用既有流程；后处理不进部署的签名比对，只改规则不要求确认
签名变化。一旦存在带后处理的版本，代码回滚下限是认识这三个算子的版本，否则加载时
按未知算子拒绝，不会静默返回未处理的数。
