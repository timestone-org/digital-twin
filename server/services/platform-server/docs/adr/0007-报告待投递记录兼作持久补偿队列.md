# ADR-0007：报告待投递记录兼作持久补偿队列

报告生成记录已经在业务事务中持久化模板快照、报告期、操作者与 traceparent，
`pending` 因此也是待执行工作的数据库凭据。提交后向 Redis Stream 发送的即时消息
只用于降低延迟；报告 worker 中的周期补偿独立于定时生成总开关运行，按数据库中
仍待执行的记录恢复投递，不把 Redis 暂不可用或消息丢失变成永久排队。

不新增独立 outbox 表或数据库列。仅在待执行记录的 `result_json._dispatch` 保存
内部投递状态，包括认领令牌、租约、下次尝试时间与退避次数；成功或失败终态由
正常执行结果接管。HTTP 读取只有在任务成功时才把结果解析成报告试算或导入内容，
内部投递元数据不进入公开响应。报告在途容量检查通过数据库短事务 advisory lock
串行覆盖 count 与创建，防止手动、导入及定时并发越过既有水位。

补偿每轮只在短事务中认领一条到期记录，使用 `FOR UPDATE SKIP LOCKED` 避免多个
进程同时认领，再提交事务并在有超时的事务外发送消息。领取、到期查询、发出前
及写回结果均以 PostgreSQL `clock_timestamp()` 为时间权威，
复核记录仍为 pending、认领令牌一致且租约有效；失效的持有者不再继续发布或覆盖新持有者。
一轮有数量和总耗时限制，单条发布与写回预算小于租约，关停停止新认领并 drain 在途
发布。失败采用冷却，成功后对尚未被 worker 认领的记录逐级退避，避免积压时反复灌入
相同消息。原始 traceparent 与稳定任务身份随所有补发保留。

数据库与 Redis 之间不承诺 exactly-once。进程在发布成功但写回之前中断、或网络结果
未知时，补偿可能产生重复消息。worker 的数据库 `pending → running` 条件更新才是
执行栅栏，同一任务只有一次 API 读取与 Word 执行。过期的 running 记录收敛为可见失败，
不自动退回 pending，从而不会在未知外部取数或出稿结果时重复执行；用户需要重新生成
时提交新的任务。长期 pending 不再只因年龄被标记失败。

旧版本有两个兼容边界：旧 API 把任意 result_json 当最终结果解析，旧 worker 又会
拒绝带 api_sources 的新模板快照；旧版调度器还会误终结积压很久的 pending。
因此已有环境升级时先将报告提交与导入入口置为维护状态，停止并 drain 全部旧
worker／调度器，再升级全部 API，随后启动新版 worker，最后恢复报告写入口与前端。
不能让不兼容的旧 API 或旧 worker 长期混部。独立全新验收环境不经过这个混部窗口。

回滚不能只换回旧 worker：它不认识新快照。需要保留兼容版本，或暂停报告功能后
整体执行已验证的兼容回滚；API 不得退到不理解内部投递字段的版本，直到这些元数据
已通过受管流程完全消失。应用回滚不删除模板、原件、生成记录或报告文件。
