# opcua-server 上下文

对上位系统（SCADA、MES）暴露 `opc.tcp` 端点的发布面。单进程内托管多个逻辑独立的服务器实例。数据在 `opcua` schema，写独占（ADR-0003）。独立成代码单元的理由见 [ADR-0006](../../../docs/adr/0006-opcua服务端独立成代码单元.md)。

---

## 1. 通用语言

| 词 | 指什么 | 不是什么 |
|---|---|---|
| **实例**（instance） | 一台逻辑上独立的 OPC UA 服务器：一个端点、一段地址空间、一组凭据 | 不是进程，也不是容器——多个实例共处一个进程 |
| **端点**（endpoint） | `opc.tcp://<host>:<port>/<path>`，上位机连的地址 | 不是 HTTP 管理面的 `/api/v1/opcua` |
| **端口池**（port pool） | 部署期声明的一段可用端口（默认 `4840`–`4859`） | 不是运行期可扩的资源 |
| **地址空间**（address space） | 实例内的节点树：对象、变量、属性、类型、方法 | 不是平台的点位台账 |
| **标识**（identifier） | NodeId 里由人指定、实例内唯一、**永不自动变化**的那一段 | 不是命名空间索引（那个由系统钉死为 2） |
| **上位机**（client） | 连上来的 OPC UA 客户端 | 不是平台的 Web 用户 |
| **实例凭据**（credential） | 上位机用来连 opc.tcp 的账号 | **不是** auth-server 的人类用户 |
| **待重启生效**（pending restart） | 已保存但要重建 `Server` 对象才生效的配置改动 | 不是「保存失败」 |

## 2. 不变式

1. **值的权威源是进程内存**，不是数据库，也不是 Redis。Redis 只做跨进程可见性投影，读它必须当作可能陈旧。
2. **节点值不落库。进程重启后所有节点回到初值**——这是明确语义，不是缺陷。需要历史时走二期的 HistoryRead，那会带自己的存储决策。
3. **标识永不自动变化。** 上位系统的组态里硬编码着 NodeId，我们这边一变，现场所有组态一起废。
4. **命名空间索引由系统钉死为 2**，不暴露给用户填——它是服务器启动时按注册顺序分配的内部序号，多实例下同一个 URI 未必拿到同一个索引。
5. **实例是否在运行，以本地监听端口的实况为准**，不以任何缓存标志位为准。标志位说在跑而端口没开，是最难排查的一类故障。
6. **端口池满即响亮失败**，不许静默降级成一个「显示运行中但连不上」的实例。
7. **私钥只在挂载卷**（`OPCUA_PKI_DIR`），库里只存指纹与主体。私钥进库会随数据库备份跑到任何存备份的地方。

## 3. 非目标

这些**明确不做**，不是漏项：

| 不做 | 原因 |
|---|---|
| OPC UA PubSub | asyncua 不支持 |
| GDS（全局发现服务） | asyncua 不支持，且单机部署无收益 |
| Issued Token 身份令牌 | 需要外部 STS，本系统没有 |
| 桥接内部点位 | 会让本服务依赖采集运行时。留插件点不实现。⚠ `/internal/v1/opcua/nodes:*`（§8）**不违反这一条**：依赖方向仍是别人调我们，本服务照样不认识点位台账、房间、模型是什么 |
| 租约竞选与热备 | 端口独占让热备热不起来，见 ADR-0006 |
| 方法节点（`node_class=method`） | 方法要绑定服务端回调（`link_method`），而本服务没有可绑定的用户代码。建节点时**显式拒绝**，不入库——留着一个调用即报错的方法节点比没有更糟 |

二期（留接口不实现）：自定义事件与 Alarms & Conditions、HistoryRead、向 LDS 注册。

## 4. 多实例的隔离边界

每个实例一棵独立的 task 树 + supervisor，单实例故障不牵连其它实例。

⚠ **`asyncua` 里有两处进程级全局，多实例下会骗人：**

- `InternalSession._current_connections` 是**类属性**，把所有实例的连接数加在一起。**不许**用它做单实例计数。
- 对第三方类做 monkey-patch 会影响进程内全部实例。**禁止**，会话追踪走 §5 的注入点。

## 5. 会话追踪：为什么是子类注入

`asyncua` **没有会话注册表**——`InternalServer.create_session()` 只构造不登记，标准的 `SessionDiagnosticsArray` 节点只有定义、没有任何代码往里写值。

因此走**子类注入**（不是 monkey-patch）：

```
Server(iserver=<InternalServer 子类>)      ← 构造参数，真实注入点
  └─ create_session(name, ...)             ← name 即 transport 的 peername
       └─ <InternalSession 子类>           ← activate_session / close_session 里登记与注销
```

代价是绑定了 `asyncua` 的两个子类面，它们不在文档化的公开 API 里。因此：

- `asyncua` **钉死版本**，不用范围约束。
- 契约测试断言这两个扩展点的签名与行为，升级时由 CI 红灯拦住。
- 一旦上游改签名，表现是启动即 `TypeError` ——**响亮失败**，而不是静默返回空会话列表。

## 6. 生效档位

配置改动分两档，**API 必须回答「本次哪些改动尚未生效」**：

| 档 | 字段 | 行为 |
|---|---|---|
| 热生效 | 加节点、删节点、写值、节点 access_level（可写位） | 立即生效；access_level 热改失败时不回滚保存，实例转待重启并把它计入本次返回的 `pending_fields` |
| 待重启 | BrowseName、数据类型、端口、安全策略、命名空间 URI | 保存成功，实例进入「待重启生效」状态 |

⚠ 反面教材：接口返回成功、实际没生效、也不告诉用户——静默失效比报错难查一个量级。「待重启生效」是实例上的**显式字段**，不是前端猜的。

## 7. 身份与凭据

上位机的账号池与 auth-server 的人类用户**完全分离**：上位机账号不该能登录 Web，人类用户也不该把登录密码填进某台 SCADA 的连接配置里。

- UserName：`opcua_instance_credentials` 存哈希（复用 `lib/auth/password`），**明文只在创建时返回一次**。
- X509：`opcua_instance_trusted_certs` 按指纹白名单，公钥进库（公钥不是秘密）。
- `user_manager` 是 per-instance（挂在 `iserver` 上），但 `get_user()` **收不到会话或对端**，无法单靠它把身份与连接对应——这正是 §5 需要注入点的原因。

## 8. URL 形状

对外前缀 `/api/v1/opcua`，错误码领域号 `21`。起停等动作走 `POST …:verb`。创建实例与写节点值**必须支持 `Idempotency-Key`**——上位机侧的重试与向 PLC 下发写值是同一类风险。

内部前缀 `/internal/v1/opcua`，边缘对 `/internal/` 一律 deny，认证走 `X-Service-Key`：

| 端点 | 给谁 |
|---|---|
| `POST /nodes:resolve` | 调用方在**绑定的那一刻**校验节点还在不在、类型对不对 |
| `POST /nodes:write` | 批量写值，**逐项回执**（一项失败不牵连其余项） |

⚠ 内部面与公开面的失败口径**有意不同**：公开面一个节点写不进就整条失败；内部面的调用方一次要写一批点位，让一个失效的绑定拖垮其余几个，现场读到的会是一整批陈旧值。口径见 [`docs/AC_PUBLISH_DESIGN.md`](../../../docs/AC_PUBLISH_DESIGN.md) §2。
